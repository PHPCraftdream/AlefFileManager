# Alef как среда исполнения приложений нового типа

Документ собирает в одном месте замысел, о котором договорились 2026-10-06: Alef — не только фреймворк для сборки десктопных программ, а **универсальная среда исполнения**. Её ставят на машину один раз, а приложения для неё — пакеты с JS-кодом. Детали разнесены по плану: `FRAMEWORK-PLAN.md` §2, §6.3, §6.4, §10 (решения 7–12) и этапы в `stages/`. Здесь — общая картина и связи между частями.

## 1. Идея

- **Приложение — архив с JS-кодом** (пакет `.alef`). Он пользуется только `@alef-tron/api` и веб-платформой. В пакете нет Rust и нет своего бинарника.
- **Среда — бинарник `alef`.** Внутри Servo и Rust-модули. Servo служит прослойкой между Rust и JS: даёт JS-движок, веб-платформу (`fetch`, WebSocket, таймеры, crypto, DOM) и наш транспорт `native://`. Rust-модули дают то, чего у веба нет: файлы, процессы, сокеты, серверы, окна, систему.
- **Поставка как у Java.** Runtime ставится отдельно, как JRE, приложения запускаются им. Единая сборка, где runtime вшит в установщик приложения (как `jpackage`), — необязательная опция.
- **Одна среда — с окнами и без.** Одно и то же приложение может быть оконным, консольной утилитой или службой. Режим задаёт манифест.

## 2. Режимы исполнения

| Режим | Манифест | Что есть у приложения | Типичный пример |
|---|---|---|---|
| окно | `windows` не пуст | окна, ввод, все модули | файловый менеджер, редактор |
| консоль | `windows: []`, `console: true` | stdin/stdout/stderr потоками, код выхода (`app.exit`) | утилита в конвейере `echo data \| app` |
| служба | `windows: []` без консоли | долгоживущие серверы, фоновая работа, завершение по сигналам | локальный API, MCP-сервер, агент синхронизации |

- В безоконных режимах документ приложения исполняется в скрытом `WebView` на программном контексте отрисовки (`SoftwareRenderingContext` в Servo 0.6), без winit. Кадры не рисуются, refresh driver стоит.
- Модули, которым нужно окно (`window`, `screen`, `dialog`), в безоконных режимах отвечают `NOT_AVAILABLE`.
- Регистрацию службы ОС (Windows Service, systemd, launchd) делает установка или автозапуск. Сам runtime в режиме службы консоли не требует.
- **Сначала спайк M0.5** (`stages/m0-spikes.md`): работает ли это без дисплея. Главные риски: Linux-сервер без X/Wayland и Windows-служба в session 0, где нет рабочего стола. От итога зависят формулировки M4 и M7.

## 3. Пакет `.alef`

- **Содержимое.** zip: `alef.ktav` в корне, ассеты, `icon.png`, `META-INF/` (список хешей всех файлов и подпись ed25519 разработчика).
- **Без распаковки.** Ассеты читаются из архива, мост получает источник ассетов «каталог или архив». Каталог остаётся для разработки (`dev`).
- **Требование к runtime.** Манифест задаёт `runtime: ^X.Y`.
- **Подпись.** Проверяется до запуска: пакет с изменённым файлом не запускается. Неподписанный пакет запускается с предупреждением, если так решил пользователь.
- **Сборка пакета:** `alef-tron build` собирает приложение, `alef-tron pack` упаковывает и подписывает; ключ разработчика создаёт `alef-tron keys`.

## 4. Runtime и лаунчер

- **Версии рядом:** `<корень Alef>/<версия>/alef`.
  - В системе один лаунчер `alef`, он выбирает версию по `runtime` из манифеста, как `javaw`/`py`.
  - Подходящей версии нет — понятная ошибка и команда `alef runtime install <версия>`.
  - Лишние версии убирает `alef runtime prune`.
- **Почему версии рядом:** до 1.0 minor может ломать API, и обновление runtime не должно ломать установленные приложения.
- **Совместимость.**
  - Лаунчер проверяет диапазон из манифеста.
  - Рукопожатие `runtime.hello` проверяет версию протокола и API; несовместимость даёт понятную ошибку, отсутствующий модуль — `NOT_AVAILABLE`.
- **Самообновление runtime.** Новая версия ставится рядом со старыми, подпись обновления проверяется (ed25519, ключ проекта).
- **Размер** (~118 МБ release на Windows) теперь размер одной установки, а не каждого приложения.

## 5. Запуск, установка и идентичность приложения

- **Запуск на месте:** `alef run app.alef -- <аргументы>` или двойной клик по `.alef`.
- **Установка:** `alef install app.alef` (или согласие при первом запуске). Копирует пакет в каталог приложений пользователя и создаёт **идентичность приложения**, хотя бинарник общий:
  - Windows: ярлык с AppUserModelID — своё имя и значок на панели задач, свои уведомления;
  - macOS: тонкая обёртка `.app` (`Info.plist`: id, имя, значок, описания TCC), которая запускает `alef run`;
  - Linux: `.desktop` с `MimeType`.
- **Регистрации в системе.** Ассоциации файлов, deep links и автозапуск регистрируются как `alef run <пакет> ...`.
- **Удаление:** `alef uninstall <id>` убирает всё созданное.
- **Обновление пакета** — `updater`. Подпись проверяется тем же ключом, что раньше; другой ключ — отказ и новый вопрос о доверии. Новые права спрашиваются заново.
- **Без установки** уведомления, deep links и автозапуск работают с деградацией: понятная ошибка `NOT_AVAILABLE`.

## 6. Права: подтверждает пользователь, может подменить

Среда запускает чужие архивы, поэтому решает **пользователь**, а не только разработчик (`FRAMEWORK-PLAN.md` §6.4, `stages/m2b-consent.md`).

- **Окно согласия.** Перед первым запуском runtime показывает встроенное окно согласия: страница runtime, код приложения в нём не исполняется. В нём каждое право из манифеста по отдельности: каждый путь `fs`, адрес `net`, слушающий порт, объявленная команда `cli`, переменная `app.env` и остальные.
- **Три исхода для каждого права:**
  - **разрешить** — настоящий доступ;
  - **подменить** — приложение получает правдоподобную среду и не может отличить её от настоящей: нет кода ошибки, нет разницы в данных;
  - **отказать** — `PERMISSION_DENIED`.
- **Чего нет в манифесте**, по-прежнему `PERMISSION_DENIED`. Это ошибка разработчика, а не решение пользователя.
- **Хранение решений.** Решения хранятся по `id` приложения и отпечатку ключа подписи: чужой пакет с тем же `id` их не унаследует. Менять можно в любой момент: `alef permissions list|set|reset <app>` и экран настроек runtime. Пакеты доверенного ключа можно пускать без вопроса, если так задал пользователь.

| Право | Подмена |
|---|---|
| сеть (`http`, `socket`, `websocket`) и собственные загрузки Servo | соединение висит до таймаута, как при мёртвой сети |
| `listen` (серверы) | `listen()` успешен и выдаёт порт, но сокет не открыт и входящих нет |
| `fs` | виртуализация: каждый scope отображается на теневой каталог приложения; чтение видит его содержимое (сначала пусто), запись успешна, но остаётся в тени |
| `cli` | приложение **заранее объявляет фиксированные команды** (`permissions.cli.commands`); пользователь по каждой разрешает, подменяет (зависает до таймаута) или отказывает; произвольные команды (`*`) — отдельное подтверждение с предупреждением |
| `clipboard.read`, `app.env`, `secrets`, `shortcut.global` | пустой буфер; переменная не задана; теневое хранилище; регистрация «успешна», но не срабатывает |

**Честные границы:**
- Подмена не даёт криптографической неотличимости: тайминги и сравнение каналов её выдают.
- Разрешённая команда `cli` видит настоящую систему, и окно согласия говорит это прямо.
- Явный выбор файла пользователем в диалоге даёт реальный доступ к этому файлу даже при подменённой `fs`.

**Механика:**
- `PermissionSet::check` возвращает `Allow | Substitute | Deny`, решение уходит в `CallContext`.
- У каждого модуля есть ветка подмены, её юнит-тесты идут без Servo.
- Ядро согласия — отдельный этап **M2b** перед `fs`, чтобы `fs`, `net` и `cli` сразу писались с подменой.

## 7. Серверы, WebSocket и MCP

Серверы — штатный способ делать службы на Alef (`stages/m4-net-cli.md`, `stages/m4b-mcp.md`).

- **`http.serve`.** Разбор HTTP, TLS и сокеты в Rust (`hyper`, `rustls`), обработчик в JS. Запросы идут потоком в документ с credit. Сервер — ресурс сессии. Режим `files` отдаёт статику без захода в JS.
- **`websocket.serve`** или `req.upgrade()` из `http.serve`: HTTP и WebSocket на одном порту.
- **`@alef-tron/mcp`** — JS-пакет поверх модулей. Спецификация MCP меняется быстро, поэтому пакет обновляется отдельно от runtime.
  - Сервер: tools, resources, prompts; транспорты stdio (консольный режим) и Streamable HTTP.
  - Клиент: stdio через `cli.spawn` и HTTP.
- **Безопасность локальных серверов:**
  - единый scope `listen:host:port` на все серверы;
  - по умолчанию **только loopback**, другой адрес — явное право и отдельная строка в окне согласия;
  - проверка `Host` и `Origin` против DNS-rebinding и CSRF;
  - bearer-токен для HTTP;
  - окно согласия предупреждает, что любой локальный процесс сможет вызывать инструменты MCP-сервера.
- **Граница:** каждый запрос идёт через мост Servo. Этого хватает для API, WebSocket-каналов, MCP и локальных инструментов, но не для высокой нагрузки — для неё нужен Rust-хост.
- **Что нужно в транспорте:** транспорт v2 надо дополнить потоком на каждый сервер (сейчас один поток событий на документ).

## 8. Как это ляжет на этапы

| Этап | Что даёт среде |
|---|---|
| M2 (идёт) | окна (`window`, `screen` — M2.2 готов), `app`, `path`, `os`; M2.3 `dialog`, `shell`, `clipboard`; M2.4 `notification`, single-instance, restore |
| **M0.5** | спайк безоконного режима: работает ли скрытый `WebView` без дисплея на трёх ОС; замеры старта, RAM, CPU |
| **M2b** | подтверждение и подмена прав: исход «подменить», хранилище решений, окно согласия, `alef permissions` |
| M3 | `fs` с виртуализацией, `store`, `sqlite`, `crypto`/`secrets`; File Manager как обычное Alef-приложение |
| M4 | `http` (клиент и сервер), `socket`, `websocket` (клиент и сервер), `cli` с объявленными командами, режимы консоль и служба |
| **M4b** | серверы и MCP: `@alef-tron/mcp` |
| M5 | меню, трей, хоткеи, автозапуск, deep links — через идентичность приложения (`alef run <пакет>`) |
| M7a | runtime и лаунчер: установщики runtime, версии рядом, `alef run`, ассоциация `.alef`, самообновление |
| M7b | пакеты `.alef`: формат, подпись, `@alef-tron/tools` (`build`, `pack`, `keys`), `alef install`, `updater` |
| M7c | единая сборка (опция): runtime и пакет в одном установщике |

## 9. Риски

- **Безоконный режим без дисплея** (Linux-сервер, Windows-служба в session 0) не проверен. Это спайк M0.5, M4 не начинается до его итога.
- **Идентичность приложения без своего бинарника.**
  - На macOS нужна `.app`-обёртка на каждое приложение; подпись и нотаризация обёрток — открытый вопрос.
  - На Windows AUMID задаётся только через ярлык.
- **Подмена прав не даёт полной неотличимости.** Обещаем «нет кода ошибки и нет разницы в данных». Приложение, которое не переносит подмену (виснет на таймауте сети, падает без файлов), — ответственность разработчика. Шаблон `create-alef-tron` покажет, как это обрабатывать.
- **Вес среды.** Около 118 МБ бинарник и сотни МБ памяти на `WebView` (замер в release впереди). Для универсальной среды это терпимо, для множества мелких служб тяжело.
  - Лёгкий вариант на будущее — SpiderMonkey без DOM (`mozjs` уже в дереве). Это другая JS-среда и отдельная большая работа, вне MVP.
- **Несколько версий runtime рядом:** место на диске и поддержка старых версий. До 1.0 исправления безопасности выходят только для последней minor.
- **Хранилище решений о правах** — цель для атак. Оно лежит в каталоге данных runtime, вне scopes `fs` любого приложения, и пишется только процессом runtime.

## 10. Открытые вопросы

- **Итог спайка M0.5.** Нужен ли запасной путь (скрытое окно 1×1, `Xvfb` в поставке), и можно ли обещать «службу» на всех ОС или только «консольное приложение».
- **Подпись и нотаризация macOS-обёрток** для установленных приложений.
- **Удалённый доступ к MCP-серверам** (OAuth из спецификации MCP) — отдельным решением, не в M4b.
- **Настоящая видимость и фокус в тестах.** Тихий режим e2e (`ALEF_E2E_QUIET`) подменяет видимость, фокус, maximize/minimize и fullscreen собственным учётом, поэтому настоящий показ окна проверяют только `startup` (Windows, с `ALEF_E2E_VISIBLE=1`) и CI на Linux под `xvfb`.
