# M8 — Проводник: события ФС, иконки и контекстное меню

## Цель

Дать приложению-проводнику (File Manager и подобным) то, что есть у системного проводника: события об изменениях файловой системы и томов, системные иконки файлов и папок, элементы системного контекстного меню файла и их вызов. Всё асинхронно или потоком событий: ни один вызов не блокирует страницу, тяжёлая работа идёт вне потока интерфейса.

| Часть | Что |
|---|---|
| M8.1 | `fs.watch`: событие `attrib`; `fs.volumes()` и `fs.watchVolumes()` — тома, подключение и отключение |
| M8.2 | `shell.fileIcon()` — системная иконка файла, папки, диска или типа (PNG) |
| M8.3 | `shell.contextMenu()` — элементы системного контекстного меню и `invoke` |

Уже есть (M3.2): `fs.watch(path, { recursive })` — `create`/`modify`/`remove`/`rename`/`overflow` потоком (`AsyncIterable`), `readDirStream` пачками.

## M8.1 — события ФС и тома

`fs.watch(path, { recursive?, signal? })` — `AsyncIterable<WatchEvent>`: `create`, `modify`, `attrib`, `remove`, `rename` (с `to`, если ОС его сообщает) и `overflow`. `attrib` означает изменение метаданных, например режима или времени, без изменения содержимого. При `overflow` потребитель перечитывает каталог/состояние. События короткого интервала объединяются; порядок и полнота между разными каталогами не гарантируются.

`fs.volumes(): Promise<Volume[]>` возвращает текущие видимые точки монтирования с `root`, `readOnly`, `kind` (`fixed|removable|network|optical|ram|unknown`) и доступными метаданными (`label`, `fileSystem`, `total`, `free`). Список не обещает все устройства системы: он ограничен видимым пространством процесса и текущей реализацией платформы. Корень — системное написание пути; на macOS том системного Data-корня может представляться как `/`. Удалённые/сетевые и неизвестные типы не угадываются как removable.

`fs.watchVolumes({ signal? }): AsyncIterable<VolumeEvent>` сообщает `mount`, `unmount`, `change`; `change` — свойства тома, не события файлов и не свободное место само по себе. Поток запускается с текущей наблюдательной подпиской, не воспроизводит историю. Закрытие итератора или abort закрывает поток и освобождает ресурс сессии; очередь ограничена. Ожидания ОС, блокирующие вызовы и обходы выполняются вне UI-потока; отмена не обязана прерывать уже выполняющийся системный вызов.

**Право и подмена.** `fs.watchVolumes` проверяет право до запуска наблюдения. Если наблюдение запрещено или подменено, возвращается завершённый пустой поток: задача watcher и ресурсная аренда не создаются. Источник — только объявленное `permissions.fs.read` с решением пользователя `allow`; достаточно любого одного `Allow fs.read`, не требуется разрешать все права. Без этого права `fs.volumes()` возвращает `[]`, а `watchVolumes` не выдаёт события; выбор файла через dialog/file-drop не даёт доступа к перечню системных томов. При `substitute` `fs.volumes()` возвращает `[]`, `watchVolumes` не выдаёт событий, а `fs.watch` продолжает наблюдать подменённую область (и может выдавать shadow events). Гранты `fs.write` без разрешённого чтения недостаточны. Unix volume labels отсутствуют.

**Платформенные пределы наблюдения.** Windows использует `GetLogicalDrives`, `GetVolumeInformationW`, `GetDriveTypeW` и `GetDiskFreeSpaceExW` в worker-опросе раз в секунду; этот опрос нужен также потому, что скрытое окно для `WM_DEVICECHANGE` не используется. Linux использует `/proc/self/mountinfo` и `statvfs`; ожидает `poll(2)` `POLLPRI`/`POLLERR` с таймаутом 1с для отмены и сверяет список после сигнала (периодической сверки по таймауту нет). Пропускаются pseudo-файловые системы `proc`, `sysfs`, `cgroup`, `cgroup2`, `devtmpfs`, `devpts`, `securityfs`, `debugfs`, `tracefs`, `configfs`, `pstore`, `mqueue`, `hugetlbfs`, `fusectl`, `rpc_pipefs`, `autofs`, `nsfs` и `binfmt_misc`; `tmpfs` учитывается только под `/media` и `/run/media`; `overlay` учитывается только для `/`, остальные пропускаются. macOS использует `getmntinfo`/`statfs` и наблюдает `/Volumes` с последующей сверкой списка; `/System/Volumes/*` пропускаются, кроме `Data`, который представляется как `/`. Точность `attrib` зависит от backend и файловой системы: Windows-событие, которое не позволяет отличить метаданные от содержимого, не считается доказательством metadata-only `attrib`.

**ТЕКУЩАЯ реализация, не полное соответствие BUS.** Проверка права (снимок стартовых решений; асинхронный диалог согласия не реализован здесь) и краткое перечисление вынесены в общий для модуля `BlockingExecutor`: локальный бюджет — 8 ожидающих/выполняемых заданий, насыщение возвращает `BUSY`. Это не глобальный и не сессионный лимит. Постоянный watcher работает в отдельном blocking worker, который владеет источником и его уничтожением; async pump обслуживает только ограниченную очередь, credit и закрытие потока. Контракт лимитов ресурсов сессии ограничивает watcher, но это не полная миграция BUS; новый синхронный IO на BUS не добавлен.

**Проверка.** Условная Linux E2E-проверка проверяет сценарий mount/unmount реального tmpfs под `/media/alef-e2e-fs-<pid>-<uuid>` после успешного `sudo -n true`; иначе проверка пропускается с причиной в targets. Точка монтирования уникальна и находится вне обычного scratch. При старте удаляются только устаревшие каталоги с точным префиксом, чей PID завершился; symlink не удаляется. В `finally` проверяется фактическое состояние через `/proc/self/mountinfo`, выполняется unmount и удаление каталога; если размонтировать не удалось, смонтированный каталог сохраняется. Описана проверка, не утверждение об успешном запуске полного runner.

## M8.2 — иконки

### API и границы безопасности

`shell.fileIcon(target, options?)` возвращает `{ png: Uint8Array, width, height }`. В `target` допускается ровно один селектор: `{ path }`, `{ extension }`, `{ mime }` или `{ kind: 'folder' | 'file' | 'drive' }`. Поддерживаемые размеры запроса: `16, 24, 32, 48, 64, 128, 256`; размер по умолчанию — `32`. Фактические размеры PNG сообщает ответ: платформенный источник может вернуть ближайший доступный размер или общий резервный PNG `32×32`.

Для `{ path }` backend сначала проверяет разрешение `fs.read`, затем существование пути, и только потом передаёт его рабочему потоку ОС. При политике подмены результатом служит встроенная общая иконка, без системного запроса по этому пути; отказ в разрешении также не доходит до OS lookup. Запросы без пути используют системные ассоциации типов/иконок и не требуют чтения файла.

### Выполнение, очередь и кэш

Подготовка (включая авторизацию и проверку существования), завершение кэша и формирование base64-ответа выполняются через общий `BlockingExecutor` с ограниченной admission capacity (32); это не выделенный OS pool. Запуск выделенного потока `shell-icons` также вынесен в `BlockingExecutor` с admission capacity 1; инициализация может вернуть `BUSY` при одновременном старте. Очередь Tokio ёмкостью 32 к этому потоку отклоняет переполнение с `BUSY`. Таймаут ожидания/ответа — 30 секунд; подготовка handler до этого ограничения пока не включена. Отмена queued job пропускается до OS lookup; активный системный вызов не прерывается. Кэш ограничен 256 записями для целей типа/расширения/MIME/вида; результаты путей не кэшируются.

### Источники и ограничения платформ

- **Windows:** для путей размером до 32 px используются системные small (16 px) и large (32 px) значки `SHGetFileInfoW`. При запросе больше 32 px путь обслуживается через `IShellItemImageFactory::GetImage` с флагом `SIIGBF_ICONONLY`; миниатюры не запрашиваются. Для расширений, MIME и видов при размере больше 32 px используется системный список значков: 48 px (`SHIL_EXTRALARGE`) при запросе меньше 128 px и 256 px (`SHIL_JUMBO`) начиная с 128 px; фактический размер PNG может отличаться от запрошенного. COM STA инициализируется на выделенном потоке; ожидание задания использует auto-reset event очереди вместе с `MsgWaitForMultipleObjectsEx`, поэтому поток обрабатывает сообщения Windows и в простое. Очередь ограничена 32 заданиями; отправка сигнализирует event после успешной постановки. Активный системный вызов отменить нельзя; сообщения обрабатываются при возврате из него.
- **macOS:** `NSWorkspace` получает системный значок на выделенном рабочем потоке; возвращаемый разделяемый `NSImage` копируется, после чего копия, `NSBitmapImageRep`, контекст растровой графики и отрисовка используются только этим потоком внутри autorelease pool. Рисование идёт в offscreen bitmap context, предыдущий текущий контекст восстанавливается guard-объектом. Вызовы не создают `NSApplication`, окна или views и не выполняют UI-действий; это не фиктивный UI-поток и не обход требования выполнять AppKit UI на главном потоке. В [Thread Safety Summary](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/ThreadSafetySummary/ThreadSafetySummary.html) `NSWorkspace` перечислен среди thread-safe классов; `NSImage` не является thread-safe, но допускает использование одним потоком за раз. Раздел [Drawing in a Thread](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/ThreadSafetySummary/ThreadSafetySummary.html#//apple_ref/doc/uid/20000736-SW4) описывает поточные контексты графики и растровое рисование вне экрана.
- **Linux:** предпочтительная тема читается из GSettings, схема `org.gnome.desktop.interface`, ключ `icon-theme`; небезопасное имя темы игнорируется. GIO определяет тип без инициализации GTK, файлы темы ищутся вручную с учётом `Inherits`; порядок ограничен 32 темами, включая `Adwaita` и `hicolor`. Для размеров выбирается точное совпадение, затем больший размер по возрастанию, затем меньший по убыванию; после них проверяются scalable-ресурсы. Не найденный или нечитаемый ресурс для непутевого запроса даёт общую запасную иконку. Это не полная реализация каталогов тем Freedesktop.

### Проверки и доказательства

Общий `run_worker_loop` пропускает отменённое задание очереди до обращения к ОС. Тест `bounded_queue_skips_cancelled_jobs_and_replies_to_live_ones` проверяет пропуск отменённого задания, ответ на активное и отказ при заполненной очереди. Общие тесты проверяют допустимые размеры, выбор ближайшего размера при равенстве, PNG-кодирование и сигнатуру/IHDR, разбор цели и MIME/расширений, ограничение и ключи кэша. Linux-тесты проверяют безопасность имени темы, наследование, выбор размера и общую иконку при отсутствии ресурса; отдельный тест проверяет реальный GIO-запрос и запасной PNG на временной цели. Windows-тесты проверяют восстановление альфа-канала, выбор размера/флагов и реальный размер IHDR PNG для путевого значка больше 32 px и общего значка из списка Windows. macOS-тест проверяет сигнатуру и размеры IHDR PNG после получения и отрисовки реальных значков папки через `NSWorkspace` в размерах 16, 48 и 256 px; ожидание результата ограничено пятью секундами, ошибки не пропускаются. Эти тесты добавлены или присутствуют в исходниках, но в рамках этой финализации не запускались; сборка и CI также не запускались.

## M8.3 — контекстное меню

`shell.contextMenu(paths, { extended? })` асинхронно возвращает `ContextMenu`: `items` с `id`, `label`, `enabled` и необязательными `checked`, `default`, `separator`, PNG `icon` (`Uint8Array`) и рекурсивным `submenu`; методы `invoke(id)` и `close()` работают с native-сессией. Это ресурс в глобальном лимите `ResourceTable`; UI приложения само отображает элементы, системное popup-окно не рисуется. Проверка путей: все цели должны иметь один и тот же канонический родительский каталог; каждый путь проверяется как `fs.read`.

При объявленном `shell.contextMenu` решение согласия обрабатывается явно: `Allow` разрешает обычную работу, `Substitute` возвращает пустое меню и запрещает `invoke`, а `Deny` (как и отсутствие права в манифесте) возвращает `PermissionDenied`. `contextMenuRunas` по умолчанию выключен; `runas` запрещён до проверки наличия пункта меню и до обращения к backend. Опасные `open`/`open-with` используют те же ограничения, что `openPath`; `trash` требует `fs.write`.

Реализация платформ: Windows использует COM STA с message loop, private canonical-verb map и ленивый `QueryContextMenu` через `WM_INITMENUPOPUP`; HWND равен null, поскольку host не предоставляет native handle. macOS использует `LSCopyApplicationURLsForURL`/`LSOpenFromURLSpec` (отклонение от NSWorkspace document). Linux запускает GIO `all_for_type` на синхронном native thread; не утверждается, что GTK-контекст инициализирован. Проверка полномочий выполняется на общем ограниченном permission executor (ёмкость 64), затем native-работа выполняется на отдельном общем ограниченном executor (ёмкость 64); COM использует собственную STA-очередь ёмкостью 8 и pump. Согласие сохраняется при запуске, поэтому отдельного prompt на вызов нет; полномочия перепроверяются перед исполнением. Принудительный таймаут расширений shell не гарантируется. macOS использует LaunchServices без AppKit UI.

Не реализованы native drawing, DnD verbs и fallback «Send to»; сторонние shell extensions требуют ручной проверки.

## Приёмка

| Проверка | Как |
|---|---|
| `attrib` приходит при смене прав/времени; тома перечисляются, подключение виртуального тома видно событием | e2e + unit |
| Иконка файла, папки, типа: PNG нужного размера на трёх ОС | e2e |
| Контекстное меню файла: элементы есть, `invoke` безопасного элемента выполняется; без права — подмена (пустое меню) | e2e + ручная (расширения оболочки Windows) |
