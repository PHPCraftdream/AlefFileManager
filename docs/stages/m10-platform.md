# M10 — Платформа: журнал приложения и отладка страницы

В каталоге API (`../API-ROADMAP.md`) два пункта не закрыты ни одним этапом: `log` (журнал в файл и отчёты о сбоях) и `devtools` (отладка страницы). Этап описывает оба. Решения по каждому записываются раньше кода: оба затрагивают границу доверия между недоверенным приложением и runtime.

| Часть | Что | Статус |
|---|---|---|
| M10.1 | `log`: журнал приложения в файл и отчёты о сбоях | дизайн ниже появится вместе с реализацией |
| M10.2 | `devtools`: отладка страницы Servo devtools только в режиме разработки | спайк закончен, решение ниже |

## M10.2 — devtools

### Что выяснено (спайк по коду Servo 0.6.0, без запуска)

- Сервер devtools входит в зависимости `servo` безусловно (`servo-devtools`, `servo-devtools-traits`, не `optional`): отдельной cargo-feature нет, размер бинарника и дерево зависимостей при включении не меняются. Новых крейтов для Supply (`cargo-deny`, MSRV) не нужно.
- Запуск — настройка `Preferences` до `ServoBuilder::build`: `devtools_server_enabled` (по умолчанию `false`) и `devtools_server_listen_address` (по умолчанию пусто). Пока `devtools_server_enabled == false`, ни потока, ни порта нет.
- Адрес: пустая строка — `127.0.0.1:7000`; значение `SocketAddr` используется как есть (то есть можно привязать и к внешнему интерфейсу); число — порт на `127.0.0.1`; нераспознанное — `127.0.0.1:7000`. Порт `0` не годится: Servo сообщает встраивателю `address.port()`, а не фактический порт. Занятый порт — `ServoError::DevtoolsFailedToStart` встраивателю, страница продолжает работать без отладки.
- Протокол — Firefox Remote Debugging Protocol по TCP, без шифрования и без собственной аутентификации. Подключившийся клиент видит страницы и исполняет в них JavaScript.
- Защита на стороне Servo: каждое входящее соединение проходит `allow_devtools_client`. Клиент, первым пакетом приславший `25:{"auth_token":"<токен>"}` с токеном, который Servo выдал встраивателю (`ServoDelegate::notify_devtools_server_started(port, token)`), пропускается без вопроса. Остальные порождают `ServoDelegate::request_devtools_connection(AllowOrDenyRequest)`; реализация по умолчанию ничего не отвечает, а неотвеченный запрос закрывается ответом `Deny` (`servo.rs`, `EmbedderMsg::RequestDevtoolsConnection`). Значит, при включённом сервере и пустом делегате любой клиент без токена получает отказ: безопасное умолчание уже есть.

### Модель угроз

Отладчик с доступом к странице равен JavaScript страницы: он может вызывать мост с capability-токеном этой страницы, но не получает ничего сверх прав, которые пользователь выдал приложению. Опасность другая: любой локальный процесс (в том числе другого пользователя той же машины) может подключиться к порту на `127.0.0.1` и действовать от имени приложения. Поэтому:

1. Включить devtools может только тот, кто запускает runtime: у приложения нет ни поля манифеста, ни вызова моста. Переменной окружения тоже нет, включение всегда явный флаг командной строки.
2. Каждое подключение подтверждает пользователь вне страницы. Подтверждение рисует runtime.
3. Только `127.0.0.1`. Адрес не настраивается.
4. Пакеты `.alef` не отлаживаются: подпись и неизменяемость пакета были бы пустыми, если бы к странице можно было подключить отладчик. Флаг для пакета отвергается так же, как `--dev-url`.

### Решение

Делаем, минимально и только для разработки.

- Флаг `--devtools[=ПОРТ]` у `alef --app <каталог> [--dev-url …]` (порт по умолчанию `7000`, `0` отвергается); у `alef-runtime dev` — тот же флаг, передаётся рантайму как есть. Для пакета (`alef run <пакет>`, `--app <файл>`) флаг отвергается, код 2, сообщение в стиле `--dev-url is not accepted for a package`. Переменной окружения нет.
- Настройки Servo: `devtools_server_enabled: true`, `devtools_server_listen_address: "127.0.0.1:<порт>"`.
- `ServoDelegate::request_devtools_connection` показывает модальный диалог `rfd` «Отладчик на этом компьютере просит доступ к странице приложения «<имя>» (<id>). Разрешить?», кнопка по умолчанию — «Отказать»; закрытие окна — отказ. Диалог идёт тем же путём, что остальные диалоги runtime (`window/host/dialogs.rs`), и не должен блокировать поток Servo дольше, чем ждёт ответа сам запрос. Одновременно не больше одного диалога: остальные запросы получают `Deny`.
- Токен (`notify_devtools_server_started`) в обычных сборках нигде не печатается и не сохраняется. В сборке с feature `e2e` он печатается строкой `ALEF_E2E devtools port=<порт> token=<токен>` для проверки.
- `ServoError::DevtoolsFailedToStart` — строка в stderr `alef: DEVTOOLS_UNAVAILABLE: port <порт> is not available` и выход с кодом 1 до показа окна: отладка запрошена явно, молчаливое отсутствие её хуже ошибки.

### Приёмка

| Проверка | Как |
|---|---|
| Без `--devtools` порт не слушает | e2e: соединение с `127.0.0.1:7000` отклонено |
| С флагом сервер слушает только loopback | e2e: приветствие root-актора по `127.0.0.1`; адрес привязки не внешний |
| Клиент с токеном принят, без токена — отказ | e2e на сборке `e2e`: первый пакет с токеном → приветствие; без токена и без ответа делегата → закрытие |
| Флаг для пакета отвергнут | unit разбора аргументов + e2e код 2 |
| Занятый порт | e2e: `DEVTOOLS_UNAVAILABLE`, код 1 |
| Диалог подтверждения | ручная: Firefox → `about:debugging` → `127.0.0.1:7000` → окно с отказом по умолчанию |

### Не цели

Свой интерфейс отладчика; удалённая отладка и привязка не к `127.0.0.1`; постоянная настройка в манифесте или конфиге; отладка пакетов; управление отладчиком из страницы.

### Риски

- Код встраивателя в `alef-runtime` (Servo) собирает только CI: каждая правка стоит полного прогона.
- Протокол и набор актёров Servo devtools нестабильны между версиями Servo: поведение проверяется только приветствием root-актора, не функциональностью отладчика.
- Диалог подтверждения зависит от того, что умеют диалоги runtime на конкретной ОС (на Linux — от портала или GTK); если показать его нельзя, запрос получает `Deny`.
