# M6 — Медиа

Обзор: `../FRAMEWORK-PLAN.md`. Решение владельца проекта (2026-10-18): отложение снято, выбран **вариант B** — нативный API без GStreamer (критерий 2: размер дистрибутива важнее стандартных web API); решение обратимо. M6.1 — спайк: кадры 1280×720@30 виртуальной камеры через транспорт в `<canvas>` (задержка, потери, CPU), синус микрофона и checksum-приёмник — всё на виртуальных устройствах, чтобы сценарий шёл в CI без железа.

## Сделано в M6.1

- Модуль `media` в alef-modules: трейты `CameraBackend` / `MicrophoneBackend` / `AudioBackend`.
- Бэкенды: `MissingCamera` / `MissingMicrophone` / `MissingAudio` отвечают `NOT_AVAILABLE` в обычной сборке; виртуальные (`VirtualCamera`, `VirtualMicrophone`, `VirtualAudio`) — детерминированные, служат e2e-прогонам и тестам. Камера рисует движущийся тестовый рисунок RGBA 1280×720 с запросным fps (по умолчанию 30, диапазон 1..120); микрофон — фазо-непрерывный синус f32 (по умолчанию 440 Гц, 48000 Гц, чанк 20 мс); приёмник аудио считает сэмплы и считает FNV-1a-64 по байтам.
- Команды: `media.camera.list/open/close`, `media.microphone.list/open/close`, `audio.open/write/close`. Открывание устройства возвращает `{ camera|microphone|sink, stream }` (страница читает поток `openReadable`).
- Права: раздел `permissions.media` манифеста (`camera`, `microphone`, bool; раздел необязателен, по умолчанию закрыт) и `permissions.audio` (bool, по умолчанию false). Подмена — `NOT_AVAILABLE` без открытия устройства; отказ и необъявленное право — `PERMISSION_DENIED`. `media.camera` и `media.microphone` — risky-права («sees through the camera…» / «hears through the microphone…»), показываются в окне согласия и `alef permissions` наравне с остальными.
- JS: субпуть `@alef-runtime/api/media` (`./media` + `./media/types`): объекты `camera` (`list`, `open`), `microphone` (`list`, `open`), `audio` (`open`); классы `Camera`/`Microphone` — async-iterable пар «заголовок+нагрузка» с `close()`, возвращающим статистику; `AudioSink` — `write(Float32Array|Uint8Array)` и `close()` со статистикой и checksum-hex; повторный `close()` отвечает `NOT_FOUND`.
- e2e: сценарий `media` (приложение `tests/e2e/apps/modules/system/media`, режимы allowed / denied / substituted), SOFT-пороги по платформам (цель — измерение на медленных раннерах): Linux и Windows ≥ 5 fps и p95 задержки < 2000 мс, macOS ≥ 0.5 fps и p95 < 5000 мс (на 1280×720@30; цифры — в разделе «Измерения спайка»); страница печатает строку `media-camera-stats frames= fps= p50_ms= p95_ms= main_ms= total_ms= drops= elapsed_ms=`; вытеснение кадров политикой drop-oldest легально: seq строго растёт, а сумма разрывов seq за прогон не превышает итоговый `dropped` из close.

## Контракт кадров и чанков

Пара кадров потока: сначала JSON-заголовок, затем binary-нагрузка — один или несколько чанков, каждый не больше транспортного чанка (256 КиБ), сумма длин которых равна `byteLength`. Камера: `{"seq","timestamp","width","height","byteLength","dropped","format":"rgba"}` + RGBA `width*height*4` байт построчно. Микрофон: `{"seq","timestamp","rate","samples","byteLength","dropped","format":"f32le"}` + little-endian f32. Короткий чанк — норма, не ошибка; нехватка или лишний байт, или новый заголовок до окончания нагрузки, — внутренняя ошибка; JS-декодер собирает чанки обратно в кадр. Поле `dropped` — сколько элементов очередь вытеснила к моменту создания элемента; продюсер никогда не блокируется (drop-oldest вытесняет только целые кадры). Закрытие: camera → `{"camera","frames","dropped"}`, microphone → `{"microphone","chunks","samples","dropped"}`, audio.close → `{"sink","samples","checksum"}` — checksum строкой-16hex: u64 не переживает JSON-число; page пишет raw LE f32 байты, приёмник fold-ит FNV-1a-64.

## Исполнение (BUS)

Продюсер — допущенное blocking-задание медиа-модуля (бюджет 8; насыщение даёт `BUSY` до старта продюсера): первый кадр сразу, дальше по тикам; остановка прерывает ожидание мгновенно, закрытие ждёт завершения задания. Между продюсером и relay — ограниченная очередь с политикой drop-oldest (камера 3 кадра, микрофон 8 чанков; счётчики pushed/dropped, вытесняются только целые кадры). Relay ждёт кредит вне BUS и пишет JSON-заголовок и binary-чанки попарно. Пути остановки — close ресурса, teardown сессии, разрыв потока; остановка идемпотентна. Закрытие устройства отменяет relay по watch-сигналу и дожидается его: незаконченный кадр отбрасывается, читатель видит `End`.

Подмена — `NOT_AVAILABLE` без открытия устройства; отказ и необъявленное право — `PERMISSION_DENIED`. `media.camera` и `media.microphone` — risky-права, их описания («sees through the camera…» / «hears through the microphone…») показываются в окне согласия и в `alef permissions` наравне с остальными.

## Измерения спайка (заполняется по CI)

Первый прогон сценария `media` в GitHub CI (1280×720@30, сырые RGBA-кадры 3,6 МБ, 60 принятых кадров, виртуальная камера):

| Раннер | fps | p50 / p95 задержки, мс | main_ms на 60 кадров | отброшено (drop-oldest) | макс. задержка вызова управления во время потока, мс |
|---|---|---|---|---|---|
| Linux x64 (headless X11) | 26,0 | 129 / 169 | 82 | 11 | 18 |
| Windows x64 | 8,8 | 177 / 450 | 186 | 140 | 37 |
| macOS arm64 | 3,1 | 655 / 831 | 114 | 206 | 343 |
| macOS x64 | 1,4 | 1007 / 1766 | 96 | 572 | 639 |

Вывод спайка: вариант B (нативный API, кадры через транспорт в canvas) работает на всех платформах, а JS-работа страницы невелика (main_ms ≪ 50 % времени), но на macOS сырой поток 720p упирается в доставку кадров от рантайма к странице: пропускная способность около 5–11 МБ/с против около 96 МБ/с на Linux, и задержка вызовов управления во время потока вырастает до 340–640 мс (на Linux до 18 мс). Поэтому пороги по платформам: macOS проверяется только на «жив и упорядочен». Прежде чем заявлять камеру на macOS, нужен профиль с меньшим разрешением/частотой или кодированные кадры, и разбор, что именно занимает поток доставки на macOS (задача после M6.1).

## Сделано в M6.2

Реальные бэкенды за cargo-фичей `media-system` в `alef-modules` (по умолчанию выключена; `e2e` её не включает; проброшена в `alef`: `media-system = ["alef-modules/media-system"]`). Две новые опциональные зависимости: `cpal = "=0.18.2"` (микрофон и вывод звука, MSRV 1.85) и `nokhwa = "=0.10.11"` (камера; фичи `input-v4l`/`input-avfoundation`/`input-msmf` включены все три, внутри crate'а каждый собирается только на своей ОС). `backend/Cargo.lock` изменился только новыми пакетами; `cargo update` не запускался.

- `media/system/camera.rs` — системная камера nokhwa: один процессный сервисный поток владеет нативной камерой; одновременно активна не более одной камеры, `list` при активной камере отвечает `BUSY`. Перечень не открывает устройства и возвращает геометрию `0`; фактические размер и частота кадров камеры сообщаются по открытию/кадрам; частота микрофона — в поле `rate` ответа `media.microphone.open`. Остановка не присоединяет сервисный поток: если нативный вызов кадра завис, лимит камеры удерживается до его возврата. Ожидание кадра ограничено максимумом из 1 секунды и трёх интервалов согласованной частоты; по истечении — фиксированная диагностика `ALEF_MEDIA_CAMERA_STUCK` и ошибка потока.
- Ограничение камеры на macOS: nokhwa ставит кадры вверх по течению в неограниченный канал; владеющий сервисный поток разбирает его и ограниченный слот drop-oldest пропускает устаревшие кадры. Эти пропуски до очереди медиа отдельно не считаются и не входят в `dropped`.
- `media/system/microphone.rs` и `media/system/audio.rs` — системные микрофон и вывод звука на cpal. Владельцы устройств ограничены общим лимитом 8, который удерживается до фактического уничтожения нативного потока; halt/close не блокируется на ожидании его завершения. Если native open/drop зависнет, занятый лимит предотвращает неограниченное создание потоков. Callbacks ОС используют try-lock кольца и фиксированный scratch на стеке; contention даёт тишину на выходе или пропускает входной чанк. Эти пропуски до очереди транспорта не отражаются в статистике.
- `media/system/audio.rs` — ограниченное кольцо `PcmRing`, callback ОС вычитывает его, underrun — тишина, overrun — drop-oldest, и то и другое со счётчиками; страницы пишут сэмплы через обычный `AudioSink`, закрытие сэмпл-синка останавливает поток ОС.
- Статистика `media.microphone.close` считает фактически поставленные в очередь сэмплы после остановки producer; `dropped` в потоковых заголовках относится только к вытесненным целым кадрам/чанкам ограниченной очередью транспорта. Внутренние пропуски камеры/микрофона и contention callback не представлены этими счётчиками.
- Чистые помощники `media/system/convert.rs` (конвертации пикселей) и `media/system/samples.rs` (кольцо `PcmRing`, конвертации аудио, подсчёт underrun/overrun) компилируются всегда и покрыты юнит-тестами обычной сборки — CI гоняет их без фичи.
- Выбор бэкендов: `Backends::system` с фичей берёт системные, без неё — Missing; пути e2e (`chosen`) всегда оставляют виртуальные устройства (в CI нет устройств). Права `permissions.media.camera`/`microphone`/`audio` работают как в M6.1; диалог прав операционной системы при первом открытии настоящего устройства — второй, независимый барьер.
- Ошибки имеют фиксированные тексты; перечисление устройств — INTERNAL при сбое ОС; неизвестный id — NOT_FOUND; отказ macOS-камеры/микрофона — PERMISSION_DENIED; другие ошибки камеры/микрофона могут быть INTERNAL или NOT_AVAILABLE в зависимости от причины. Фатальная ошибка backend завершает поток вместо вечной тишины. Известные ограничения upstream: macOS AVFoundation может ограничивать `compatible_camera_formats` условием `!= fourcc`, Windows MSMF — не более двух compatible fourcc; это может сузить перечисленные режимы. Зависимости не патчились.
- CI: шаг `Media system feature check` (`cargo check --locked -p alef-modules --features media-system`) на все ОС матрицы + `libasound2-dev` на Linux (ALSA-заголовки cpal; путь v4l nokhwa — чистые Rust-ioctl, системных пакетов не требует). MSRV-джоба supply.yml собирает без фичей — изменений не требует. Реальное железо в CI НЕ проверяется.
- Info.plist, который пишет `alef install` для приложения формата `app`, содержит `NSCameraUsageDescription` и `NSMicrophoneUsageDescription` (рендер в `backend/crates/alef/src/runtimes/install/integration/render.rs`). `packages/tools` форматы пока не объявляют эти ключи — вне среза. Реальное железо и CI не подтверждены этим описанием.
- Пропускная способность macOS для 720p (задача #179 из спайка M6.1) здесь не решается и не скрывается: системная камера на macOS упрётся в ту же доставку кадров, пока задача не сделана.
