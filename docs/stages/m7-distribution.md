# M7 — Дистрибуция

Обзор: `../FRAMEWORK-PLAN.md` §6.3. Зависит от M3 (генерический бинарник `alef`, приложения на JS поверх runtime), M2b (согласие и подмена прав) и CI из M0.4.

## Цель

Поставка как у Java: **runtime ставится отдельно, приложение — пакет `.alef`**; единая сборка (runtime в установщике приложения) — необязательная опция. Разработчик без Rust: `npm create alef-runtime` → `npm run dev` → `npm run build` даёт пакет `.alef`; `npm run bundle` — по желанию установщик с runtime внутри. Этап делится на три части.

| Часть | Что |
|---|---|
| M7a | runtime и лаунчер: установщики runtime, версии рядом, `alef run`, ассоциация `.alef`, самообновление runtime |
| M7b | пакеты: формат `.alef`, подпись, `@alef-runtime/tools`, `alef install`, идентичность приложения, обновление пакета (`updater`) |
| M7c | единая сборка (опция): runtime и пакет в одном установщике |

## M7a — runtime и лаунчер

- **Установка runtime** — установщик (Windows: MSI/NSIS, macOS: `.pkg`/`.dmg`, Linux: AppImage/`.deb`) и npm-пакеты для разработки: `@alef-runtime/runtime-win32-x64`, `-darwin-arm64`, `-darwin-x64`, `-linux-x64` (бинарник `alef`, `os`/`cpu` в `package.json`) и мета-пакет `@alef-runtime/runtime` (выбор бинарника при запуске, как esbuild). Установщики предлагают необязательную (по умолчанию выключенную) опцию прогрева / автозапуска брокера — см. `docs/stages/m11-warm-start.md`.
- **Версии рядом:** `<корень Alef>/<версия>/alef`; в системе один лаунчер `alef`, который читает `runtime: ^X.Y` из манифеста пакета и запускает подходящую установленную версию. Подходящей нет — понятная ошибка с командой локального копирования (`alef runtime install <версия> <путь-к-бинарнику-alef>`); неиспользуемые версии убирает `alef runtime prune`. Автоматический запуск выбранного бинарника остаётся дальнейшим шагом.
- **Запуск:** `alef run <пакет.alef|каталог> -- <аргументы>`; двойной клик по `.alef` (ассоциация типа файла) делает то же. Каталог остаётся для разработки (`dev`).
- **Самообновление runtime:** новая версия ставится рядом со старыми и не ломает установленные приложения; подпись обновления проверяется (ed25519, ключ проекта).
- **Размер:** release-бинарник runtime ~118 МБ (Windows, Servo 0.6): теперь это размер одной установки, а не каждого приложения. Цели: strip символов, LTO в релизе, сжатие в установщике; замер на каждой платформе в CI. Релизный workflow собирает профиль `dist` (наследует `release`: `strip = "symbols"`, `lto = "thin"`; `codegen-units` и `panic` не переопределяются — время на раннере и unwinding). Замер бинарника и архива пишется в job summary и в артефакт `size-<platform>.json`; измеренные числа (dry-run, профиль `dist`, бинарник / архив): windows-x64 126,0 / 47,7 МиБ (zip), linux-x64 130,3 / 50,1 МиБ, macos-arm64 111,7 / 43,3 МиБ, macos-x64 115,6 / 45,7 МиБ (tar.gz).

### Запуск пакета без установки (M7a.1)

**Договор среза, не отчёт о готовом лаунчере.** Шаг 1 вводит в общую схему необязательное строковое поле `runtime` и отдельные помощники строгой проверки SemVer 2.0.0 для пакетов. Разбор диапазона — `semver::VersionReq`, грамматика Cargo: `^`, `~`, пересечения сравнений через запятую, wildcard (`*`, `1.*`, `1.2.*`) и точное `=1.2.3`; не npm-грамматика в целом. Пустая строка, `null`, нестроковые значения, неверный диапазон и `||` отвергаются. Версия приложения из каталога остаётся прежней непустой строкой, без нового требования SemVer. Этот шаг сам по себе **не включает запуск пакетов**: дальше отдельно идут (2) ограниченный неизменяемый снимок архива, (3) архивные ассеты, (4) передача authority в модули, (5) проверенная загрузка и хранилище доверия, (6) подключение CLI и единого запуска, (7) реальные e2e. Ниже — обязательный договор этих будущих шагов.

**Один запуск, два источника.** `alef run <PATH> [параметры лаунчера] [-- аргументы приложения]` и `alef --app <PATH>` — равнозначные записи одного конвейера загрузки → проверки → плана → доверия → прав → runtime. Источник определяется типом объекта ФС: каталог — прежний запуск разработки (включая `--dev-url`, без упаковки, установки и подписанта), обычный файл — кандидат в пакет; остальные типы отвергаются. Расширение `.alef` не требуется; неудачная проверка файла не переключается на загрузку каталога. Для пакета `--dev-url` запрещён. Сохраняются `OsString` аргументы, граница `--`, завершающий deep-link URL и служебный `--launch-mode window`.

**Манифест и совместимость.** Корневой `alef.ktav` читается только из проверенного снимка, декодируется как UTF-8 и разбирается тем же `Manifest::from_ktav_str`; обязательные поля и проверка `id` сохраняются. Строгая SemVer `version` обязательна только для пакета. Без `runtime` используется этот бинарник без обещания совместимости; с диапазоном его должна удовлетворять текущая версия, сообщаемая `app.info.runtimeVersion`. С `runtime`, не удовлетворённым текущему бинарнику, лаунчер один раз перезапускается в наибольшую установленную подходящую версию из хранилища (см. «Как сделано (M7a.4, relaunch на выбранный runtime)»); при отсутствии подходящей диагностика перечисляет установленные версии и предлагает локальную установку; ошибка чтения хранилища сообщается отдельно, не как пустой список. Манифест, ассеты, начальные URL окон и иконка проверяются до любой записи доверия или согласия. Порядок: снимок и полная проверка → манифест и совместимость → ассеты/иконка/план → аргументы приложения → доверие → права → модули/мост → выполнение.

**Ошибки.** В stderr: `alef: <CATEGORY>: <detail>`, с путём пакета и проблемной записью, где доступны. Код **2** — непригодный ввод, проверка пакета, манифест, совместимость, выбранные ассеты и лимиты запуска; **3** — нерешённое/отменённое доверие или согласие на права; **1** — операционная ошибка после проверки ввода, включая I/O хранилища доверия и ошибку runtime; **0** либо запрошенный приложением код — успешное выполнение. Обязательные диагностические сообщения:

```text
NOT_A_PACKAGE: expected a format-1 Alef ZIP package
PACKAGE_FORMAT: <reader detail>
PACKAGE_INTEGRITY: <entry>: CRC-32 mismatch
PACKAGE_INTEGRITY: <entry>: SHA-256 mismatch
PACKAGE_SIGNATURE: strict Ed25519 verification failed
PACKAGE_MANIFEST: missing root alef.ktav
MANIFEST_INVALID: id/version: <reason>
MANIFEST_INVALID: $APP is unavailable for archive applications
RUNTIME_INCOMPATIBLE: requires <range>; this executable provides <version>; installed runtimes: <versions or none>; no installed runtime satisfies <range>; install a matching local binary with alef runtime install <version> <path-to-alef-binary>
PACKAGE_RUN_LIMIT: <limit and entry>
SIGNER_CHANGED: <id> is pinned to <old>; this package uses <new>
SIGNATURE_REQUIRED: <id> was previously accepted with a signing key
NOT_AVAILABLE: native registration requires an installed application
```

`NOT_A_PACKAGE` — только не-ZIP; узнаваемый ZIP, нарушающий строгий профиль, — `PACKAGE_FORMAT`, не неподписанный пакет. Некорректная запись подписи сохраняет отдельную диагностику читателя, без продолжения с предупреждением. Ошибки вложенных записей разбираются структурно (`PackageError::Entry`), не по тексту. Ошибки выбранных ассетов выявляются до построения runtime и получают код 2.

**Доверие: TOFU по точному `id`.** Верная подпись удостоверяет ключ, не реальное имя разработчика. При первом подписанном запуске окно runtime показывает недостоверное отображаемое имя из манифеста, проверенные `id` и версию, **полный** отпечаток подписанта и вопрос «запомнить этот ключ для этого id приложения». Принятие закрепляет ключ только за точным `id`; права решаются независимо, даже если их список пуст. Неинтерактивный эквивалент — `--trust-key <fingerprint>`: ровно 64 hex-символа нижнего регистра, обязательно совпадающие с проверенным подписантом. `--grant` не подтверждает доверие. Совпавший закреплённый ключ переходит к правам; другой — код 3 `SIGNER_CHANGED`, без замены ключа или обхода.

Неподписанный пакет без закреплённого подписанта допускается только после заметного предупреждения runtime **на каждый запуск** либо с `--allow-unsigned`; доверенная личность разработчика не сохраняется. Его отдельная идентичность — SHA-256 точных неизменяемых байт всего архива, изменение содержимого меняет пространство решений. Если за `id` уже закреплён подписант, неподписанный запуск запрещён с кодом 3 `SIGNATURE_REQUIRED`, даже с `--allow-unsigned`. Отдельного режима обхода закрепления здесь нет.

**Хранилище доверия отдельно от прав.** Неизменяемые закрепления: `runtime_home()/trust/<sha256-of-exact-id>.ktav`; запись версии 1 содержит точный `app_id`, открытый ключ и пересчитанный отпечаток (оба по 64 hex-символа нижнего регистра), предел записи 4 КиБ. Отсутствие — первое использование; повреждение, чужой id, неизвестная версия, ссылка/reparse point или ошибка чтения — отказ (fail-closed), не новый вопрос. Каталог закрыт для других пользователей; запись полностью записывается и синхронизируется, затем публикуется атомарно без замены существующего файла; при гонке победившая запись перечитывается и сравнивается. Временные файлы убираются при ошибке, каталог синхронизируется где поддерживается. Только лаунчер пишет закрепления, не bridge приложения. `permissions reset` их не удаляет; повреждённое хранилище прав не служит основанием доверия.

**Публичный id и authority различны.** `AppInfo.id` и текст UI остаются id манифеста. Лаунчер задаёт authority: `Directory`, `SignedPackage { fingerprint }` либо `UnsignedPackage { archive_digest }`; приложение её не выбирает. Для пакетов токен — SHA-256 в hex нижнего регистра над доменно-разделённым кодированием точных полей с префиксом длины каждого: вид, id, отпечаток/дайджест. Не lossy-сокращение имени и не FNV. Каталоги сохраняют legacy-поведение без миграции.

В `Identity` сохраняются прежние JSON-поля, но `signer` пакета — `pkg-signed:<fingerprint>` или `pkg-unsigned:<digest>`, а `Identity::key` для этих префиксов возвращает сильный токен. Он разделяет `ALEF_HOME/consent` и `ALEF_HOME/shadow`; `$APPDATA`, `$APPCONFIG`, `$APPCACHE` пакета — `<существующая база ОС>/alef-packages/<authority-token>`. `store` — `$APPDATA/store`, восстановление окон — `$APPDATA/window-state.ktav`, secrets — `alef/packages/<authority-token>`, single-instance endpoints (включая Windows pipes и запасные Unix sockets) — по токену, не публичному id. Каталоговые ключи согласия и пространства хранения/секретов/instance остаются прежними.

**Как сделано (M7a.1, база данных приложения).** Переменная `ALEF_APP_HOME` переносит базы данных, конфига и кэша приложений обоих источников: каталоговых — `<база>/<id>` (legacy-раскладка), пакетных — `<база>/alef-packages/<authority-token>` (_bases_ в `namespace_paths` строит вызывающий). Значение принимается только заданное, непустое и абсолютное — как `ALEF_HOME` игнорирует относительное; иначе базы — каталоги ОС (`data_local_dir`, `config_dir`, `cache_dir`). Базы — `<ALEF_APP_HOME>/data`, `<ALEF_APP_HOME>/config`, `<ALEF_APP_HOME>/cache`; создаёт их по-прежнему лениво сами модули, не лаунчер. `$DOCUMENTS`, `$DOWNLOADS`, `$DESKTOP`, `$HOME`, `$TEMP` не переносятся — это папки пользователя, не профиль приложения. Области прав `$APPDATA`, `$APPCONFIG`, `$APPCACHE` следуют за базами автоматически: строятся из тех же `PathVars`. Дочерние процессы CLI и повторно запущенный оконный runtime наследуют `ALEF_HOME` и `ALEF_APP_HOME` из окружения родителя. При повторном запуске runtime вычисляет пути заново из унаследованных значений.

**Нативные регистрации.** Для пакета после обычной проверки прав настоящие `app.autostart.enable`, `disable`, `isEnabled`, `app.registerDeepLinks`, `unregisterDeepLinks` возвращают `NOT_AVAILABLE: native registration requires an installed application`. Проверка в обработчике до system и e2e-real backend: нельзя создавать, читать или удалять даже legacy-регистрации каталога с тем же id. Подмена сохраняет прежнее поведение в памяти. Каталоговые регистрации не меняются; проверка и доставка deep-link аргумента при запуске поддерживаются.

**Снимок, проверка, публикация.** Один handle обычного файла читается в собственную память с проверенным пределом и fallible allocation; дальше — `Package::from_bytes`, без повторного открытия пути, изменяемого mmap или внешнего изменяемого буфера. Снимок общий для запросов, не копия на каждый запрос. Замена, усечение или перезапись исходного файла после получения снимка не меняют этот запуск; следующий проверяет всё заново. До разбора манифеста, согласия и выполнения сохраняется полный проход по всем payload-файлам, включая приватные: CRC-32 всегда, SHA-256 при наличии списка хешей; подпись — строгая Ed25519. Чтения снова проверяют CRC и доступный SHA-256. Неподписанный архив без списка имеет только CRC, не аутентичность издателя. Не кэшировать все распакованные данные и не распаковывать архив на диск.

Профиль запуска: **256 МиБ сжатого архива**, **64 МиБ одного публичного ассета**, **1 МиБ манифеста**, **4 МиБ байт иконки**, PNG не больше **1024×1024** (размеры проверяются до выделения памяти изображения). Это не изменение валидности Формата 1: больший корректный пакет получает код 2 `PACKAGE_RUN_LIMIT`. Размер записи проверяется до выделения потребительского буфера (`read_limited`); отсутствующая иконка даёт стандартную, ошибка проверки/лимита не скрывается.

Публичны только точные потомки выбранного `assets` (по умолчанию `dist`), с границей `root + "/"`; корневого fallback нет. Корень должен иметь хотя бы одного потомка, файл `dist`, `Dist/...` или `dist2/...` не подходят; проверяются коллизии регистра неявных каталогов. Общий pathname-парсер и точный регистр сохраняются. Корневые манифест, иконка и `META-INF` приватны; намеренный `dist/alef.ktav` публичен как любой потомок. Entry и начальные URL окон проходят ту же проверку и ограниченное чтение до доверия/прав.

Не больше **четырёх одновременных чтений** ассетов: остальные запросы ждут в ограниченной очереди на 256 мест (ожидающий держит только путь, не данные), запрос сверх очереди — `WouldBlock` / HTTP 429; страница загружает десятки модулей одной пачкой, поэтому отказ пятому запросу ломал бы загрузку. Admission происходит до запуска worker. Permit остаётся у worker до завершения проверки и создания тела ответа, даже при отмене вызывающего; общий mutex сериализует чтение снимка. Нет неограниченной очереди и распакованного кэша; отмена ожидающего возвращает его место. Это предел памяти ассетов в работе на стороне runtime, **не общий предел памяти renderer/JavaScript или процесса**. Полный проход всё ещё подчиняется пределам Формата 1 и может временно держать один приватный файл до 512 МиБ вместе со снимком и метаданными; переносимый wall-clock timeout не обещается.

**Нет каталога приложения у архива.** `$APP` не имеет расширения в путь ФС; точная переменная `$APP` в файловой области пакета — `MANIFEST_INVALID: $APP is unavailable for archive applications`. `$APPDATA`, `$APPCONFIG`, `$APPCACHE` доступны в пространстве authority. Объявления `sidecar:` отвергаются до запуска; динамические sidecar-вызовы — `NOT_AVAILABLE`, даже при `cli.exec: *`. Никакой распаковки или поиска в родителе пакета, CWD и writable cache. Обычные внешние CLI-команды, права и PATH не меняются: заданный CWD — разрешённый реальный каталог, без CWD — рабочий каталог лаунчера. Шаблоны аргументов остаются буквальными, новой интерполяции путей нет. `assets` — корень внутри архива, entry/URL окон — относительно web-root; корневая иконка читается только из проверенного архива. Relaunch и дочерние окна сохраняют аргументы и заново открывают/проверяют пакет.

**Вне пакетного среза M7a.1:** install/uninstall приложения, обновление приложения и runtime, download, ротация или замена ключа, rollback tracking, глобальное доверие разработчику, ассоциации файлов, пакетные нативные регистрации, извлечение sidecar и archive `fs` API. Дальнейшие требования установки, updater и версий рядом ниже/выше — дорожная карта, не возможности M7a.1.

## M7b — пакеты и установка приложений

### Пакет `.alef`

zip: `alef.ktav` в корне, ассеты, `icon.png`, `META-INF/` — список хешей всех файлов и подпись ed25519 разработчика. Ассеты читаются из архива без распаковки на диск (источник ассетов моста — каталог или архив). Подпись проверяется до запуска; неподписанный пакет запускается с предупреждением (политика пользователя). Манифест задаёт `runtime: ^X.Y` — требуемый диапазон версий runtime.

#### Формат 1 (общий договор читателя на Rust и упаковщика на JS)

Оба конца пишутся по этому тексту независимо; расхождение находит перекрёстная проверка на общих векторах: файл `tests/fixtures/package-vectors.txt` (86 архивов, по одному на строку: имя, ожидаемый ответ `signed:<отпечаток>` / `unsigned` / `reject`, архив в hex) собирает `packages/tools/scripts/package-vectors.mjs` по тексту формата, не кодом упаковщика и не кодом читателя; оба читателя обязаны дать ответ каждой строки. Формат узкий намеренно: всё, что два разбора ZIP могли бы понять по-разному, запрещено, а не уточнено.

**Контейнер.** Файл — ровно: записи подряд (local header, затем данные), без промежутков; затем central directory; затем EOCD из 22 байт с комментарием нулевой длины. Ни префикса, ни суффикса, ни промежутков, ни пересечений, ни второго архива; EOCD — последние 22 байта файла, все смещения отсчитываются от начала файла и проверяются с контролем переполнения. Порядок записей в central directory совпадает с порядком local headers. Запрещены: ZIP64, data descriptors, дополнительные поля (extra length равна 0 в обоих заголовках), комментарии записей, шифрование, многотомность, записи-каталоги и любые записи кроме обычных файлов (внешние атрибуты читатель игнорирует и никогда не использует как тип или права). Общие флаги записи равны ровно `0x0800` (UTF-8, бит 11). Методы сжатия 0 (stored) и 8 (deflate); CRC-32 записан и в local header, и в central directory и проверяется; имя (побайтно), требуемая версия, флаги, метод, время и дата DOS, CRC-32, оба размера и длина имени в local header и в central directory совпадают. Единственный источник перечня записей — central directory, и все потребители пакета (лаунчер, runtime, updater, установщик) читают файлы только через один проверенный источник; чтение соседних файлов на диске и второй независимый разбор ZIP запрещены.

**Пределы.** Проверяются по объявленным значениям до выделения памяти и распаковки: файл архива не больше 2304 МиБ, central directory не больше 16 МиБ, записей не больше 10 000, файл не больше 512 МиБ несжатым, сумма несжатых размеров не больше 2 ГиБ, `META-INF/hashes` не больше 16 МиБ, `META-INF/signature` не больше 256 байт. Объявленному размеру не доверяется: распаковка обязана потребить ровно compressed size байт и выдать ровно uncompressed size байт (для stored они равны), чтение останавливается на объявленном размере + 1 байт и это ошибка.

**Имена.** Только ASCII, и только байты `A–Z a–z 0–9 . _ - @ +` и разделитель `/`. Всё остальное — отказ (пробел, не-ASCII, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, `%`, `~`, управляющие символы). Так два разбора не могут разойтись из-за кодировок, нормализации Unicode, регистра за пределами ASCII и псевдонимов Windows; расширение алфавита — задача следующей версии формата, не уточнение этой. Имя не пусто и не начинается с `/`; сегменты не пусты, не равны `.` и `..`, не заканчиваются точкой, не длиннее 255 байт; имя целиком не длиннее 1024 байт; часть сегмента до первой точки не равна (без учёта регистра) `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`. Два имени, равные после приведения ASCII-букв к нижнему регистру, — дубликаты (отказ); имя файла не может быть началом пути (по сегментам) другой записи. Зарезервированные имена `alef.ktav`, `META-INF/hashes`, `META-INF/signature` имеют только это точное написание: запись, равная зарезервированному без учёта регистра, но отличающаяся побайтно, — ошибка; под `META-INF/` (в любом регистре) других записей нет.

**Состав.** Обязателен файл `alef.ktav` в корне. Остальное — файлы пакета (в том числе необязательный корневой `icon.png`); подпись покрывает все они. Публичны только файлы внутри выбранного манифестом подкаталога `assets` (необязательная строка, по умолчанию `dist`). `native://app/x` выбирает ровно `<assets>/x`, без возврата к корню ZIP или приложения. Корневые манифест, иконка и `META-INF` не становятся веб-ресурсами. Всё внутри публичного подкаталога публикуется намеренно; подпись доказывает целостность, не приватность. Это договор публикации runtime, не изменение набора хешируемых файлов и не утверждение о завершённой интеграции ZIP с Servo.

**`META-INF/hashes`.** UTF-8 без BOM, строки заканчиваются `\n` (последняя тоже), не больше 10 000 строк. Строка: 64 hex-символа нижнего регистра SHA-256 содержимого файла, два пробела, имя записи (как в архиве). Строки по возрастанию имён, сравнение лексикографическое по беззнаковым байтам (для ASCII это код символа; при совпадении начала короткое имя идёт первым; сортировка по умолчанию `.sort()` в JS, использующая UTF-16, допустима только потому, что имена ASCII). Каждый файл архива кроме `META-INF/*` ровно в одной строке, лишних строк нет, пустых строк, `\r` и BOM нет.

**`META-INF/signature`.** UTF-8, ровно три строки с `\n` в конце: `alef-package 1`, `key <base64>` (32 байта открытого ключа Ed25519), `sig <base64>` (64 байта подписи). Base64 по RFC 4648 §4: без пробелов и переносов, с обязательным `=`, с нулевыми неиспользуемыми битами; признак — повторное кодирование декодированных байт даёт исходную строку побайтно. Подписывается сообщение `alef-package-v1\n` + точные байты `META-INF/hashes`. Нормативна проверка в runtime (Rust): Ed25519 по RFC 8032 с отказом при S ≥ L и при A или R малого порядка (`verify_strict`); проверка в @alef-runtime/tools — удобство разработчика, её «подпись верна» не означает, что runtime примет пакет, а пакеты, которые собирает сам упаковщик, проходят обе. Отпечаток ключа — SHA-256 открытого ключа, hex нижнего регистра; это идентичность ключа, а не подтверждённое имя разработчика: интерфейс показывает отпечаток и состояние доверия к нему, и не выдаёт имя из манифеста за удостоверенную личность подписанта.

**Проверка при открытии.** (1) контейнер, пределы, имена и состав; (2) есть `signature` — есть и `hashes`, подпись верна; (3) есть `hashes` — набор файлов равен набору списка, хеш каждого файла совпадает (полный проход, до запуска); (4) каждое чтение файла проверяет его хеш по списку ещё раз. Нет `signature` — пакет **не подписан**: результат «не подписан», но если `hashes` есть, он проверяется так же. Любое расхождение — ошибка, а не предупреждение. Результат открытия: `Signed { key, fingerprint }` или `Unsigned`. Таблица записей, список хешей, ключ и результат подписи фиксируются при открытии и на весь сеанс; повторное открытие архива по пути их не заменяет. Чтение возвращает потребителю только полностью проверенные байты: до совпадения CRC-32 и SHA-256 никакие куски не передаются, не выполняются и не разбираются, а проверка и потребление работают над одним и тем же снимком байт в памяти (не над повторным чтением файла и не над изменяемым отображением в память).

**Упаковщик.** Записи расположены по возрастанию имён (то же сравнение), local headers и central directory в одном порядке. Поля фиксированы: версия «создано» `0x031E` (Unix, 3.0), версия «нужно» 20, флаги `0x0800`, время DOS 0 и дата DOS `0x0021` (1980-01-01), внешние атрибуты `0x81A40000` (обычный файл 0644), без дополнительных полей и комментариев. Метод 8 для файла, который он делает меньше, иначе 0; байты deflate зависят от сборки zlib, поэтому тот же вход даёт те же байты на одной версии Node, а подпись покрывает хеши содержимого, не байты архива. Закрытый ключ — только у разработчика (`alef-runtime keys`), в пакет не попадает.

**Требования к установке и обновлению** (не часть читателя; обязательны для M7a и остального M7b).

- Устанавливаемый пакет имеет в проверенном `alef.ktav` `id` и `version` (SemVer 2.0.0); регистрационные данные, диапазон `runtime` и ассоциации берутся только из проверенного манифеста, вложенные архивы — обычные файлы и не распаковываются.
- **Требование к будущему updater, не свойство M7b.6:** установка сохраняет проверенные `id` и 32 байта ключа подписи, а также наибольшую принятую версию. Updater сравнивает кандидата с этой записью, а не с ключом из доставленного пакета или повторно открытого прежнего файла; `updater.publicKey`, если задан, обязан совпадать с ключом установленного пакета.
- **Требование к будущему updater:** обновление допускается только при точном совпадении `id`, том же ключе и версии, большей сохранённой наибольшей (по SemVer, без build metadata); откат — только отдельным явным действием пользователя. Имя приложения не заменяет `id`.
- **Требование к будущему updater:** для ранее подписанного установленного приложения отсутствие подписи — ошибка; запуск такого пакета как неподписанного требует отдельного явного решения пользователя и не наследует доверие, права и идентичность прежней установки.
- Команда запуска, которую строит установщик, — путь и массив аргументов без оболочки; значения манифеста в `.desktop`, XML, plist и скриптах кодируются по правилам формата, а не подставляются как текст команды: подпись не очищает строки.

**Как сделано (M7b.1, Rust).** Крейт `alef-package` владеет источником и узким ZIP-читателем: stored и raw deflate через `flate2` с miniz, проверка CRC-32 и ограничение распаковки объявленным размером + 1 байт. Таблицы записей, хешей и идентичность подписанта фиксируются при открытии; проверяются SHA-256 и строгие подписи Ed25519, повторные чтения возвращают собственные буферы и заново проверяют CRC и хеши. Неподписанный пакет без `META-INF/hashes` проверяется только по CRC, без гарантии SHA-256. **Не сделано:** интеграция с runtime, launcher, updater и install — позже.

**Как сделано (M7a.1, пакет).** `Package::open_snapshot` открывает один дескриптор обычного файла, проверяет потолок сжатых байт и получает собственный буфер архива с выделением памяти, допускающим отказ; до возврата выполняется полная проверка пакета. Последующие изменения файла на диске или замена пути не меняют снимок; получение снимка не гарантирует атомарности при одновременной перезаписи того же размера. `entry_size` ищет точное имя в фиксированной таблице и возвращает объявленный несжатый размер; `read_limited` проверяет лимит вызывающего до чтения, затем полностью проверяет байты, сохраняя прежний `read`. Пределы запуска выбирают вызывающие: например, 256 МиБ сжатого архива, 64 МиБ на ассет, 1 МиБ на манифест и 4 МиБ на иконку — необязательный профиль, не правило Формата 1. Потребителям следует разделять один снимок через mutex, поскольку чтение требует `&mut self`; это API пакета, не утверждение о выполненной интеграции с launcher или runtime.

**Как сделано (M7a.1, архивные ассеты runtime).** Мост принимает каталог или проверенный снимок `Package`, публикует только точных потомков выбранного корня, использует общий pathname-парсер и проверяет entry до регистрации модулей и транспорта. Архивные чтения сериализованы mutex, ограничены 64 МиБ и четырьмя одновременными чтениями; остальные ждут в очереди на 256 мест, сверх очереди — HTTP 429; отмена вызывающего не освобождает permit работающего чтения (найдено e2e пакета: прежний немедленный отказ пятому запросу блокировал модули страницы). Это API runtime и его регрессионные проверки: **лаунчер пока не запускает пакеты**, подключение пакетного запуска, доверия и authority остаётся отдельным шагом.

**Как сделано (M7a.1, загрузка и доверие).** Крейт `alef` как протестированная библиотека: классификация источника по типу ФС (каталог — прежний запуск разработки, обычный файл — пакет, остальное — `NOT_A_PACKAGE`); ограниченный снимок одного файла (256 МиБ архив, 64 МиБ ассет, 1 МиБ манифест, 4 МиБ иконка, PNG не больше 1024×1024 до выделения памяти), полная проверка пакета, манифест только через проверенный снимок, строгая SemVer-версия и требование `runtime` с точным текстом `RUNTIME_INCOMPATIBLE`, отказ `sidecar:` и проверка существования выбранного корня; ошибки типизированы (`alef: <КАТЕГОРИЯ>: <детали>`, коды 2/3/1, `PackageError` разбирается структурно); хранилище доверия fail-closed (`runtime_home()/trust/<sha256-id>.ktav`, 4 КиБ, каталог 0700, запрет ссылок и reparse points, атомарная публикация без замены — hard link на Unix и `MoveFileExW` без флага замены на Windows, временные файлы убираются, гонка перечитывается и сравнивается); решение доверия TOFU (`--trust-key` только равный подписанту, `SIGNER_CHANGED`, `SIGNATURE_REQUIRED` даже с `--allow-unsigned`, `--grant` доверие не одобряет, неподписанный пакет идентичен digest'ом архива и не закрепляется); окно доверия в стиле consent с необязательными полями `trust` в request/answer (прежние запросы и ответы остаются валидными; вопрос доверия без прав работает) и переменная `ALEF_E2E_TRUST` (accept/refuse) только в сборке с фичей `e2e`; план пакета строится тем же конвейером, что и каталога: `AssetInput::Archive`, `PathVars.app: None` (точный отказ `$APP`), identity согласия `pkg-signed:<отпечаток>`/`pkg-unsigned:<digest>`. **Не сделано (следующий шаг):** командная строка (`run`, `trust`, `--trust-key`, `--allow-unsigned`, запрет `--dev-url` для пакетов), подключение в `launch` и e2e реального бинарника.

**Как сделано (M7a.1, команда run).** Обе формы запуска — `run <PATH>` и опция `--app` — это один `Command::Run`: источник классифицируется по типу ФС (каталог — прежний запуск разработки с `--dev-url`, обычный файл — пакет, остальное — `NOT_A_PACKAGE`, суффикс не требуется). Новые опции `--trust-key` и `--allow-unsigned` для каталога и `--dev-url` для пакета — ошибки использования с кодом 2. В `launch` один конвейер: загрузка → проверка → план → доверие (окно доверия или `--trust-key`; отказ → 3, ошибка хранилища → 1) → согласие → runtime. Стабильные отказы пакета печатаются как `alef: <КАТЕГОРИЯ>: <детали>` с кодами 2/3/1. Authority пакета попадает в `ModuleContext`, иконка берётся из проверенного пакета, `AppInfo` хранит id манифеста. Перезапуск окна и window-child повторно открывают и проверяют пакет тем же конвейером через прежние аргументы. `alef permissions list|set|reset` работают с пакетом через тот же проверенный загрузчик и identity (`pkg-signed:`/`pkg-unsigned:`) и никогда не создают и не заменяют pin доверия; субкоманда `alef trust <REQUEST> <ANSWER>` обслуживает окно доверия.

**Как сделано (M7a.1, ранняя проверка документов).** `alef-runtime` даёт публичный `prepare_assets(AssetInput, entry, initial_document_urls) -> PreparedAssets`: источник собирается и аудируется один раз, а входной документ и все начальные оконные документы проверяются тем же `pathname`-lookup'ом, которым мост отвечает на запросы, с теми же видами `io::Error`; `Bridge::with_options` принимает готовый `PreparedAssets` вместо `AssetInput` и больше не проверяет и не пересобирает источник. Лаунчер вызывает `prepare_assets` в новом `application::pipeline::settle_launch` до окна доверия и до вопроса согласия, поэтому пакет с отсутствующим входным документом завершается кодом 2 и категорией `MANIFEST_INVALID` (`alef: MANIFEST_INVALID: assets: …`), не задав пользователю ни одного вопроса. Каталог без `--dev-url` проходит ту же раннюю проверку; с `--dev-url` документы не проверяются, как и раньше (dev-сервер отдаёт их сам). Списки мутаций этого шага — `run.json` и `preflight.json` в `scripts/quality/mutations/` — прогоняются рабочим процессом `Mutation`.

**Как сделано (M7a.3, хранилище версий runtime).** Локальный модуль хранит версии в `runtime_home()/runtimes/<MAJOR.MINOR.PATCH>/<binary>` (`alef.exe` на Windows, `alef` на Unix); абсолютный `ALEF_HOME` переопределяет `runtime_home()`, иначе используется прежний пользовательский каталог данных. Имена версий — строго три числовых компонента, без prerelease/build и ведущих нулей. Корень и каталог версии не могут быть ссылкой или Windows reparse point; установленной считается версия с обычным бинарником, тоже без ссылок/reparse. `alef runtime list` перечисляет версии по числовому SemVer, от старых к новым, печатает путь и отмечает текущую версию ` *`. `select` выбирает наибольшую подходящую установленную версию тем же общим `runtime_requirement_met` и парсером диапазонов, что проверяет манифест; версии публичного API остаются строками, отдельной зависимости semver у лаунчера нет.

`alef runtime install <VERSION> <SOURCE_BINARY>` только копирует предоставленный локальный обычный файл, ничего не скачивает. Временный файл `.tmp-<pid>-<counter>` создаётся эксклюзивно в корне хранилища с повтором при коллизии; байты копируются, выполняется `flush`, на Unix права бинарника ставятся 0755 до `sync_all`, корня и каталога версии — 0700. Публикация без замены: hard link на Unix, `MoveFileExW` с flags 0 на Windows; каталог на Unix синхронизируется best-effort. При обычном отказе убирается только собственный временный файл и собственный пустой каталог версии; чужой файл или каталог не удаляется. При гонке двух успешных источников за одну новую версию ровно один установщик побеждает, другой получает `ALREADY_INSTALLED`, включая ещё незавершённый каталог победителя.

`alef runtime prune [--keep <VERSION>]... [--dry-run]` всегда сохраняет текущую `CARGO_PKG_VERSION` и явно перечисленные версии. Dry run печатает `would-remove`, не удаляя; реальный запуск — `removed`, небезопасное дерево — `skipped` с причиной. Неизвестные имена, файлы вместо каталогов и каталоги без обычного бинарника не трогаются; ссылки/reparse в дереве запрещают удаление, глубина обхода ограничена 64. При несовместимом текущем бинарнике категория `RUNTIME_INCOMPATIBLE` и код 2 сохраняются: отсутствие подходящих версий даёт упорядоченный список и команду установки, наличие — relaunch в выбранный бинарник (M7a.4), нечитаемое хранилище — отдельную причину без ложного утверждения об отсутствии версий.

| Категория хранилища runtime | Код выхода | Причина |
|---|---|---|
| `INVALID_ARGUMENT` | 2 | Неверные аргументы, версия или исходный файл |
| `ALREADY_INSTALLED` | 2 | Версия уже установлена или её каталог занят установкой |
| `RUNTIME_STORE` | 1 | Операционная ошибка хранилища |

Этот срез доверяет предоставленному бинарнику и метке версии: встроенную версию и происхождение файла не удостоверяет. Безопасность путей предполагает стабильное дерево под контролем владельца, не защищает от враждебной одновременной подмены тем же владельцем; восстановление после падения/отключения питания не обещается. **Не сделано:** download/network, updater, системный installer, проверка update-signature. Добавлены регрессионные тесты; результаты CI здесь не утверждаются.

**Как сделано (M7a.4, relaunch на выбранный runtime).** Когда требование `runtime` не удовлетворено работающему бинарнику и `runtimes::select` находит подходящую установленную версию с обычным файлом-бинарником, лаунчер запускает ИМЕННО этот бинарник с теми же аргументами (точный argv после имени программы) и тем же окружением, наследует стандартные потоки и завершается с кодом выхода потомка. Оба родителя завершаются только после потомка: на Unix лаунчер запускает потомка в отдельной группе процессов и пересылает ему INT/TERM/HUP, а платформенные механизмы (PDEATHSIG/watchdog на Linux/macOS) убивают его при смерти родителя; на Windows — spawn, ожидание и пересылка кода, консольные события наследуются, а job-объект механизма relaunch не оставляет сирот. Замена процесса через exec не используется: пересылка сигналов и защита от сирот требуют живого родителя. Защита от цикла: потомок получает `ALEF_RELAUNCHED=1` (глубина максимум 1); потомок с маркером, всё ещё не удовлетворяющий требованию, завершается прежней `RUNTIME_INCOMPATIBLE` (код 2), без второго шага. Значение без числа или нечисловое трактуется как максимальная глубина (fail-closed). `ALEF_RELAUNCHED` и `ALEF_RELAUNCHED_FROM` снимаются из окружения процесса на старте до появления потоков, поэтому собственные дочерние процессы приложений их не наследуют — так же, как `ALEF_HOME`/`ALEF_APP_HOME` остаются внутренними переменными лаунчера. Выбранный бинарник — только тот, что вернул `select` (наибольшая подходящая), никогда путь из пакета или окружения; перед запуском повторно проверяется обычный файл (не ссылка/reparse) и что это не сам работающий бинарник. Ничья не удовлетворяет — прежняя диагностика и код 2; ошибка чтения хранилища — отдельная причина; незапустившийся бинарник — `RUNTIME_RELAUNCH_FAILED: <причина>`, код 1 (та же таблица категорий ошибок запуска). Строка «relaunch не реализован» исчезла; успешный relaunch сам ничего не печатает (печатает потомок); переключателя подробности в лаунчере нет, поэтому строки о версии и пути при relaunch нет. `alef runtime list`, `install`, `prune` не изменились; `prune` по-прежнему хранит текущую `CARGO_PKG_VERSION`, а версия родителя в `ALEF_RELAUNCHED_FROM` — только для диагностики и никогда не доверяется (prune её не читает). Согласие, доверие и ключи данных не зависят от версии бинарника: identity согласия строится из id манифеста и подписанта/дайджеста пакета, закрепления доверия лежат по sha256 точного id, а папки данных — по authority-токену; всё это вычисляется из пакета и окружения одинаково в обоих процессах, поэтому приложение после relaunch сохраняет доверие, решения о правах и папки данных (проверено чтением кода, без изменений). Каталоговые приложения (`--app`) впервые проверяют `runtime` манифеста тем же общим `runtime_requirement_met`, сразу после чтения `alef.ktav` и до плана/доверия/прав. **Не сделано:** download/network, updater, системный installer, проверка подписи обновлений; relaunch работает только с уже установленными локально версиями.

**Как сделано (M7d.6, установщики runtime и ассоциация .alef).** Генератор `scripts/release/installer.mjs` — чистый node без новых зависимостей, детерминированный (два прогона дают равные байты), переиспользует помощники `bundle-formats.mjs` (tar/ar/gzip, deb control, NSIS/desktop/plist-экранирование); юнит-тесты `scripts/release/tests/installer.test.mjs` (15): враждебные строки версии отвергаются (строгий semver — три числовых компонента без prerelease/build, ведущих нулей и завершающего перевода строки), deb читается обратно (ar-члены, control, postinst/prerm/postrm, mime XML, desktop MimeType/Exec), plist-UTI, детерминизм байтов, CLI-смоук; настоящий makensis компилирует сгенерированный скрипт на Linux и Windows в CI (тест `makensis_compiles_the_win32_runtime_installer_without_warnings`, включается `ALEF_TEST_MAKENSIS=1`), сам установщик не запускается. Windows (win32-x64): per-user NSIS-сценарий (`RequestExecutionLevel user`, только HKCU); бинарник ставится как `%LOCALAPPDATA%\alef\runtimes\<версия>\alef.exe` — это реальный корень хранилища версий (`runtimes/store.rs`: `data_local_dir()/alef/runtimes/<v>/alef.exe`), поэтому установленные версии сразу видны `alef runtime list`/select/prune; путь `$LOCALAPPDATA\Programs\Alef` из раннего плана не использован именно потому, что расходился с хранилищем; версионно-независимый шим `%LOCALAPPDATA%\alef\bin\alef.cmd` выбирает наибольшую установленную версию при запуске, запись в HKCU `Environment\Path` добавляется при отсутствии с broadcast WM_SETTINGCHANGE; ассоциация: HKCU `Software\Classes\.alef` → ProgId `Alef.Package`, `shell\open\command` = `"<шим>" run "%1"`, DefaultIcon; запись «Установка и удаление программ» на каждую версию (`AlefRuntime-<версия>`); деинсталлятор перечисляет каталог версий через FindFirst/FindNext с пропуском `.`/`..`, удаляет только свою версию и её запись ARP, а шим, запись PATH и ассоциацию снимает только когда это была последняя версия (пустой каталог `runtimes`). Linux (linux-x64): ДВА deb-пакета от одного генератора — версионный `alef-runtime-<версия>_amd64.deb` ставит только `/opt/alef-runtime/<версия>/alef` с `Depends: alef-runtime-common (= <версия>)` и регистрирует `/usr/bin/alef` через update-alternatives в postinst/prerm с приоритетом, монотонным по semver; общий `alef-runtime-common_<версия>_amd64.deb` (та же версия runtime) владеет mime XML `application/x-alef-package` (`.alef`) и `.desktop`-файлом, postinst/postrm обновляют mime- и desktop-базы, когда утилиты есть, без Depends/Replaces/Breaks; версионные пакеты с разными версиями действительно стоят рядом (разные имена пакетов), `/usr/bin/alef` указывает на выбранный alternatives вариант; версии из deb не попадают в пользовательское хранилище — добавить конкретную версию можно `alef runtime install <версия> /opt/alef-runtime/<версия>/alef`. macOS (darwin-arm64 / darwin-x64): `.pkg` собирается только утилитами Apple — `build-pkg.sh` выполняется на macOS-раннере и собирает настоящий applet `Alef.app` через `osacompile` из AppleScript-исходника (`on open theFiles` → `do shell script` с `quoted form of` для каждого файла — shell-скрипт событий document-open от Finder не получает), добавляет через PlistBuddy UTI `org.alef.package` (conforms to `public.data`, расширение `alef`) и CFBundleDocumentTypes, затем pkgbuild/productbuild дают настоящий `alef-runtime-<v>.pkg`; ставится `/Library/Alef/runtime/<версия>/alef`, postinstall создаёт симлинк `/usr/local/bin/alef` на установленную версию; хранилище runtime — пользовательское, поэтому для выбора версий лаунчером нужно явно `alef runtime install <версия> /Library/Alef/runtime/<версия>/alef`; автоматической интеграции с пользовательским хранилищем pkg не делает; без подписи и нотаризации (этот срез). Двойной клик по `.alef` на Windows/Linux/macOS открывает пакет через лаунчер `alef run`. В release.yml шаг генерации установщика после замера размеров передаёт генератору точное платформенное имя (win32-x64 / darwin-arm64 / darwin-x64 / linux-x64) и загрузка вместе с архивами кладёт в артефакт установщики, deb-пакеты (обоих), .pkg и Windows staging (включая bin/alef.exe и bin/alef.cmd, на которые ссылается .nsi), чтобы артефакт компилировался как есть; тест генератора добавлен в unit-прогон джобы plan. Не сделано: подпись и нотаризация установщиков (Authenticode/Developer ID), MSI/WiX, AppImage, dmg, самообновление runtime, автоматическая конвертация deb/pkg-версий в пользовательское хранилище; приёмочная строка «Установщик runtime ставит, запускает, удаляет; версии рядом не мешают друг другу» остаётся ручной (на трёх ОС).
**Как сделано (M7a.1, e2e пакета).** Сценарий `package` в `tests/e2e/scenarios/app/package.mjs` (зарегистрирован в `tests/e2e/run.mjs`) гоняет настоящий бинарник `alef` (сборка с фичей `e2e`) на настоящих пакетах, собранных API `@alef-runtime/tools` (`createKey`, `pack`), с ключами и `ALEF_HOME` внутри своей временной папки; на Linux общие базы `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME` тоже уводятся туда, поэтому на платформе, где сценарий выполняется в CI, за пределы папки прогона ничего не остаётся, на других платформах сообщённые приложением папки данных удаляются в `finally`. Положительные случаи: первый подписанный запуск с `--trust-key`, страница из архива отвечает и выходит с затребованным кодом; второй запуск обходится без вопроса доверия и читает записанное первым; ровно один pin в `runtime_home()/trust/<sha256-id>.ktav`; вариант `--app`; неподписанный пакет с `--allow-unsigned` без pin. Отрицательные случаи проверяют точную категорию и код и отсутствие `ALEF_READY`: `NOT_A_PACKAGE`, `PACKAGE_INTEGRITY` (битый байт при починенных CRC), `PACKAGE_SIGNATURE` (список хешей переписан без переподписи — архив правится с заменой deflate-потока той же длины), `MANIFEST_INVALID` без `id` и без выбранного корня ассетов, `RUNTIME_INCOMPATIBLE`, `TRUST_REFUSED`, `SIGNER_CHANGED`, `SIGNATURE_REQUIRED`, неверный `--trust-key` как `INVALID_ARGUMENT`. Изоляция на диске: два подписанта одного id (разные домашние папки, общая база данных ОС) получают разные токены `alef-packages/<token>` для данных и кэша, разные файлы согласия и разные папки shadow (materialised substituted `fs.write`); при живом первом подписанте второй доходит до `ALEF_READY` — endpoint на токен, не на id; секрет первого подписанта второму не виден (в пределах одного процесса; межпроцессная сохранность системного хранилища секретов e2e не утверждает — там, где хранилище не переживает процессы, сценарий печатает SKIP, а исчезновение пробы при уцелевшей канарке считается подозрением на продукт и падает); запуск того же id из каталога остаётся в прежнем месте `<база>/<id>`. Учётные данные, созданные пробой секретов, удаляет само приложение.

### Установка

`alef install <пакет.alef>` устанавливает проверенный пакет в пользовательское хранилище и публикует артефакт запуска. Установка не требует отдельного обещания согласия при первом запуске; запуск и доверие следуют общему конвейеру выше.

- Windows: ярлык с AppUserModelID; регистрация `HKCU\\Software\\Classes\\AppUserModelId` задаёт id, `DisplayName` и `IconUri`.
- macOS: тонкая `.app`-обёртка с PNG-значком; это не `.icns`, без TCC-описаний и без codesign.
- Linux: `.desktop` без `MimeType`.

**Как сделано (M7b.6, install / uninstall / apps).** Команды: `alef install <PATH.alef> [--trust-key <KEY>] [--allow-unsigned]`, `alef uninstall ID --purge-data` и `alef apps --json`. Установка использует тот же проверенный snapshot и plan документов, что и запуск; коды доверия — 2/3/1. Пакет копируется, не перемещается, в `<ALEF_HOME>/apps/<sha256-id>/<version>.alef`; значок извлекается отдельно. `app.ktav` читается строго, ограничен 16 КиБ и допускает ровно поля `id`, `name`, `version`, `icon`, `package`, `executable` (диагностические сведения) и `installed_time` (Unix epoch seconds). `ALEF_HOME` остаётся прежним production override; `ALEF_APPLICATIONS_DIR` используется только в тестах/e2e, исключён из release.

Повтор идентичной установки успешен («already installed»), отличающиеся байты дают `ALREADY_INSTALLED`, понижение версии — `DOWNGRADE`. Для подписанного приложения проверяется pin ключа; более старая версия удаляется только после публикации нового артефакта и записи. Установка и удаление сериализуются стабильным root gate и `.lock`; ожидание ограничено 2 секундами, занятость даёт `BUSY`. Публикация идёт через временный файл с fsync и без перезаписи; ссылки и reparse points отклоняются. Гарантии предполагают стабильное дерево под контролем владельца; восстановление после аварийного падения не обещается.

Иконка извлекается из пакета. Linux публикует `alef-<hash>.desktop` без `MimeType`; macOS и Windows используют экранированное имя и полный hash для `.app`/`.lnk`, предотвращая коллизии. macOS-обёртка содержит XML plist, launcher с правами 755 и PNG, не `.icns`. Windows регистрирует `HKCU\Software\Classes\AppUserModelId` с `id`, `DisplayName` и `IconUri`; PowerShell получает только константные значения окружения и ограничен 10 секундами. Записи реестра пропускаются во всех test/e2e builds; тесты реального реестра не выполняются, unit-тесты используют заглушки. Production-проверка — ручная.

Публикация integration artifact выполняется через same-volume stage и скрытые backup-пути: при отказе publication восстанавливаются предыдущие артефакты, а stage удаляется; после commit ошибки очистки backup только выводятся как предупреждение и не отменяют успешную установку. Native-тесты macOS проверяют замену `.app`, launcher/plist/icon и rollback-публикацию; покрытие платформы и фактический результат CI здесь не утверждаются.

**Как сделано (M7d.1, alef run <id>).** `alef run <ARG> [-- аргументы]`: если ARG — существующий объект ФС, это путь, и запуск идёт ровно как раньше (путь всегда выигрывает, включая существующий файл с именем, похожим на id). Иначе, если ARG — валидный id манифеста (та же грамматика, что у `alef install`/`alef uninstall`), лаунчер читает запись `<ALEF_HOME>/apps/<sha256(id)>/app.ktav` существующим строгим читателем (тот же корень хранилища, что у `alef apps`), проверяет, что названный пакет — обычный файл внутри каталога приложения (без ссылок и reparse points, без `..`, имя файла равно `<version>.alef` записи), и запускает его через ТОТ ЖЕ конвейер, что `alef run <этот файл>`: то же согласие, тот же relaunch, тот же контекст updater (`installed` вычисляется из пути запущенного пакета так же, как при запуске по ярлыку). Доверие — по общему правилу запуска пакета (артефакты установки запускают `alef run <путь>`): подписанный пакет открывается по закреплённому при установке ключу без нового вопроса; неподписанный — по обычному правилу неподписанного пакета (`--allow-unsigned` или явное принятие при запуске), без специального исключения. `--app` разрешение id не применяет: `alef --app <id>` при отсутствии локального объекта даёт прежнюю ошибку `NOT_A_PACKAGE`, код 2. Гонка с одновременным `alef install`: попытка — это снимок записи, разрешение пути по ней и открытие пакета; если за время попытки запись изменилась или исчезла, попытка повторяется с новой записью (не более трёх), иначе возвращается ошибка самой попытки; публикация атомарна, полузаписанный пакет появиться не может. Повреждённое хранилище — корень `apps` или каталог приложения является ссылкой, reparse point или не каталог — даёт `APP_STORE`, код 1, а не `NOT_INSTALLED`. Имена внутренних подкоманд после `run` (`trust`, `consent`) — обычные цели и могут быть id установленных приложений. Аргумент, который не путь и не валидный id, даёт прежнюю ошибку отсутствующего источника (`NOT_A_PACKAGE`, код 2); валидный id не установлен — `alef: NOT_INSTALLED: <id>`, код 1 (категория `alef uninstall`); повреждённая запись — ясная ошибка `APP_RECORD`/`APP_STORE`, код 1, хранилище не изменяется. Чтение записи не берёт блокировку и не мешает concurrent `alef install`: публикация в хранилище атомарна (временный файл без перезаписи плюс rename/link), поэтому запуск никогда не видит полузаписанный пакет; если обновление идёт одновременно с запуском, работает старая или новая версия, а если запись меняется во всех трёх попытках, возвращается ошибка последней. `--app` и каталоговые источники не изменились; артефакты идентичности установки по-прежнему указывают на путь пакета. Справка `--help` упоминает форму id. В сборках с фичей `e2e` при `ALEF_E2E=1` и `ALEF_E2E_RUN_TARGET=1` лаунчер печатает разрешённый путь запуска и завершается без старта приложения — только для тестов. Разрешение покрыто unit-тестами (`runtimes/install/tests/run_id.rs`: установка, `NOT_INSTALLED`, повреждённая запись, файл вне каталога, несовпадающая версия, ссылка на Unix, существующий файл-победитель, форма `--app` без разрешения, id-имена подкоманд, перечитывание записи при обновлении, граница повторов, ссылки корня и каталога хранилища, контекст updater) и шагами e2e `tests/app_install.rs` (запуск по id даёт точный путь пакета, существующий путь выигрывает, неизвестный id — `NOT_INSTALLED`, код 1, `--app <id>` — прежняя `NOT_A_PACKAGE`, код 2). Результаты CI здесь не утверждаются.

Удаление без флага `--purge-data` удаляет артефакты приложения до удаления пакета, сохраняя consent, pin и пользовательские данные. Флаг `--purge-data` перед удалением печатает точные пути для authority, затем удаляет consent, shadow data, config, cache и pin; legacy-данные не затрагиваются. Очистка половинной установки успешна, если артефакты или пакет уже отсутствуют; неизвестное приложение возвращает `NOT_INSTALLED` и код выхода 1. `alef apps` выводит отсортированный текст с id, version и name; повреждённый hash помечается `DAMAGED` при коде выхода 0, а `--json` выводит массив. Зелёный CI не утверждается.


Ассоциации файлов, deep links и автозапуск не регистрируются; автоматического удаления нет. Применение обновлений сделано в M7b.7 ниже; прочее вне среза M7c.

**Как сделано (M7b.7, updater.install).** Контракт: JS `updater.install(): Promise<never>` — обещание не выполняется никогда: при успехе процесс заменяется, при отказе — AlefError; нативная команда `updater.install` без аргументов реализована рядом с check/download в `backend/crates/alef-modules/src/net/updater/`. Нового права нет — те же требования, что у updater.download (endpoint из конфигурации, объявленный в permissions.net.http). Правило установленности: обновление применяет только приложение, запущенное ИЗ хранилища `alef install` — путь работающего пакета равен `<ALEF_HOME>/apps/<sha256(id)>/<version>.alef`; лаунчер вычисляет это при открытии пакета и передаёт в контекст updater (`installed`), alef-modules не зависит от крейта alef. Запуск `alef run <файл>` вне хранилища или каталоговое приложение — `UPDATE_NOT_INSTALLED`: у `updater.install` нет ответа `NOT_AVAILABLE`, команда требует установленное приложение в любом запуске. Порядок шагов (каждый отказ до замены процесса оставляет старую версию полностью работоспособной): предложение + скачанный файл из `updates/<version>.alef` (нет — `UPDATE_NOT_DOWNLOADED`); блокировка обновления (`Storage::prepare`) и повторная проверка файла с диска ровно как при download (подпись, доверенный ключ, id, версия равна предложению и строго выше работающей, лимит размера); затем applier — callback/типаж `UpdateApplier`, реализованный в alef поверх той же транзакционной установки `alef install` с теми же правилами доверия: подписант обязан совпасть с закреплённым ключом, новый вопрос о доверии не задаётся никогда, иной подписант — `UPDATE_KEY_MISMATCH` и ничего не меняется; публикация `<apps>/<hash>/<новая версия>.alef`, замена записей и артефактов идентичности, откат при сбое, удаление старой версии только после успеха. Новые права обновлённого пакета спрашиваются заново существующим потоком согласия при его первом запуске (M2b) — обхода нет. Параллельные вызовы и конкурентность: один семафор на check/download/install, второй вызов — `UPDATE_BUSY`; блокировка обновления и повторная проверка не доверяют файлу, лежавшему на диске. Перезапуск: новый процесс `<текущий исполняемый файл alef> run <новый путь пакета>` запускается оторванно от старого (своя процесс-группа на Unix; breakaway из job-объекта на Windows, причём отказ breakaway — это ошибка `UPDATE_RELAUNCH_FAILED`, а не беззвучный откат: дочерний процесс, оставшийся в kill-on-close job, умер бы вместе со старым); затем работающему приложению даётся тот же раунд `before-quit`, что и `app.exit`/`app.quit` (`Termination::request`), и процесс завершается; обещание JS при этом не выполняется никогда. Решение по single-instance: старый процесс передаёт новому переменную `ALEF_UPDATE_REPLACES_PID` со своим pid; новый процесс снимает переменную до любых потоков (дети приложений её не наследуют) и до поднятия интерфейса ждёт выхода предшественника ограниченно (15 с, опрос 25 мс), так что `app.requestSingleInstance` нового процесса никогда не видит живой endpoint старой версии; таймаут ожидания — диагностический `UPDATE_RELAUNCH_FAILED` с кодом выхода 1; новая версия перед отчётом вызывает `app.requestSingleInstance` и обязана получить `true`, что подтверждает передачу single-instance в e2e. Вето на `before-quit` после успешной установки — `UPDATE_RELAUNCH_FAILED`: запущенный новый процесс при этом продолжает жить и завершается по таймауту ожидания; старая версия работает дальше, файлы новой сохранены. Ошибки очистки прежних пакетов после записи новой версии не отменяют установку (предупреждение в stderr, как в транзакции integration-артефактов), `updater.check` и `updater.download` без контекста updater отвечают `NOT_AVAILABLE`, а `updater.install` — `UPDATE_NOT_INSTALLED`. Отказ запустить новый процесс после успешной установки — самый неприятный случай: файлы новой версии сохраняются (следующий ручной запуск получит новую версию), старый процесс продолжает работать, возвращается `UPDATE_RELAUNCH_FAILED`. Коды ошибок: `UPDATE_NOT_INSTALLED`, `UPDATE_NOT_DOWNLOADED`, `UPDATE_BAD_DOCUMENT`, `UPDATE_SIGNATURE_INVALID`, `UPDATE_KEY_MISMATCH`, `UPDATE_BUSY`, `UPDATE_IO`, `UPDATE_RELAUNCH_FAILED`. НЕ сделано: откат на предыдущую версию после неудачного обновления, delta-пакеты, каналы, расписание обновлений, переключение runtime, системные установщики.

**Как сделано (M7d.2, updater и версия runtime).** Контракт: feed может нести необязательное поле `runtime` — диапазон `semver::VersionReq` в той же грамматике, что и поле `runtime` манифеста; валидируется тем же парсером (`deserialize_runtime` alef-core), невалидный диапазон — `UPDATE_BAD_DOCUMENT`. `updater.check()` при доступном обновлении возвращает `runtime?: { range, satisfied }`: `satisfied` истинно, когда диапазону удовлетворяет работающий runtime ИЛИ одна из установленных версий; лаунчер вычисляет список установленных версий (`runtimes::store::installed`, ошибка чтения — пустой список) и передаёт его в `UpdaterContext` как данные вместе с версией работающего runtime — alef-modules не зависит от крейта alef. Нет поля `runtime` в feed — поле отсутствует в ответе. `updater.download()`: манифест скачанного пакета авторитетен — если feed объявил диапазон и он отличается от диапазона манифеста (feed соврал), загрузка отклоняется с `UPDATE_BAD_DOCUMENT` и ничего не публикуется; проверка встроена в ту же повторную верификацию пакета, поэтому и `install` отвергает расхождение так же. `updater.install()`: перед вызовом applier, если диапазон манифеста не удовлетворён ни работающим runtime, ни установленными версиями — новый код `UPDATE_RUNTIME_REQUIRED` (HTTP 400), сообщение называет диапазон и команду `alef runtime install <version> <path-to-alef-binary>`; ничего не меняется на диске и applier не вызывается. Если диапазон удовлетворён только другой установленной версией, установка продолжается: перезапуск идёт обычным путём (`<текущий исполняемый файл> run <новый пакет>`), новый процесс входит в штатный конвейер запуска, где требование `runtime` манифеста не удовлетворяется его версии, и срабатывает существующий relaunch (M7a.4): `relaunch::runtime::attempt` выбирает через `runtimes::store::select` наибольшую установленную подходящую версию и запускает именно её (один прыжок, маркер `ALEF_RELAUNCHED` ограничивает глубину) — проверено чтением кода, без изменений в relaunch. Коды ошибок M7b.7 дополнены `UPDATE_RUNTIME_REQUIRED`. НЕ сделано: автоматическая установка требуемого runtime из updater, предложение обновления runtime в интерфейсе приложения, переключение каналов.

JS-профиль ZIP строгий: только ASCII-имена, файлы без записей-каталогов, flags `0x0800`, без extras, комментариев, descriptors, ZIP64 и многотомности; дубликаты и конфликты префиксов выявляются до чтения ключа и содержимого. Сжатие автоматически выбирается только при выигрыше размера; детерминизм ограничен одинаковыми входными байтами, ключом, параметрами и версией Node. Оптимизация тестов заменяет массовое создание файлов метаданными-моками для снижения дискового I/O; таймауты не увеличены, `test:tools` использует обычную конкурентность runner и изолированные временные каталоги. ### `updater`

```ts
updater.check(): Promise<{ available: boolean, version?, notes?, runtime?: { range, satisfied } }>
updater.download({ onProgress? }): Promise<void>
updater.install(): Promise<never>    // установливает скачанный обновлённый пакет в хранилище и перезапускает приложение в новую версию
```

- Манифест: `updater: { endpoint: https://..., publicKey: <ed25519> }`; обновляется **пакет** `.alef` (подпись ключом разработчика проверяется до установки; ключ должен совпасть с прежним, иначе — отказ (`UPDATE_KEY_MISMATCH`); новый вопрос о доверии не задаётся никогда). Новые права в обновлении спрашиваются заново (M2b).
- Обновление требуемой версии runtime сделано (M7d.2 выше): feed может объявить диапазон `runtime`; updater сообщает его и удовлетворённость, а установка без подходящего runtime отклоняется.

### Как сделано (M7b.5, updater: check и download)

**Фактический срез.** Нативные команды `updater.check`, `updater.download`, `updater.close` реализованы в `backend/crates/alef-modules/src/net/updater/`; JS-обёртка — `packages/api/src/net/updater.ts`. Это получение и проверка пакета, не его установка.

**Доступность и baseline.** Контекст updater создаётся только для уже запущенного подписанного пакета с валидной конфигурацией updater и доступным каталогом данных; без контекста команда отвечает `NOT_AVAILABLE`. Сравнение предложения ведётся с версией этого работающего приложения (`config.version`), а не с самой высокой когда-либо установленной/скачанной версией. Более новая сохранённая проверенная версия не понижает baseline, но может привести к `UPDATE_NOT_AVAILABLE` при публикации старой. Конфиг/каталог отсутствуют — updater недоступен, неподписанный запуск не получает его.

**Feed.** GET без перехода по редиректам, успех HTTP обязателен; body ограничен 64 КиБ, срок — 30 с. Строгий JSON без неизвестных полей: `version` (валидная сравнимая SemVer), необязательный `notes` только строка (не `null`), `package`, `sha256` — ровно 64 строчных hex-символа. `package` разрешается относительно endpoint и обязан быть того же origin. Поле `signature` не поддерживается и отвергается как неизвестное: подлинность package обеспечивает внутренняя подпись формата `.alef`, а не подпись feed. Версия не выше running baseline даёт `available:false`.

**Download и публикация.** Загружается только предложенный пакет, максимум 512 МиБ, deadline 600 с; проверяются объявленный SHA-256, корректность внутренней подписи, совпадение ключа с доверенным ключом запущенного пакета, `app_id` и версия с feed. Хранилище — приватный `<ALEF_APP_HOME>/data/alef-packages/<authority-token>/updates` (фактический каталог `data` контекста); каталог проверяется на ссылки/reparse points, Windows ACL/Unix-права задаются при создании. Один стабильный `.alef-update.lock` удерживается на время операции; временный файл создаётся в том же каталоге, публикация — `persist_noclobber` в `<version>.alef`, так что существующий файл не перезаписывается. Верификация выполняется blocking worker с сигналом отмены; удаление временного файла делегировано RAII `NamedTempFile`. После публикации более старые проверенные пакеты удаляются; при ошибке updater пытается удалить новый файл и возвращает UPDATE_IO. Отмена после публикации может оставить уже проверенный файл.

**Границы и гарантии.** Установка, перезапуск, переключение runtime, rollback, delta-пакеты, каналы и расписание не входят в этот срез; установка и перезапуск сделаны в M7b.7 выше. Это не заявление о полном закрытии updater: каталоговые приложения не получают updater (`NOT_AVAILABLE` для check и download; `updater.install` отвечает им `UPDATE_NOT_INSTALLED`), применение скачанного пакета сделано в M7b.7 выше. Наличие локальных тестов в исходниках не является утверждением, что тесты или CI сейчас зелёные.

### Права updater и коды ошибок

Нового права updater нет. Конфигурация `updater` в манифесте требует endpoint, уже объявленный в `permissions.net.http`; штатное согласие на сетевые права не меняется. Нативный updater обращается только к фиксированному endpoint из этой конфигурации и не принимает произвольный URL от страницы.

| Код | Значение в updater |
|---|---|
| `NOT_AVAILABLE` | updater отсутствует для текущего запуска/конфигурации |
| `UPDATE_NOT_AVAILABLE` | нет предложения к download или уже сохранена более новая версия |
| `UPDATE_BAD_DOCUMENT` | feed, URL, версия, манифест или предложение некорректны |
| `UPDATE_TOO_LARGE` | feed больше 64 КиБ или package больше 512 МиБ |
| `UPDATE_HASH_MISMATCH` | SHA-256 package не совпал с feed |
| `UPDATE_SIGNATURE_INVALID` | пакет unsigned или внутренняя проверка подписи не прошла |
| `UPDATE_ID_MISMATCH` | `app_id` пакета не совпал с работающим приложением |
| `UPDATE_KEY_MISMATCH` | configured/trusted key или ключ подписанта пакета не совпал |
| `UPDATE_ALREADY_DOWNLOADED` | целевой файл версии уже существует (noclobber) |
| `UPDATE_NETWORK` | запрос/ответ/тело HTTP завершились ошибкой |
| `UPDATE_TIMEOUT` | истёк deadline check (30 с) или download (600 с) |
| `UPDATE_BUSY` | параллельная операция или занята межпроцессная блокировка |
| `UPDATE_IO` | ошибка безопасного хранилища/файловой операции |
| `UPDATE_NOT_INSTALLED` | приложение запущено не из хранилища установленных приложений (`alef install`), обновление невозможно |
| `UPDATE_NOT_DOWNLOADED` | предложенного и скачанного обновления нет |
| `UPDATE_RUNTIME_REQUIRED` | манифест скачанного пакета требует диапазон `runtime`, не удовлетворённый ни работающим runtime, ни установленными версиями; установка не выполняется |
| `UPDATE_RELAUNCH_FAILED` | установка прошла, но запуск новой версии или завершение старой не удались; старая версия продолжает работать, файлы новой версии сохранены |

## M7c — единая сборка (опция)

`alef-runtime bundle` кладёт runtime рядом с пакетом и собирает обычный установщик: Windows — NSIS или MSI (WiX), подпись signtool; macOS — `.app` (Info.plist, TCC), `.dmg`, codesign + нотаризация; Linux — AppImage и `.deb`. Приложение ставится одним файлом и не зависит от общего runtime. Ассеты — пакет `.alef` рядом с бинарником (позже — внутри ресурса бинарника).

**Как сделано (M7c, срез 1: alef-runtime bundle).** Команда `alef-runtime bundle <PACKAGE.alef> --runtime <бинарник> --platform <…>` и API `bundle(packagePath, options)` в `@alef-runtime/tools` собирают установочные артефакты одним проходом. Сначала проверка пакета: подпись, хеши, формат 1; неподписанный принимается только с `--allow-unsigned`; `--no-verify` не реализован намеренно. id/name/version/runtime читаются из проверенного снимка `alef.ktav`. Диапазон `runtime` сверяется ТОЛЬКО с явным `--runtime-version`: runtime-бинарник никогда не запускается для выяснения версии (у него нет `--version`), без `--runtime-version` проверка пропускается с предупреждением. Семантика диапазонов — строгая грамматика: только компараторы с оператором из `=`, `>`, `>=`, `<`, `<=`, `^`, `~` и ПОЛНОЙ версией `x.y.z` (арифметика на BigInt u64); prerelease-границы разрешены только для `=` и операторов сравнения; wildcards, голые и частичные версии отвергаются с ясной ошибкой; невалидные версии/диапазоны никогда не совпадают. Имя бандла — `<name>-<version>-<platform>`, `--name` переопределяет корень (строгий ASCII-набор, не `.`/`..`; обязателен для `nsis`; префиксы записей zip санируются в набор имён ZIP, если в корне есть иные символы). Умолчания — `dir` плюс платформенный архив (zip для win32-x64, иначе tar.gz). Раскладка `dir`: `bin/<runtime>`, `app/app.alef`, LICENSE/NOTICE копируются точно из каталога runtime (каждый ≤16 МиБ, сверх — отказ), `bundle.json` с SHA-256 пакета и runtime, лаунчер вызывает `alef run <пакет>` (`.cmd` для win32-x64, `sh` иначе; оба резолвят `$0` через symlink, права 0755). Форматы: `zip` — unix-права во внешних атрибутах, записи ≤512 МиБ (больший runtime — только tar.gz); `tar.gz` — ustar, записи в байтовом порядке, детерминированный, время из `SOURCE_DATE_EPOCH` или 0; `deb` — ar с `control.tar.gz` и `data.tar.gz`, дерево `/opt/<pkg>` с обёрткой `run` в `/opt/<pkg>/<pkg>`, symlink `/usr/bin/<pkg>` на обёртку, обёртка и `.desktop` используют правило двойного экранирования Exec из runtime, `.desktop` как у writer'а runtime (Type/Name/Exec/Icon?/Terminal=false/Categories=Utility;/StartupWMClass, без `Version`), Architecture amd64, Package — lowercase kebab, Maintainer из `--maintainer` либо плейсхолдер; `nsis` — сгенерированный `installer.nsi` с `OutFile`, per-user установка в `$LOCALAPPDATA\Programs`, ярлык Start Menu с аргументом `run`, экранированным по правилам NSIS (`$\"`), и безопасным именем `.lnk`, HKCU-ключ деинсталляции и AppUserModelId; текст `build-installer.cmd`; сама команда `bundle` makensis не запускает, зато CI компилирует собранный скрипт настоящим makensis на Linux и Windows (тест `makensis_compiles_the_staged_installer_into_a_setup_exe_without_warnings`, включается `ALEF_TEST_MAKENSIS=1`: код выхода 0, ни одного `warning:`, `<имя>-setup.exe` начинается с `MZ`), установщик не запускается; `app` — тонкое дерево `.app` с Info.plist (CFBundleIdentifier, а также `NSCameraUsageDescription` и `NSMicrophoneUsageDescription`: без них macOS завершает процесс при открытии камеры или микрофона), лаунчер вызывает `run`, при `zip` дополнительно упаковывается в `<stem>.app.zip` с правами. `dmg` — образ диска macOS: собирается только на macOS-хосте (на другом хосте и для не-darwin платформы отказ до записи), `hdiutil create -srcfolder <корень> -volname <имя> -fs HFS+ -format UDZO -ov` вызывается вектором аргументов без оболочки над папкой, в которой лежит `<stem>.app` (срез `-srcfolder` копирует СОДЕРЖИМОЕ папки, поэтому дерево `.app` кладётся внутрь корня), имя тома — имя приложения без разделителей и управляющих символов, не длиннее 27 знаков; готовый образ публикуется эксклюзивной ссылкой (без перезаписи, `--force` заменяет), рабочий каталог удаляется всегда. Образ не подписан и не детерминирован (hdiutil пишет время и случайные идентификаторы), ссылка «Applications» для перетаскивания не добавляется. Тесты: четыре с подставным hdiutil (аргументы и содержимое корня, отказы до записи, сбои инструмента и `--force`, имя тома) выполняются везде; на macOS-раннерах CI включается `ALEF_TEST_HDIUTIL=1`: настоящий `hdiutil create`, затем `hdiutil verify`, монтирование только для чтения и проверка `Info.plist` и runtime внутри `.app`, размонтирование в `finally`. Безопасность: пути runtime и пакета проходятся покомпонентно, компоненты-symlink отвергаются (цепочка temp-каталога ОС исключена); runtime ≤1 ГиБ: раскладки `dir` и `nsis` копируют его потоково с двойной проверкой хеша, а форматы `zip`/`tar.gz` и `app` материализуют его в памяти (ограничен пределом 1 ГиБ на runtime и 512 МиБ на запись zip); пакет ограничен по размеру и проверен на идентичность; публикация без гонок — no-clobber через `link`/эксклюзивный `mkdir` (`--force` заменяет); цели вывода — только прямые дети выходного каталога; лаунчеры, `.desktop` и NSIS вызывают `run` с путём пакета. Тесты: 32 в `packages/tools/test/bundle.test.mjs` (30 выполняются, 2 пропускаются вне POSIX). **Не сделано:** подпись и нотаризация установщиков и образов, AppImage, MSI/WiX, лаунчер с пакетом, встроенным в бинарник runtime, автообновление собранного приложения, ручные проверки на чистых машинах (строка приёмки остаётся ручной).

**Как сделано (M7c, срез 2: runtime любой платформы).** Бинарник чужой ОС не нужно искать вручную: `alef-runtime fetch-runtime [--platform <…>] [--runtime-version <semver>] [--cache <каталог>] [--registry <url>]` и API `fetchRuntime(options)` берут его из платформенного пакета `@alef-runtime/runtime-<platform>` и печатают путь; `bundle` без `--runtime` делает то же самое для своей `--platform`, но только после проверки пакета (неподписанный, нечитаемый или требующий другой runtime пакет отвергается до скачивания). Платформа по умолчанию — текущая; версия по умолчанию — версия самих tools (tools и runtime выпускаются с одной версией), `--runtime-version` берёт другую; поиск версии по диапазону из манифеста приложения не делается. Реестр читается напрямую через `fetch`, без `npm`: запись пакета целиком (`/@alef-runtime%2Fruntime-<platform>`), из неё `dist.tarball` и `dist.integrity`; тарболл проверяется по sha512 из реестра (запись без sha512 отвергается), затем распаковывается встроенным чтением ustar с проверкой контрольной суммы каждого заголовка, а `package.json` внутри должен называться и версионироваться как запрошено. Реестр — только https, http допустим для localhost; адрес с логином и паролем отвергается. Результат лежит в кэше `<кэш>/<версия>/<платформа>/` (по умолчанию `$ALEF_RUNTIME_HOME/cache/runtime`, как ключи) рядом с `LICENSE-MIT` и `LICENSE-APACHE`; каталог публикуется одним `rename` из рабочего, поэтому недокачанного в кэше не бывает, повторный запрос сети не использует. `bundle` теперь копирует в раскладку и `LICENSE-*` из каталога runtime, поэтому собранное приложение получает тексты лицензий runtime. Лимиты: запись реестра ≤16 МиБ, тарболл ≤256 МиБ, бинарник ≤1 ГиБ; тарболл и распакованный бинарник держатся в памяти. Прокси-переменные `fetch` по умолчанию не читает (Node 24: `NODE_USE_ENV_PROXY=1`); подлинность издателя (provenance) не проверяется — доверие даёт https реестра и его integrity. Файлы bundle перенесены в `src/workflow/bundle/` из-за предела 7 элементов в каталоге. **Не сделано:** выбор версии по диапазону, предзагрузка всех платформ одной командой, проверка provenance, пакет, который выпускается и публикуется (платформенные пакеты пока не опубликованы, до первого релиза команда работает только с `--registry` на свой реестр или с `--runtime`).

## CI и выпуск

- Матрица из M0.4; релизный workflow по тегу: сборка runtime на 4 конфигурациях → артефакты → установщики runtime и публикация npm-пакетов `@alef-runtime/runtime-*`, затем `@alef-runtime/runtime`, `@alef-runtime/api`, `@alef-runtime/mcp`, `@alef-runtime/tools`, `create-alef-runtime` с согласованной версией.
- Версия протокола транспорта и версия `@alef-runtime/api` проверяются рукопожатием `runtime.hello`; диапазон `runtime` из манифеста проверяет лаунчер.
- Политика версий: semver; до 1.0 — minor может ломать API, фиксируется в CHANGELOG; поэтому несколько версий runtime стоят рядом.

**Как сделано (релизный workflow).** `.github/workflows/release.yml`: триггеры — пуш тега `v*` (реальный режим), пуш ветки `release-check/**` (тот же прогон в dry-run, приёмочная строка «dry-run публикации» проверяется им), `workflow_dispatch`. Джобы: `plan` (scripts/release/plan.mjs: одна согласованная версия во всех публикуемых package.json; в реальном режиме совпадение с тегом без `v`; печать порядка публикации — сначала платформенные `@alef-runtime/runtime-*` из таблицы `platforms` в scripts/ci/affected.json (единственный источник матрицы сборки, `fromJSON(needs.plan.outputs.matrix)`), затем `@alef-runtime/runtime`, `@alef-runtime/api`, `@alef-runtime/mcp`, `@alef-runtime/tools`, `create-alef-runtime`; без секрета реальный режим падает сразу с понятной ошибкой), `build` (релизный `alef` без фичи `e2e`, смоук `--help` (у `alef` нет `--version`), архив `alef-<версия>-<платформа>.zip` на Windows / `.tar.gz` иначе + `.sha256`, артефакты), `npm-publish` (скачивание артефактов через `gh run download`, генерация платформенных пакетов существующим `packages/runtime/scripts/make-platform-package.mjs`, публикация по порядку через `scripts/release/publish-package.mjs`: staging-копия без `private` и с подстановкой версии вместо `workspace-version-placeholder`; тексты `LICENSE-MIT` и `LICENSE-APACHE`, которые пакет перечисляет в `files`, но не хранит у себя, берутся из корня исходников — как в платформенных пакетах (без этого мета-пакет `@alef-runtime/runtime` не проходил staging: запись `files` без файла — ошибка); dry-run — `npm publish --dry-run`, реальный режим — `npm publish --access public --provenance`), `github-release` (только реальный режим, `gh release create` с архивами и контрольными суммами, единственная джоба с `contents: write`). Сопровождающий создаёт явно: секрет репозитория `NPM_TOKEN` (automation-токен npm с правом публикации скоупа `@alef-runtime`) и защищённое GitHub-окружение `release` (обе публикующие джобы объявляют `environment: release`). **Не сделано:** подпись бинарников (Authenticode / нотаризация), установщики помимо архивов (M7c), автоматический CHANGELOG (заметки релиза берутся из `--generate-notes` GitHub); первый реальный релиз — до них публикация проверяется только dry-run.

## Приёмка

| Проверка | Как |
|---|---|
| Чистая машина без Rust: `npm create alef-runtime`, `dev`, `build`, `pack`, `alef run` пакета | CI-job на трёх ОС |
| Лаунчер выбирает версию по `runtime` манифеста; при отсутствии — понятная ошибка | e2e |
| Подпись: пакет с изменённым файлом не запускается; чужой ключ при обновлении — отказ | e2e |
| `alef install` создаёт ярлык/обёртку/`.desktop` с идентичностью приложения, `uninstall` убирает | ручная на трёх ОС |
| Установщик runtime ставит, запускает, удаляет; версии рядом не мешают друг другу | ручная на трёх ОС |
| Приложение-пример alef-file-manager (отдельный репозиторий) собрано как обычное Alef-приложение (пакет `.alef`) и установлено | ручная |
| `updater`: обновление с подписью ставится; с неверной подписью — отказ | e2e |
| Единая сборка (M7c): установщик со встроенным runtime работает на чистой машине | ручная |
| npm-пакеты публикуются из CI по тегу | dry-run публикации |

**Как сделано (M7d.4, чистая машина).** Сценарий e2e `devflow` (tests/e2e/scenarios/app/devflow.mjs) повторяет путь разработчика без Rust и без сети npm-пакетов проекта: create-alef-runtime генерирует проект во временном каталоге ВНЕ репозитория (`--yes`, фиксированные имя и id), `npm pack` рабочих пакетов `@alef-runtime/api` и `@alef-runtime/tools` кладёт tarball-ы рядом, зависимости проекта переключаются на них (`file:`), затем `npm install` (без audit/fund, userconfig — во временном каталоге, кэш npm — обычный кэш раннера, ограничение по времени). Дальше установленным CLI: `alef-runtime build`, `keys` (домашний каталог ключей — `ALEF_RUNTIME_HOME` во временном каталоге), `pack`, `verify` (отпечаток из `keys` должен совпасть), затем реальный бинарник `alef` (собранный с фичей `e2e`) запускает пакет `alef run <pkg>.alef --trust-key <отпечаток>`: страница собранного бандла отвечает через мост `e2e.report` (хвост, добавленный в `src/main.js` до сборки, повторяет механизм tests/e2e/harness.js), вердикт PASS, процесс выходит с кодом 0, ключ закреплён в `trust/` внутри того же временного каталога. Затем `alef-runtime dev` (dev-сервер rsbuild на фиксированном порту, `--ready-timeout` ограничен; runtime находится через `ALEF_BIN`) доводит до готовности и dev-сервер, и runtime, страница завершает runtime, CLI останавливает dev-сервер и возвращает код 0 — шаг включён, потому что детерминирован и ограничен по времени. Всё записанное остаётся во временном каталоге сценария (ALEF_HOME, ALEF_RUNTIME_HOME, XDG_* и кэш npm — туда же), профиль приложения переносится во временный каталог переменной `ALEF_APP_HOME` (на Windows также `APPDATA`/`LOCALAPPDATA` детей), пользовательский не затрагивается; каталог удаляется в `finally` после остановки процессов. В CI сценарий выполняется там, где сегодня выполняется e2e: Linux (ubuntu-24.04, xvfb) — на каждом прогоне с e2e, Windows — в группе «lifecycle/integration: app» (окно требует успешной ANGLE-сборки). Не покрыто: опубликованные npm-пакеты (вместо них tarball-ы рабочей копии), машина, действительно лишённая Rust (у раннеров CI toolchain есть — сценарий просто не вызывает cargo и скрипты сборки репозитория), установщики и лаунчер.

**Как сделано (M7d.5, приложение-пример как пакет).** Историческая запись: работа делалась, когда приложение File Manager жило в этом репозитории. Теперь приложение, его сборка и упаковка находятся в отдельном репозитории alef-file-manager (приложение-пример, PHPCraftdream/alef-file-manager), а перечисленные ниже скрипты, шаги CI, артефакты и e2e-сценарий из этого репозитория удалены; упаковка любого приложения остаётся командой `pack` из `@alef-runtime/tools`. Тогда сборка File Manager (`npm run build:frontend`: Rsbuild плюс `frontend/assemble-app.ts`) давала обычный каталог Alef-приложения `frontend/app` (манифест, иконка, ассеты в `dist`). Пакование шло как у любого приложения: `npm run pack:app` (`node scripts/app/pack.mjs`, обычный node-скрипт без shell-подстановок — кроссплатформенно) вызывал CLI `@alef-runtime/tools` `pack` на `frontend/app`; имя ключа бралось только из переменной окружения `ALEF_RUNTIME_KEY` (обязательно, проверялось на допустимые символы), результат — `dist/file-manager.alef` либо путь из аргумента. В CI (Linux, job `build`; условие повторяло условие frontend-сборки и требовало выход планировщика `package_app` — изменён `frontend/**` или `packages/tools/**`, либо полный прогон) шаг «Package the File Manager (.alef)» создавал одноразовый ключ командой `alef-runtime keys fm-package-ci` в scratch-каталоге `ALEF_RUNTIME_HOME` под `runner.temp`, затем упаковывал и проверял подпись (`alef-runtime verify` печатает `signed by <отпечаток>`); `.alef` выкладывался артефактом `file-manager-alef` (хранение 7 дней). Вручную пакет ставился так: скачать артефакт и выполнить `alef install <файл>.alef --trust-key <отпечаток>`, где отпечаток — строка `signed by <fingerprint>` из лога CI. e2e-сценарий `fm-package` упаковывал собранный `frontend/app` одноразовым ключом через tools API, проверял подпись и отпечаток, запускал `alef run <пакет> --trust-key <отпечаток>` и ждал runtime-сигнал `ALEF_READY app=org.alef.filemanager` с таймаутом; в джобах без собранного frontend (в CI File Manager собирался только на Linux) сценарий завершался с ясной пометкой о пропуске.

## Риски

- Идентичность приложения без своего бинарника: на macOS нужна `.app`-обёртка на каждое приложение, её подпись и нотаризация — открытый вопрос; без них — предупреждение Gatekeeper. На Windows AUMID задаётся только через ярлык (при запуске на месте уведомления общие).
- Подпись и нотаризация macOS требуют Apple Developer аккаунта; без них — неподписанные сборки с предупреждением Gatekeeper.
- Несколько версий runtime рядом — место на диске и поддержка старых версий (политика: исправления безопасности только для последней minor до 1.0).
- Время сборки Servo в CI — кэш обязателен; релизная сборка на 4 платформах — часы.
