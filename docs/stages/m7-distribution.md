# M7 — Дистрибуция

Обзор: `../FRAMEWORK-PLAN.md` §6.3. Зависит от M3 (генерический бинарник `alef`, File Manager как JS-приложение), M2b (согласие и подмена прав) и CI из M0.4.

## Цель

Поставка как у Java: **runtime ставится отдельно, приложение — пакет `.alef`**; единая сборка (runtime в установщике приложения) — необязательная опция. Разработчик без Rust: `npm create alef-tron` → `npm run dev` → `npm run build` даёт пакет `.alef`; `npm run bundle` — по желанию установщик с runtime внутри. Этап делится на три части.

| Часть | Что |
|---|---|
| M7a | runtime и лаунчер: установщики runtime, версии рядом, `alef run`, ассоциация `.alef`, самообновление runtime |
| M7b | пакеты: формат `.alef`, подпись, `@alef-tron/tools`, `alef install`, идентичность приложения, обновление пакета (`updater`) |
| M7c | единая сборка (опция): runtime и пакет в одном установщике |

## M7a — runtime и лаунчер

- **Установка runtime** — установщик (Windows: MSI/NSIS, macOS: `.pkg`/`.dmg`, Linux: AppImage/`.deb`) и npm-пакеты для разработки: `@alef-tron/runtime-win32-x64`, `-darwin-arm64`, `-darwin-x64`, `-linux-x64` (бинарник `alef`, `os`/`cpu` в `package.json`) и мета-пакет `@alef-tron/runtime` (выбор бинарника при запуске, как esbuild).
- **Версии рядом:** `<корень Alef>/<версия>/alef`; в системе один лаунчер `alef`, который читает `runtime: ^X.Y` из манифеста пакета и запускает подходящую установленную версию. Подходящей нет — понятная ошибка с командой локального копирования (`alef runtime install <версия> <путь-к-бинарнику-alef>`); неиспользуемые версии убирает `alef runtime prune`. Автоматический запуск выбранного бинарника остаётся дальнейшим шагом.
- **Запуск:** `alef run <пакет.alef|каталог> -- <аргументы>`; двойной клик по `.alef` (ассоциация типа файла) делает то же. Каталог остаётся для разработки (`dev`).
- **Самообновление runtime:** новая версия ставится рядом со старыми и не ломает установленные приложения; подпись обновления проверяется (ed25519, ключ проекта).
- **Размер:** release-бинарник runtime ~118 МБ (Windows, Servo 0.6): теперь это размер одной установки, а не каждого приложения. Цели: strip символов, LTO в релизе, сжатие в установщике; замер на каждой платформе в CI.

### Запуск пакета без установки (M7a.1)

**Договор среза, не отчёт о готовом лаунчере.** Шаг 1 вводит в общую схему необязательное строковое поле `runtime` и отдельные помощники строгой проверки SemVer 2.0.0 для пакетов. Разбор диапазона — `semver::VersionReq`, грамматика Cargo: `^`, `~`, пересечения сравнений через запятую, wildcard (`*`, `1.*`, `1.2.*`) и точное `=1.2.3`; не npm-грамматика в целом. Пустая строка, `null`, нестроковые значения, неверный диапазон и `||` отвергаются. Версия приложения из каталога остаётся прежней непустой строкой, без нового требования SemVer. Этот шаг сам по себе **не включает запуск пакетов**: дальше отдельно идут (2) ограниченный неизменяемый снимок архива, (3) архивные ассеты, (4) передача authority в модули, (5) проверенная загрузка и хранилище доверия, (6) подключение CLI и единого запуска, (7) реальные e2e. Ниже — обязательный договор этих будущих шагов.

**Один запуск, два источника.** `alef run <PATH> [параметры лаунчера] [-- аргументы приложения]` и `alef --app <PATH>` — равнозначные записи одного конвейера загрузки → проверки → плана → доверия → прав → runtime. Источник определяется типом объекта ФС: каталог — прежний запуск разработки (включая `--dev-url`, без упаковки, установки и подписанта), обычный файл — кандидат в пакет; остальные типы отвергаются. Расширение `.alef` не требуется; неудачная проверка файла не переключается на загрузку каталога. Для пакета `--dev-url` запрещён. Сохраняются `OsString` аргументы, граница `--`, завершающий deep-link URL и служебный `--launch-mode window`.

**Манифест и совместимость.** Корневой `alef.ktav` читается только из проверенного снимка, декодируется как UTF-8 и разбирается тем же `Manifest::from_ktav_str`; обязательные поля и проверка `id` сохраняются. Строгая SemVer `version` обязательна только для пакета. Без `runtime` используется этот бинарник без обещания совместимости; с диапазоном его должна удовлетворять текущая версия, сообщаемая `app.info.runtimeVersion`. Автоматического перехода на другой runtime здесь нет: диагностика перечисляет установленные версии и предлагает локальную установку только при отсутствии подходящей. При наличии подходящей называет выбранную версию и бинарник, явно сообщая, что relaunch ещё не реализован; ошибка чтения хранилища сообщается отдельно, не как пустой список. Манифест, ассеты, начальные URL окон и иконка проверяются до любой записи доверия или согласия. Порядок: снимок и полная проверка → манифест и совместимость → ассеты/иконка/план → аргументы приложения → доверие → права → модули/мост → выполнение.

**Ошибки.** В stderr: `alef: <CATEGORY>: <detail>`, с путём пакета и проблемной записью, где доступны. Код **2** — непригодный ввод, проверка пакета, манифест, совместимость, выбранные ассеты и лимиты запуска; **3** — нерешённое/отменённое доверие или согласие на права; **1** — операционная ошибка после проверки ввода, включая I/O хранилища доверия и ошибку runtime; **0** либо запрошенный приложением код — успешное выполнение. Обязательные диагностические сообщения:

```text
NOT_A_PACKAGE: expected a format-1 Alef ZIP package
PACKAGE_FORMAT: <reader detail>
PACKAGE_INTEGRITY: <entry>: CRC-32 mismatch
PACKAGE_INTEGRITY: <entry>: SHA-256 mismatch
PACKAGE_SIGNATURE: strict Ed25519 verification failed
PACKAGE_MANIFEST: missing root alef.ktav
MANIFEST_INVALID: id/version: <reason>
MANIFEST_INVALID: $APP is unavailable for archive applications
RUNTIME_INCOMPATIBLE: requires <range>; this executable provides <version>; installed runtimes: <versions or none>; no installed runtime satisfies <range>; install a matching local binary with alef runtime install <version> <path-to-alef-binary>; runtime relaunch is not implemented in this slice
PACKAGE_RUN_LIMIT: <limit and entry>
SIGNER_CHANGED: <id> is pinned to <old>; this package uses <new>
SIGNATURE_REQUIRED: <id> was previously accepted with a signing key
NOT_AVAILABLE: native registration requires an installed application
```

`NOT_A_PACKAGE` — только не-ZIP; узнаваемый ZIP, нарушающий строгий профиль, — `PACKAGE_FORMAT`, не неподписанный пакет. Некорректная запись подписи сохраняет отдельную диагностику читателя, без продолжения с предупреждением. Ошибки вложенных записей разбираются структурно (`PackageError::Entry`), не по тексту. Ошибки выбранных ассетов выявляются до построения runtime и получают код 2.

**Доверие: TOFU по точному `id`.** Верная подпись удостоверяет ключ, не реальное имя разработчика. При первом подписанном запуске окно runtime показывает недостоверное отображаемое имя из манифеста, проверенные `id` и версию, **полный** отпечаток подписанта и вопрос «запомнить этот ключ для этого id приложения». Принятие закрепляет ключ только за точным `id`; права решаются независимо, даже если их список пуст. Неинтерактивный эквивалент — `--trust-key <fingerprint>`: ровно 64 hex-символа нижнего регистра, обязательно совпадающие с проверенным подписантом. `--grant` не подтверждает доверие. Совпавший закреплённый ключ переходит к правам; другой — код 3 `SIGNER_CHANGED`, без замены ключа или обхода.

Неподписанный пакет без закреплённого подписанта допускается только после заметного предупреждения runtime **на каждый запуск** либо с `--allow-unsigned`; доверенная личность разработчика не сохраняется. Его отдельная идентичность — SHA-256 точных неизменяемых байт всего архива, изменение содержимого меняет пространство решений. Если за `id` уже закреплён подписант, неподписанный запуск запрещён с кодом 3 `SIGNATURE_REQUIRED`, даже с `--allow-unsigned`. Отдельного режима обхода закрепления здесь нет.

**Хранилище доверия отдельно от прав.** Неизменяемые закрепления: `runtime_home()/trust/<sha256-of-exact-id>.json`; запись версии 1 содержит точный `app_id`, открытый ключ и пересчитанный отпечаток (оба по 64 hex-символа нижнего регистра), предел записи 4 КиБ. Отсутствие — первое использование; повреждение, чужой id, неизвестная версия, ссылка/reparse point или ошибка чтения — отказ (fail-closed), не новый вопрос. Каталог закрыт для других пользователей; запись полностью записывается и синхронизируется, затем публикуется атомарно без замены существующего файла; при гонке победившая запись перечитывается и сравнивается. Временные файлы убираются при ошибке, каталог синхронизируется где поддерживается. Только лаунчер пишет закрепления, не bridge приложения. `permissions reset` их не удаляет; повреждённое хранилище прав не служит основанием доверия.

**Публичный id и authority различны.** `AppInfo.id` и текст UI остаются id манифеста. Лаунчер задаёт authority: `Directory`, `SignedPackage { fingerprint }` либо `UnsignedPackage { archive_digest }`; приложение её не выбирает. Для пакетов токен — SHA-256 в hex нижнего регистра над доменно-разделённым кодированием точных полей с префиксом длины каждого: вид, id, отпечаток/дайджест. Не lossy-сокращение имени и не FNV. Каталоги сохраняют legacy-поведение без миграции.

В `Identity` сохраняются прежние JSON-поля, но `signer` пакета — `pkg-signed:<fingerprint>` или `pkg-unsigned:<digest>`, а `Identity::key` для этих префиксов возвращает сильный токен. Он разделяет `ALEF_HOME/consent` и `ALEF_HOME/shadow`; `$APPDATA`, `$APPCONFIG`, `$APPCACHE` пакета — `<существующая база ОС>/alef-packages/<authority-token>`. `store` — `$APPDATA/store`, восстановление окон — `$APPDATA/window-state.json`, secrets — `alef/packages/<authority-token>`, single-instance endpoints (включая Windows pipes и запасные Unix sockets) — по токену, не публичному id. Каталоговые ключи согласия и пространства хранения/секретов/instance остаются прежними.

**Как сделано (M7a.1, база данных приложения).** Переменная `ALEF_APP_HOME` переносит базы данных, конфига и кэша приложений обоих источников: каталоговых — `<база>/<id>` (legacy-раскладка), пакетных — `<база>/alef-packages/<authority-token>` (_bases_ в `namespace_paths` строит вызывающий). Значение принимается только заданное, непустое и абсолютное — как `ALEF_HOME` игнорирует относительное; иначе базы — каталоги ОС (`data_local_dir`, `config_dir`, `cache_dir`). Базы — `<ALEF_APP_HOME>/data`, `<ALEF_APP_HOME>/config`, `<ALEF_APP_HOME>/cache`; создаёт их по-прежнему лениво сами модули, не лаунчер. `$DOCUMENTS`, `$DOWNLOADS`, `$DESKTOP`, `$HOME`, `$TEMP` не переносятся — это папки пользователя, не профиль приложения. Области прав `$APPDATA`, `$APPCONFIG`, `$APPCACHE` следуют за базами автоматически: строятся из тех же `PathVars`. Дочерние процессы CLI и повторно запущенный оконный runtime наследуют `ALEF_HOME` и `ALEF_APP_HOME` из окружения родителя. При повторном запуске runtime вычисляет пути заново из унаследованных значений.

**Нативные регистрации.** Для пакета после обычной проверки прав настоящие `app.autostart.enable`, `disable`, `isEnabled`, `app.registerDeepLinks`, `unregisterDeepLinks` возвращают `NOT_AVAILABLE: native registration requires an installed application`. Проверка в обработчике до system и e2e-real backend: нельзя создавать, читать или удалять даже legacy-регистрации каталога с тем же id. Подмена сохраняет прежнее поведение в памяти. Каталоговые регистрации не меняются; проверка и доставка deep-link аргумента при запуске поддерживаются.

**Снимок, проверка, публикация.** Один handle обычного файла читается в собственную память с проверенным пределом и fallible allocation; дальше — `Package::from_bytes`, без повторного открытия пути, изменяемого mmap или внешнего изменяемого буфера. Снимок общий для запросов, не копия на каждый запрос. Замена, усечение или перезапись исходного файла после получения снимка не меняют этот запуск; следующий проверяет всё заново. До разбора манифеста, согласия и выполнения сохраняется полный проход по всем payload-файлам, включая приватные: CRC-32 всегда, SHA-256 при наличии списка хешей; подпись — строгая Ed25519. Чтения снова проверяют CRC и доступный SHA-256. Неподписанный архив без списка имеет только CRC, не аутентичность издателя. Не кэшировать все распакованные данные и не распаковывать архив на диск.

Профиль запуска: **256 МиБ сжатого архива**, **64 МиБ одного публичного ассета**, **1 МиБ манифеста**, **4 МиБ байт иконки**, PNG не больше **1024×1024** (размеры проверяются до выделения памяти изображения). Это не изменение валидности Формата 1: больший корректный пакет получает код 2 `PACKAGE_RUN_LIMIT`. Размер записи проверяется до выделения потребительского буфера (`read_limited`); отсутствующая иконка даёт стандартную, ошибка проверки/лимита не скрывается.

Публичны только точные потомки выбранного `assets` (по умолчанию `dist`), с границей `root + "/"`; корневого fallback нет. Корень должен иметь хотя бы одного потомка, файл `dist`, `Dist/...` или `dist2/...` не подходят; проверяются коллизии регистра неявных каталогов. Общий pathname-парсер и точный регистр сохраняются. Корневые манифест, иконка и `META-INF` приватны; намеренный `dist/alef.ktav` публичен как любой потомок. Entry и начальные URL окон проходят ту же проверку и ограниченное чтение до доверия/прав.

Не больше **четырёх outstanding запросов** ассетов: неблокирующее admission до запуска worker, пятый — `WouldBlock` / HTTP 429. Permit остаётся у worker до завершения проверки и создания тела ответа, даже при отмене вызывающего; общий mutex сериализует чтение снимка. Нет неограниченной очереди и распакованного кэша. Это предел памяти ассетов в работе на стороне runtime, **не общий предел памяти renderer/JavaScript или процесса**. Полный проход всё ещё подчиняется пределам Формата 1 и может временно держать один приватный файл до 512 МиБ вместе со снимком и метаданными; переносимый wall-clock timeout не обещается.

**Нет каталога приложения у архива.** `$APP` не имеет расширения в путь ФС; точная переменная `$APP` в файловой области пакета — `MANIFEST_INVALID: $APP is unavailable for archive applications`. `$APPDATA`, `$APPCONFIG`, `$APPCACHE` доступны в пространстве authority. Объявления `sidecar:` отвергаются до запуска; динамические sidecar-вызовы — `NOT_AVAILABLE`, даже при `cli.exec: *`. Никакой распаковки или поиска в родителе пакета, CWD и writable cache. Обычные внешние CLI-команды, права и PATH не меняются: заданный CWD — разрешённый реальный каталог, без CWD — рабочий каталог лаунчера. Шаблоны аргументов остаются буквальными, новой интерполяции путей нет. `assets` — корень внутри архива, entry/URL окон — относительно web-root; корневая иконка читается только из проверенного архива. Relaunch и дочерние окна сохраняют аргументы и заново открывают/проверяют пакет.

**Вне пакетного среза M7a.1:** install/uninstall приложения, обновление приложения и runtime, download и автоматический relaunch runtime, ротация или замена ключа, rollback tracking, глобальное доверие разработчику, ассоциации файлов, пакетные нативные регистрации, извлечение sidecar и archive `fs` API. Дальнейшие требования установки, updater и версий рядом ниже/выше — дорожная карта, не возможности M7a.1.

## M7b — пакеты и установка приложений

### Пакет `.alef`

zip: `alef.ktav` в корне, ассеты, `icon.png`, `META-INF/` — список хешей всех файлов и подпись ed25519 разработчика. Ассеты читаются из архива без распаковки на диск (источник ассетов моста — каталог или архив). Подпись проверяется до запуска; неподписанный пакет запускается с предупреждением (политика пользователя). Манифест задаёт `runtime: ^X.Y` — требуемый диапазон версий runtime.

#### Формат 1 (общий договор читателя на Rust и упаковщика на JS)

Оба конца пишутся по этому тексту независимо; расхождение находит перекрёстная проверка на общих векторах: файл `tests/fixtures/package-vectors.txt` (86 архивов, по одному на строку: имя, ожидаемый ответ `signed:<отпечаток>` / `unsigned` / `reject`, архив в hex) собирает `packages/tools/scripts/package-vectors.mjs` по тексту формата, не кодом упаковщика и не кодом читателя; оба читателя обязаны дать ответ каждой строки. Формат узкий намеренно: всё, что два разбора ZIP могли бы понять по-разному, запрещено, а не уточнено.

**Контейнер.** Файл — ровно: записи подряд (local header, затем данные), без промежутков; затем central directory; затем EOCD из 22 байт с комментарием нулевой длины. Ни префикса, ни суффикса, ни промежутков, ни пересечений, ни второго архива; EOCD — последние 22 байта файла, все смещения отсчитываются от начала файла и проверяются с контролем переполнения. Порядок записей в central directory совпадает с порядком local headers. Запрещены: ZIP64, data descriptors, дополнительные поля (extra length равна 0 в обоих заголовках), комментарии записей, шифрование, многотомность, записи-каталоги и любые записи кроме обычных файлов (внешние атрибуты читатель игнорирует и никогда не использует как тип или права). Общие флаги записи равны ровно `0x0800` (UTF-8, бит 11). Методы сжатия 0 (stored) и 8 (deflate); CRC-32 записан и в local header, и в central directory и проверяется; имя (побайтно), требуемая версия, флаги, метод, время и дата DOS, CRC-32, оба размера и длина имени в local header и в central directory совпадают. Единственный источник перечня записей — central directory, и все потребители пакета (лаунчер, runtime, updater, установщик) читают файлы только через один проверенный источник; чтение соседних файлов на диске и второй независимый разбор ZIP запрещены.

**Пределы.** Проверяются по объявленным значениям до выделения памяти и распаковки: файл архива не больше 2304 МиБ, central directory не больше 16 МиБ, записей не больше 10 000, файл не больше 512 МиБ несжатым, сумма несжатых размеров не больше 2 ГиБ, `META-INF/hashes` не больше 16 МиБ, `META-INF/signature` не больше 256 байт. Объявленному размеру не доверяется: распаковка обязана потребить ровно compressed size байт и выдать ровно uncompressed size байт (для stored они равны), чтение останавливается на объявленном размере + 1 байт и это ошибка.

**Имена.** Только ASCII, и только байты `A–Z a–z 0–9 . _ - @ +` и разделитель `/`. Всё остальное — отказ (пробел, не-ASCII, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, `%`, `~`, управляющие символы). Так два разбора не могут разойтись из-за кодировок, нормализации Unicode, регистра за пределами ASCII и псевдонимов Windows; расширение алфавита — задача следующей версии формата, не уточнение этой. Имя не пусто и не начинается с `/`; сегменты не пусты, не равны `.` и `..`, не заканчиваются точкой, не длиннее 255 байт; имя целиком не длиннее 1024 байт; часть сегмента до первой точки не равна (без учёта регистра) `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`. Два имени, равные после приведения ASCII-букв к нижнему регистру, — дубликаты (отказ); имя файла не может быть началом пути (по сегментам) другой записи. Зарезервированные имена `alef.ktav`, `META-INF/hashes`, `META-INF/signature` имеют только это точное написание: запись, равная зарезервированному без учёта регистра, но отличающаяся побайтно, — ошибка; под `META-INF/` (в любом регистре) других записей нет.

**Состав.** Обязателен файл `alef.ktav` в корне. Остальное — файлы пакета (в том числе необязательный корневой `icon.png`); подпись покрывает все они. Публичны только файлы внутри выбранного манифестом подкаталога `assets` (необязательная строка, по умолчанию `dist`). `native://app/x` выбирает ровно `<assets>/x`, без возврата к корню ZIP или приложения. Корневые манифест, иконка и `META-INF` не становятся веб-ресурсами. Всё внутри публичного подкаталога публикуется намеренно; подпись доказывает целостность, не приватность. Это договор публикации runtime, не изменение набора хешируемых файлов и не утверждение о завершённой интеграции ZIP с Servo.

**`META-INF/hashes`.** UTF-8 без BOM, строки заканчиваются `\n` (последняя тоже), не больше 10 000 строк. Строка: 64 hex-символа нижнего регистра SHA-256 содержимого файла, два пробела, имя записи (как в архиве). Строки по возрастанию имён, сравнение лексикографическое по беззнаковым байтам (для ASCII это код символа; при совпадении начала короткое имя идёт первым; сортировка по умолчанию `.sort()` в JS, использующая UTF-16, допустима только потому, что имена ASCII). Каждый файл архива кроме `META-INF/*` ровно в одной строке, лишних строк нет, пустых строк, `\r` и BOM нет.

**`META-INF/signature`.** UTF-8, ровно три строки с `\n` в конце: `alef-package 1`, `key <base64>` (32 байта открытого ключа Ed25519), `sig <base64>` (64 байта подписи). Base64 по RFC 4648 §4: без пробелов и переносов, с обязательным `=`, с нулевыми неиспользуемыми битами; признак — повторное кодирование декодированных байт даёт исходную строку побайтно. Подписывается сообщение `alef-package-v1\n` + точные байты `META-INF/hashes`. Нормативна проверка в runtime (Rust): Ed25519 по RFC 8032 с отказом при S ≥ L и при A или R малого порядка (`verify_strict`); проверка в @alef-tron/tools — удобство разработчика, её «подпись верна» не означает, что runtime примет пакет, а пакеты, которые собирает сам упаковщик, проходят обе. Отпечаток ключа — SHA-256 открытого ключа, hex нижнего регистра; это идентичность ключа, а не подтверждённое имя разработчика: интерфейс показывает отпечаток и состояние доверия к нему, и не выдаёт имя из манифеста за удостоверенную личность подписанта.

**Проверка при открытии.** (1) контейнер, пределы, имена и состав; (2) есть `signature` — есть и `hashes`, подпись верна; (3) есть `hashes` — набор файлов равен набору списка, хеш каждого файла совпадает (полный проход, до запуска); (4) каждое чтение файла проверяет его хеш по списку ещё раз. Нет `signature` — пакет **не подписан**: результат «не подписан», но если `hashes` есть, он проверяется так же. Любое расхождение — ошибка, а не предупреждение. Результат открытия: `Signed { key, fingerprint }` или `Unsigned`. Таблица записей, список хешей, ключ и результат подписи фиксируются при открытии и на весь сеанс; повторное открытие архива по пути их не заменяет. Чтение возвращает потребителю только полностью проверенные байты: до совпадения CRC-32 и SHA-256 никакие куски не передаются, не выполняются и не разбираются, а проверка и потребление работают над одним и тем же снимком байт в памяти (не над повторным чтением файла и не над изменяемым отображением в память).

**Упаковщик.** Записи расположены по возрастанию имён (то же сравнение), local headers и central directory в одном порядке. Поля фиксированы: версия «создано» `0x031E` (Unix, 3.0), версия «нужно» 20, флаги `0x0800`, время DOS 0 и дата DOS `0x0021` (1980-01-01), внешние атрибуты `0x81A40000` (обычный файл 0644), без дополнительных полей и комментариев. Метод 8 для файла, который он делает меньше, иначе 0; байты deflate зависят от сборки zlib, поэтому тот же вход даёт те же байты на одной версии Node, а подпись покрывает хеши содержимого, не байты архива. Закрытый ключ — только у разработчика (`alef-tron keys`), в пакет не попадает.

**Требования к установке и обновлению** (не часть читателя; обязательны для M7a и остального M7b).

- Устанавливаемый пакет имеет в проверенном `alef.ktav` `id` и `version` (SemVer 2.0.0); регистрационные данные, диапазон `runtime` и ассоциации берутся только из проверенного манифеста, вложенные архивы — обычные файлы и не распаковываются.
- При установке сохраняются проверенные `id` и 32 байта ключа подписи, а также наибольшая принятая версия. Updater сравнивает кандидата с этой записью, а не с ключом из доставленного пакета или повторно открытого прежнего файла; `updater.publicKey`, если задан, обязан совпадать с ключом установленного пакета.
- Обновление допускается только при точном совпадении `id`, том же ключе и версии, большей сохранённой наибольшей (по SemVer, без build metadata); откат — только отдельным явным действием пользователя. Имя приложения не заменяет `id`.
- Для ранее подписанного установленного приложения отсутствие подписи — ошибка; запуск такого пакета как неподписанного требует отдельного явного решения пользователя и не наследует доверие, права и идентичность прежней установки.
- Команда запуска, которую строит установщик, — путь и массив аргументов без оболочки; значения манифеста в `.desktop`, XML, plist и скриптах кодируются по правилам формата, а не подставляются как текст команды: подпись не очищает строки.

**Как сделано (M7b.1, Rust).** Крейт `alef-package` владеет источником и узким ZIP-читателем: stored и raw deflate через `flate2` с miniz, проверка CRC-32 и ограничение распаковки объявленным размером + 1 байт. Таблицы записей, хешей и идентичность подписанта фиксируются при открытии; проверяются SHA-256 и строгие подписи Ed25519, повторные чтения возвращают собственные буферы и заново проверяют CRC и хеши. Неподписанный пакет без `META-INF/hashes` проверяется только по CRC, без гарантии SHA-256. **Не сделано:** интеграция с runtime, launcher, updater и install — позже.

**Как сделано (M7a.1, пакет).** `Package::open_snapshot` открывает один дескриптор обычного файла, проверяет потолок сжатых байт и получает собственный буфер архива с выделением памяти, допускающим отказ; до возврата выполняется полная проверка пакета. Последующие изменения файла на диске или замена пути не меняют снимок; получение снимка не гарантирует атомарности при одновременной перезаписи того же размера. `entry_size` ищет точное имя в фиксированной таблице и возвращает объявленный несжатый размер; `read_limited` проверяет лимит вызывающего до чтения, затем полностью проверяет байты, сохраняя прежний `read`. Пределы запуска выбирают вызывающие: например, 256 МиБ сжатого архива, 64 МиБ на ассет, 1 МиБ на манифест и 4 МиБ на иконку — необязательный профиль, не правило Формата 1. Потребителям следует разделять один снимок через mutex, поскольку чтение требует `&mut self`; это API пакета, не утверждение о выполненной интеграции с launcher или runtime.

**Как сделано (M7a.1, архивные ассеты runtime).** Мост принимает каталог или проверенный снимок `Package`, публикует только точных потомков выбранного корня, использует общий pathname-парсер и проверяет entry до регистрации модулей и транспорта. Архивные чтения сериализованы mutex, ограничены 64 МиБ и четырьмя outstanding запросами; пятый получает HTTP 429, отмена вызывающего не освобождает permit работающего чтения. Это API runtime и его регрессионные проверки: **лаунчер пока не запускает пакеты**, подключение пакетного запуска, доверия и authority остаётся отдельным шагом.

**Как сделано (M7a.1, загрузка и доверие).** Крейт `alef` как протестированная библиотека: классификация источника по типу ФС (каталог — прежний запуск разработки, обычный файл — пакет, остальное — `NOT_A_PACKAGE`); ограниченный снимок одного файла (256 МиБ архив, 64 МиБ ассет, 1 МиБ манифест, 4 МиБ иконка, PNG не больше 1024×1024 до выделения памяти), полная проверка пакета, манифест только через проверенный снимок, строгая SemVer-версия и требование `runtime` с точным текстом `RUNTIME_INCOMPATIBLE`, отказ `sidecar:` и проверка существования выбранного корня; ошибки типизированы (`alef: <КАТЕГОРИЯ>: <детали>`, коды 2/3/1, `PackageError` разбирается структурно); хранилище доверия fail-closed (`runtime_home()/trust/<sha256-id>.json`, 4 КиБ, каталог 0700, запрет ссылок и reparse points, атомарная публикация без замены — hard link на Unix и `MoveFileExW` без флага замены на Windows, временные файлы убираются, гонка перечитывается и сравнивается); решение доверия TOFU (`--trust-key` только равный подписанту, `SIGNER_CHANGED`, `SIGNATURE_REQUIRED` даже с `--allow-unsigned`, `--grant` доверие не одобряет, неподписанный пакет идентичен digest'ом архива и не закрепляется); окно доверия в стиле consent с необязательными полями `trust` в request/answer (прежние запросы и ответы остаются валидными; вопрос доверия без прав работает) и переменная `ALEF_E2E_TRUST` (accept/refuse) только в сборке с фичей `e2e`; план пакета строится тем же конвейером, что и каталога: `AssetInput::Archive`, `PathVars.app: None` (точный отказ `$APP`), identity согласия `pkg-signed:<отпечаток>`/`pkg-unsigned:<digest>`. **Не сделано (следующий шаг):** командная строка (`run`, `trust`, `--trust-key`, `--allow-unsigned`, запрет `--dev-url` для пакетов), подключение в `launch` и e2e реального бинарника.

**Как сделано (M7a.1, команда run).** Обе формы запуска — `run <PATH>` и опция `--app` — это один `Command::Run`: источник классифицируется по типу ФС (каталог — прежний запуск разработки с `--dev-url`, обычный файл — пакет, остальное — `NOT_A_PACKAGE`, суффикс не требуется). Новые опции `--trust-key` и `--allow-unsigned` для каталога и `--dev-url` для пакета — ошибки использования с кодом 2. В `launch` один конвейер: загрузка → проверка → план → доверие (окно доверия или `--trust-key`; отказ → 3, ошибка хранилища → 1) → согласие → runtime. Стабильные отказы пакета печатаются как `alef: <КАТЕГОРИЯ>: <детали>` с кодами 2/3/1. Authority пакета попадает в `ModuleContext`, иконка берётся из проверенного пакета, `AppInfo` хранит id манифеста. Перезапуск окна и window-child повторно открывают и проверяют пакет тем же конвейером через прежние аргументы. `alef permissions list|set|reset` работают с пакетом через тот же проверенный загрузчик и identity (`pkg-signed:`/`pkg-unsigned:`) и никогда не создают и не заменяют pin доверия; субкоманда `alef trust <REQUEST> <ANSWER>` обслуживает окно доверия.

**Как сделано (M7a.1, ранняя проверка документов).** `alef-runtime` даёт публичный `prepare_assets(AssetInput, entry, initial_document_urls) -> PreparedAssets`: источник собирается и аудируется один раз, а входной документ и все начальные оконные документы проверяются тем же `pathname`-lookup'ом, которым мост отвечает на запросы, с теми же видами `io::Error`; `Bridge::with_options` принимает готовый `PreparedAssets` вместо `AssetInput` и больше не проверяет и не пересобирает источник. Лаунчер вызывает `prepare_assets` в новом `application::pipeline::settle_launch` до окна доверия и до вопроса согласия, поэтому пакет с отсутствующим входным документом завершается кодом 2 и категорией `MANIFEST_INVALID` (`alef: MANIFEST_INVALID: assets: …`), не задав пользователю ни одного вопроса. Каталог без `--dev-url` проходит ту же раннюю проверку; с `--dev-url` документы не проверяются, как и раньше (dev-сервер отдаёт их сам). Списки мутаций этого шага — `run.json` и `preflight.json` в `scripts/quality/mutations/` — прогоняются рабочим процессом `Mutation`.

**Как сделано (M7a.3, хранилище версий runtime).** Локальный модуль хранит версии в `runtime_home()/runtimes/<MAJOR.MINOR.PATCH>/<binary>` (`alef.exe` на Windows, `alef` на Unix); абсолютный `ALEF_HOME` переопределяет `runtime_home()`, иначе используется прежний пользовательский каталог данных. Имена версий — строго три числовых компонента, без prerelease/build и ведущих нулей. Корень и каталог версии не могут быть ссылкой или Windows reparse point; установленной считается версия с обычным бинарником, тоже без ссылок/reparse. `alef runtime list` перечисляет версии по числовому SemVer, от старых к новым, печатает путь и отмечает текущую версию ` *`. `select` выбирает наибольшую подходящую установленную версию тем же общим `runtime_requirement_met` и парсером диапазонов, что проверяет манифест; версии публичного API остаются строками, отдельной зависимости semver у лаунчера нет.

`alef runtime install <VERSION> <SOURCE_BINARY>` только копирует предоставленный локальный обычный файл, ничего не скачивает. Временный файл `.tmp-<pid>-<counter>` создаётся эксклюзивно в корне хранилища с повтором при коллизии; байты копируются, выполняется `flush`, на Unix права бинарника ставятся 0755 до `sync_all`, корня и каталога версии — 0700. Публикация без замены: hard link на Unix, `MoveFileExW` с flags 0 на Windows; каталог на Unix синхронизируется best-effort. При обычном отказе убирается только собственный временный файл и собственный пустой каталог версии; чужой файл или каталог не удаляется. При гонке двух успешных источников за одну новую версию ровно один установщик побеждает, другой получает `ALREADY_INSTALLED`, включая ещё незавершённый каталог победителя.

`alef runtime prune [--keep <VERSION>]... [--dry-run]` всегда сохраняет текущую `CARGO_PKG_VERSION` и явно перечисленные версии. Dry run печатает `would-remove`, не удаляя; реальный запуск — `removed`, небезопасное дерево — `skipped` с причиной. Неизвестные имена, файлы вместо каталогов и каталоги без обычного бинарника не трогаются; ссылки/reparse в дереве запрещают удаление, глубина обхода ограничена 64. При несовместимом текущем бинарнике категория `RUNTIME_INCOMPATIBLE` и код 2 сохраняются: отсутствие подходящих версий даёт упорядоченный список и команду установки, наличие — выбранный бинарник и явное отсутствие relaunch, нечитаемое хранилище — отдельную причину без ложного утверждения об отсутствии версий.

| Категория хранилища runtime | Код выхода | Причина |
|---|---|---|
| `INVALID_ARGUMENT` | 2 | Неверные аргументы, версия или исходный файл |
| `ALREADY_INSTALLED` | 2 | Версия уже установлена или её каталог занят установкой |
| `RUNTIME_STORE` | 1 | Операционная ошибка хранилища |

Этот срез доверяет предоставленному бинарнику и метке версии: встроенную версию и происхождение файла не удостоверяет. Безопасность путей предполагает стабильное дерево под контролем владельца, не защищает от враждебной одновременной подмены тем же владельцем; восстановление после падения/отключения питания не обещается. **Не сделано:** download/network, updater, системный installer, проверка update-signature и автоматический relaunch на выбранный runtime. Добавлены регрессионные тесты; результаты CI здесь не утверждаются.

### Установка

`alef install <пакет.alef>` (или согласие при первом запуске) копирует пакет в каталог приложений пользователя и создаёт **идентичность приложения**, хотя бинарник общий:

- Windows: ярлык с AppUserModelID (имя и значок в панели задач, уведомления приложения);
- macOS: тонкая обёртка `.app` (`Info.plist`: id, имя, значок, описания TCC), которая запускает `alef run`;
- Linux: `.desktop` с `MimeType` для deep links.

Ассоциации файлов, deep links и автозапуск регистрируются как `alef run <пакет> ...`. `alef uninstall <id>` убирает всё созданное. Решения по правам (M2b) хранятся отдельно и удаляются по желанию.

### Пакеты npm и команды `@alef-tron/tools`

| Пакет | Содержимое |
|---|---|
| `@alef-tron/api` | JS API (`packages/api`), сборка ESM + `.d.ts` |
| `@alef-tron/mcp` | MCP-сервер и клиент (M4b) |
| `@alef-tron/tools` | CLI `alef-tron`: `dev`, `build`, `pack`, `bundle`, `check`, `keys`; зависит от `@ktav-lang/ktav` для проверки `alef.ktav` |
| `create-alef-tron` | шаблон: `alef.ktav` (разделы безопасности закрыты), Vite/Rsbuild на выбор, пример вызова API, пример обработки подмены прав (таймауты сети, пустая ФС) |

Организацию `alef-tron` в npm зарегистрировать до первой публикации.

- `dev` — проверить `alef.ktav`, запустить dev-сервер фронтенда (команда из `package.json` или конфига) и `alef run . --dev-url http://127.0.0.1:<port>`; HMR; закрытие окна останавливает dev-сервер.
- `build` — проверить манифест, собрать фронтенд, сложить `dist/` + `alef.ktav` в каталог приложения.
- `pack` — собрать и подписать пакет `.alef` из каталога приложения (`keys` создаёт и хранит ключ разработчика).
- `check` — проверка манифеста и окружения.

**Как сделано (M7b.2, JS).** Приватный `@alef-tron/tools` 0.1.0: ESM на Node >=22.12.0, без зависимостей, CLI `keys`, `pack`, `verify`, базовый `check` и публичный API. `keys` печатает имя, отпечаток и raw32 `key <base64>`; список — только имена и отпечатки. `pack` подписывает список SHA-256 содержимого Ed25519, по умолчанию пишет соседний `<имя-каталога>.alef`; каталог ключей и `.alef-tron` исключены всегда, `.git` и `node_modules` включаются явно. JS-профиль ZIP строгий: только ASCII-имена, файлы без записей-каталогов, flags `0x0800`, без extras, комментариев, descriptors, ZIP64 и многотомности; дубликаты и конфликты префиксов выявляются до чтения ключа и содержимого. Сжатие автоматически выбирается только при выигрыше размера; детерминизм ограничен одинаковыми входными байтами, ключом, параметрами и версией Node. Читатель сохраняет неизменяемый снимок архива и индекс; проверка хеширует все файлы до возврата и при каждом чтении. `node:crypto` — удобная JS-проверка, нормативна Rust `verify_strict`; успех JS не гарантирует принятия runtime. `check` проверяет лишь обычный файл до 1 МиБ и непустой UTF-8 текст без BOM и табов, не синтаксис и схему Ktav; зависимостей парсера нет, полную валидацию манифеста выполняет Alef до запуска приложения. Оптимизация тестов заменяет массовое создание файлов метаданными-моками для снижения дискового I/O; таймауты не увеличены, `test:tools` использует обычную конкурентность runner и изолированные временные каталоги. Lint охватывает `packages`, tsconfig не меняется. **Отложено:** `dev`, `build`, `bundle`, `create-alef-tron`, полная JS-проверка манифеста и окружения, runtime/updater, публикация npm и перекрёстные тесты Rust/JS.

**Как сделано (M7b.3, dev и build).** CLI `@alef-tron/tools` получил команды `build [dir] [--out <dir>]` и `dev [dir] [--ready-timeout <ms>] [-- <аргументы>]`. `build` выполняет настроенную команду сборки и собираёт каталог приложения: `alef.ktav`, необязательную `icon.png` и дерево outDir внутри каталога ресурсов манифеста; опасные и пересекающиеся назначения отклоняются до любых удалений. `dev` запускает настроенную dev-команду, опрашивает `alef-tron.devUrl` до готовности (по умолчанию 60 с), затем порождает runtime с `--app` и `--dev-url` (плюс аргументы после `--`); runtime ищется по `ALEF_BIN`, `@alef-tron/runtime` (`getRuntimePath()`) и `alef` в PATH. Оба процесса принадлежат команде и убираются за собой: dev-сервер завершается при выходе runtime, гибели dev, таймауте готовности и по SIGINT/SIGTERM; код выхода runtime возвращается. **Не сделано:** полная проверка схемы манифеста и bundle — позже.

**Как сделано (M7b.4, create-alef-tron).** Приватный `create-alef-tron` 0.1.0: ESM на Node >=22.12.0, без зависимостей. CLI: `create-alef-tron [directory] [--name] [--id] [--bundler rsbuild|vite] [--yes]`; умолчания — `my-alef-app`, имя из каталога, `com.example.<нормализованное имя>`, `rsbuild`; `--yes` берёт умолчания и не спрашивает. Шаблон манифеста закрыт: все секции прав и `external` пусты/false, версия 0.1.0, одно окно `/index.html`, сгенерированный `icon.png`. Оверлеи rsbuild и vite дополняют общий базовый шаблон; версии: `@alef-tron/* ^0.1.0`, `@rsbuild/core` 2.2.9 точно (наблюдается в корневом `package.json`), `vite ^6.0.0` (Vite 6 поддерживает Node 22; точный патч здесь не наблюдался). Страница-пример вызывает `app.info()` и демонстрирует работу с подставленными правами: пустой `fs` через `fs.readDir` от `path.appData()`, HTTP со своим таймаутом через `http.request`; таймауты, пустые результаты и `PERMISSION_DENIED` — обычные исходы. Инсталляций и git нет; шаблоны — обычные файлы с подстановкой `{{ID}}`/`{{NAME}}`/`{{PACKAGE}}` и отказом при инъекции. Тесты `node --test` (27), oxlint и check-structure зелёные; сборки бандлерами не запускались, публикация npm вне среза.

**Как сделано (M7a.2, npm runtime-пакеты).** Приватный `@alef-tron/runtime` 0.1.0: резолвер `ALEF_BIN` (существующий обычный файл) → платформенный пакет через `require.resolve` → понятная ошибка с платформой, пакетом, причиной и исправлением, без fallback. Таблица платформ закреплена тестом за матрицей CI. Скрипт `make-platform-package.mjs` генерирует четыре платформенных пакета для релиза. Шим `bin/alef` запускает бинарник без оболочки, пересылает аргументы, код выхода и сигналы. Константа `PLATFORM_VERSION_RELATION` (workspace-version-placeholder) ждёт генератора релиза.

### `updater`

```ts
updater.check(): Promise<{ available: boolean, version?, notes? }>
updater.download({ onProgress? }): Promise<void>
updater.install(): Promise<never>    // перезапуск
```

- Манифест: `updater: { endpoint: https://..., publicKey: <ed25519> }`; обновляется **пакет** `.alef` (подпись ключом разработчика проверяется до установки; ключ должен совпасть с прежним, иначе — отказ и новый вопрос о доверии). Новые права в обновлении спрашиваются заново (M2b).
- Обновление требуемой версии runtime: если пакет требует более новый runtime, updater сообщает и предлагает поставить его.

## M7c — единая сборка (опция)

`alef-tron bundle` кладёт runtime рядом с пакетом и собирает обычный установщик: Windows — NSIS или MSI (WiX), подпись signtool; macOS — `.app` (Info.plist, TCC), `.dmg`, codesign + нотаризация; Linux — AppImage и `.deb`. Приложение ставится одним файлом и не зависит от общего runtime. Ассеты — пакет `.alef` рядом с бинарником (позже — внутри ресурса бинарника).

## CI и выпуск

- Матрица из M0.4; релизный workflow по тегу: сборка runtime на 4 конфигурациях → артефакты → установщики runtime и публикация npm-пакетов `@alef-tron/runtime-*`, затем `@alef-tron/runtime`, `@alef-tron/api`, `@alef-tron/mcp`, `@alef-tron/tools`, `create-alef-tron` с согласованной версией.
- Версия протокола транспорта и версия `@alef-tron/api` проверяются рукопожатием `runtime.hello`; диапазон `runtime` из манифеста проверяет лаунчер.
- Политика версий: semver; до 1.0 — minor может ломать API, фиксируется в CHANGELOG; поэтому несколько версий runtime стоят рядом.

## Приёмка

| Проверка | Как |
|---|---|
| Чистая машина без Rust: `npm create alef-tron`, `dev`, `build`, `pack`, `alef run` пакета | CI-job на трёх ОС |
| Лаунчер выбирает версию по `runtime` манифеста; при отсутствии — понятная ошибка | e2e |
| Подпись: пакет с изменённым файлом не запускается; чужой ключ при обновлении — отказ | e2e |
| `alef install` создаёт ярлык/обёртку/`.desktop` с идентичностью приложения, `uninstall` убирает | ручная на трёх ОС |
| Установщик runtime ставит, запускает, удаляет; версии рядом не мешают друг другу | ручная на трёх ОС |
| File Manager собран как обычное Alef-приложение (пакет `.alef`) и установлен | ручная |
| `updater`: обновление с подписью ставится; с неверной подписью — отказ | e2e |
| Единая сборка (M7c): установщик со встроенным runtime работает на чистой машине | ручная |
| npm-пакеты публикуются из CI по тегу | dry-run публикации |

## Риски

- Идентичность приложения без своего бинарника: на macOS нужна `.app`-обёртка на каждое приложение, её подпись и нотаризация — открытый вопрос; без них — предупреждение Gatekeeper. На Windows AUMID задаётся только через ярлык (при запуске на месте уведомления общие).
- Подпись и нотаризация macOS требуют Apple Developer аккаунта; без них — неподписанные сборки с предупреждением Gatekeeper.
- Несколько версий runtime рядом — место на диске и поддержка старых версий (политика: исправления безопасности только для последней minor до 1.0).
- Время сборки Servo в CI — кэш обязателен; релизная сборка на 4 платформах — часы.
