# M0.3 — Трей, меню, глобальные хоткеи и диалоги с циклом winit

Spike-код: `backend/crates/alef-runtime/src/spikes/integration.rs` (feature `spike-integration`, по умолчанию выключена; `--features alef-runtime/spike-integration` + env). Режимы: `ALEF_SPIKE_INTEGRATION=1` (полный; `+ALEF_SPIKE_INTEGRATION_NO_DIALOG=1` — без диалога), `ALEF_SPIKE_RESIZE_ONLY=1` (только драйвер resize — база без объектов интеграции). Хуки в `window/app.rs` — 3 точки по 2 строки за `#[cfg(feature = "spike-integration")]`: `activate` (после создания окна), `poll` (в `process_requests` после получения state), `deactivate` (в `exiting`). Spike НЕ трогает ControlFlow: собственный поток-таймер шлёт `Wake`, дедлайн анимации хоста не перезаписывается. Тест-страница: `experiments/integration-spike/` (счётчик rAF (только логирует), закрывает окно; вердикт — из Rust, см. ниже).

## Архитектура доставки событий (рекомендация для M5)

Крейты (`tray-icon` 0.24, `muda` 0.19, `global-hotkey` 0.8) отдают события через ОДИН общий crossbeam-канал на источник; клонирование хендла не дублирует сообщения. Поэтому: **один поток-потребитель на каждый receiver** (`spawn_forwarder`): поток — единственный читатель крейтового канала, конвертирует событие в owned-значение (`SpikeEvent`), кладёт в собственный `std::sync::mpsc` spike-канал и будит цикл через `EventLoopProxy<Wake>`; главный поток в `drain_events` читает ТОЛЬКО собственный канал. Проба шлёт synthetic-события в ТОТ ЖЕ канал — она проверяет путь канал → Wake → drain. Альтернатива — `set_event_handler` (заменяет канал крейта целиком, глобальный static) — пригодна, но выбран паттерн forwarder-потоков: он не подменяет поведение крейтов и одинаков для всех трёх.

Юнит-тест `forwarding_layer_is_lossless_ordered_and_non_duplicating` (15-й тест alef-runtime): тот же generic `spawn_forwarder`, 4 потока-производителя × 250 событий → ни одно не потеряно/не задублировано, порядок внутри производителя сохранён, по одному wake на событие. Проверяет механизм (receiver → own channel → wake), без GUI-крейтов.

## Замеры (debug, машина загружена — значимы соотношения; один exe)

Команда: `ALEF_TRANSPORT_SPIKE=1 <режим> ALEF_RESIZE_TRACE=1 <exe> --frontend-dir experiments/integration-spike`. Одинаковая последовательность: 16 программных resize (цикл A/B через `request_inner_size`).

| | run0 база (resize-only) | run1 интеграция, без диалога | run2 интеграция, полный |
|---|---|---|---|
| exit | 0 | 0 | 0 |
| создание menu/tray/hotkey | не создавались (`null`) | все `true` | все `true` |
| forwarding (пробы через реальный канал) | `null` (не выполнялся) | `true` (4/4) | `true` (4/4) |
| диалог | — | пропущен | виден на +1.23 c, WM_CLOSE → закрыт за 23 мс, `show()` → `Ok` за 4.39 c |
| resize-presents / `timed_out=true` | 16 / **0** (из 492 trace) | 16 / **0** (из 612) | 16 / **0** (из 425) |
| ожидание кадра min/p50/max, мс | 5.2 / 29.0 / 90.1 | 10.5 / 29.1 / 65.8 | 11.4 / 31.3 / 168.9 |
| rAF, кадров/505 мс | — | 23.8 в среднем | 16.2 при открытом диалоге, 23.2 после |
| события трея (реальный ввод!) | 0 | 0 | **35** (Enter/Move по иконке) |

Выводы по числам: в трёх прогонах зафиксировано 0 таймаутов (хост-ждёт 100 мс, painter-безопас 250 мс; оба нулей). p50 ожидания кадра: 29.0 → 29.1 → 31.3 мс (отношение ≤1.08 на одной загруженной машине). Один прогон на режим недостаточен, чтобы исключить регрессию; требуется N>>3 на чистой/стабильной машине. Открытый диалог НЕ останавливает отрисовку, но снижает rAF до ≈70% (16.2 кадров/505мс против 23.2–23.8) — вероятно, модальный owner-диалог влияет на приоритет подачи кадров; для M2/M5 стоит замерить в release.

**Реальные события трея**: в run2 курсор задерживался над иконкой — 35 событий `Enter`/`Move` дошли до лога с полными координатами через весь конвейер (крейтовый receiver → forwarder → канал → Wake → drain). Это первая e2e-проверка с настоящим вводом; клик/пункты меню/хоткей реальным вводом не проверены.

Машинная проверка (`experiments/integration-spike/run.sh full|nodialog|baseline [break-forwarding]`): вердикт пишет Rust (`ALEF_SPIKE_VERDICT_FILE`) — булевы `created`, `forwarding`, `dialog_render_continuity`, `resize_no_timeouts`, `shutdown_clean`; процесс завершается с кодом ≠ 0 при любой ложной проверке, раннер падает и на отсутствующей проверке (fail-closed). `dialog_render_continuity` считается по нативным счётчикам презентаций (отношение во время диалога к базе ≥ 0.35, порог в `verdict.rs`), а НЕ по rAF страницы: страница лишь логирует rAF (`phase:"measure"`), приведённые выше значения rAF — наблюдение из логов, не часть вердикта. Оракул проверен: подряд два прогона `full` дали `RUN PASS`; прогон `full break-forwarding` (`ALEF_SPIKE_BREAK=forwarding` отбрасывает одну пробу) завершился кодом 1 — проверка умеет падать. Первый «проваленный» прогон ошибочно прошёл, потому что раннер передавал `ALEF_SPIKE_BREAK=break-forwarding` вместо `forwarding`; исправлено.

## Проверено автоматически

- создание: `init_for_hwnd` (HMENU ≠ 0), иконка трея, регистрация хоткея — прогоны 1–2;
- механизм пересылки: юнит-тест (lossless/order/no-dup под конкуренцией) + проба 4/4 через реальный канал в обоих интеграционных прогонах + 35 реальных событий трея в run2;
- диалог: открыт из Tokio (MessageBoxW в собственном потоке rfd, воркер не блокируется), закрыт WM_CLOSE в окно своего процесса, resize во время и после — без таймаутов;
- resize: три режима, 0 таймаутов во всех (хост-ждёт: 100 мс `window/state.rs`, painter-безопас: 250 мс);
- завершение: иконка удалена, меню снято (`remove_for_hwnd`) перед `detach()`, хоткей снят, код выхода 0 (проверено во всех прогонах).

## Осталось ручным (ввод/платформы)

1. Клик по иконке трея → меню (2 пункта) → `menu event`; хоткей Ctrl+Alt+Shift+F20 при неактивном окне → `hotkey event`.
2. Модальность: клик в главное окно при открытом диалоге должен блокироваться (rfd передаёт HWND как owner — по исходникам; поведение ОС не наблюдали).
3. Внешний вид иконки/меню; перетаскивание окна; плавность resize глазами.
4. Linux/macOS — не запускались: Linux — GTK/libappindicator/libxdo для трея и меню, глобальные хоткеи только X11 (Wayland не поддерживается global-hotkey), rfd — xdg-portal (libdbus/zenity) или gtk3; macOS — всё строго main thread (меню NSApp, трей, manager хоткеев).

## Пробелы для M5

`TranslateAcceleratorW` для menu accelerators (winit-цикл не вызывает); на Wayland нет глобальных хоткеев; снижение темпа rAF при модальном диалоге — замерить в release; `send` у событий крейтов `pub(crate)` — программной генерации нет, авто-e2e только через собственный канал (проба) или `set_event_handler`.
