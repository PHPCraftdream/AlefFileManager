# M2b — Подтверждение и подмена прав

Обзор: `../FRAMEWORK-PLAN.md` §6.4. Зависит от M2 (модули `app`, `window`, окно runtime). Этап стоит перед M3: `fs`, `net` и `cli` пишутся сразу с веткой подмены, а не переделываются потом.

## Цель

Пользователь, а не только разработчик, решает, что приложение получит. Он подтверждает каждое право из манифеста и может **подменить** любое: приложение получает правдоподобную среду и не может отличить её от настоящего поведения (сеть есть, но запросы уходят в таймаут; файловая система виртуальная). После этапа есть механизм, хранилище решений и окно согласия; сами подмены `fs`, `net`, `cli` дописываются в их этапах (M3, M4).

## Модель

Три исхода для права: **разрешить** (настоящий доступ), **подменить** (среда-двойник), **отказать** (`PERMISSION_DENIED`). Права, которых нет в манифесте, по-прежнему дают `PERMISSION_DENIED` — это ошибка разработчика, а не решение пользователя. Полная таблица подмен по модулям — `../FRAMEWORK-PLAN.md` §6.4; здесь — устройство.

## Объём

### `alef-core`

- `Decision { Allow, Substitute, Deny }`; `PermissionSet::check` возвращает его вместо «да/нет». Манифестное право определяет, что *можно* спросить; решение пользователя — что *получено*.
- Решение попадает в `CallContext` (`ctx.decision()`), модуль выбирает ветку: настоящая работа или подмена. Правило для авторов модулей: подмена не выдаёт себя ошибкой, у неё нет отдельного кода.
- `ConsentStore` (trait) — решения пользователя по приложению: ключ — `id` приложения и отпечаток ключа подписи пакета (пакет с тем же `id`, но другим ключом чужих решений не наследует); значение — решения по каждому праву и цели (путь, адрес, команда) и хеш раздела `permissions`, по которому видно, что права изменились. Реализация — файл в каталоге данных runtime (не приложения); хранится вне доступа приложения.
- Разбор объявленных команд `cli` (`permissions.cli.commands`: `name`, `program`, шаблон `args`, `description`) и проверка вызова по ним — в M4, схема манифеста — здесь.

### `alef-runtime` и `alef`

- **Окно согласия** — встроенная страница runtime (`native://runtime/consent`, код приложения в нём не исполняется), открывается перед запуском приложения, если права новые или изменились. Показывает каждое право отдельно: каждый путь `fs`, адрес `net`, слушающий порт (`listen`), каждую объявленную команду `cli`, переменные `app.env`, `clipboard.read`, `secrets`, `shortcut.global`, `window.create`. Для каждого — «разрешить / подменить / отказать», групповые «разрешить всё», «подменить всё». Опасные права (`cli` с `*`, `listen` не на loopback, `fs` с широким корнем) помечены и требуют отдельного подтверждения.
- Команды согласия (`runtime.consent.*`) доступны только странице согласия: проверяется источник запроса, приложению они не видны.
- `alef permissions list|set|reset <app>` и тот же экран из меню runtime — решение можно изменить в любой момент; изменение действует со следующего запуска (для безопасного сужения — сразу).
- Доверенные ключи: пакеты, подписанные ключом, который пользователь объявил доверенным, получают согласие без вопроса — по его политике (по умолчанию пусто).
- Первые пользователи механизма — `app.env` (подмена: переменная «не задана»), `clipboard.read` (буфер самого приложения) и `shell.*` (оболочка, которая ничего не делает); остальные подключаются в своих этапах.

### Манифест

- Необязательный `permissions.cli.commands` (появляется в M4); форма в `../FRAMEWORK-PLAN.md` §6.4. Все прежние разделы остаются; новых обязательных разделов нет.
- `permissions.window.create` (M2.2) попадает в окно согласия как обычное право.

## Как устроено

**Модель** — `alef-core::security::consent`. `Decision` (`allow`, `substitute`, `deny`), `Right` (`permission` и необязательный `scope` ровно так, как их написал манифест; в тексте `permission[:scope]`, у `Right::risk()` — пометка рискованных: `cli.exec` с `*` или с оболочкой/интерпретатором (`cmd`, `powershell`, `bash`, `python`, `node` и т. п., в том числе по полному пути, с `.exe` и `sidecar:`), `fs.*` на весь диск, весь `$HOME` или папку прямо под корнем диска (`/home/**`, `C:/Users/**`), `net.http` на любой адрес; шаблон читается как написан: `.` и двойные разделители не меняют смысла, `$HOME/*/**` — это весь `$HOME`; `..` в шаблоне пути — ошибка манифеста, а в правах, которые уже записаны, считается рискованным), `Consent` (решения пользователя; право без решения — запрет), `Identity` (`id` и «кто подписал»), `ConsentStore` и `FileConsentStore` (по файлу JSON на идентичность, запись через `.part`; повреждённый файл, чужая версия или файл, подложенный под чужое имя, — как «не спрашивали»).

**Идентичность.** Приложение из каталога известно по `id` и каноническому пути каталога: другой каталог с тем же `id` чужих решений не наследует. Пакет с подписью (M7b) будет известен по отпечатку ключа.

**Проверка.** `PermissionSet::check` отвечает `Decision`: право без записи в манифесте и право, в котором пользователь отказал, — один и тот же `PERMISSION_DENIED`, различить их приложению нечем. Где области пересекаются, действует самое строгое из подходящих решений; путь, который пользователь выбрал в диалоге (грант сессии), всегда настоящий. Набор решений общий у всех копий `PermissionSet`, поэтому `PermissionSet::narrow` сужает права уже запущенного приложения: взятое назад действует сразу, выданное дополнительно — со следующего запуска. `with_protected(папка)` выводит каталог данных runtime из-под любого права `fs` и любого гранта.

**Подмена не по умолчанию.** Команда, у которой есть двойник, объявляет `CommandBuilder::substitutes()` и читает `ctx.decision()`. Без объявления решение «подменить» превращается в отказ: ни один обработчик не отдаёт настоящее пользователю, который выбрал двойника (`window.create`, команды `e2e.*`). Двойники сейчас: `app.env` (переменная «не задана», без ошибки), `clipboard.read` (буфер приложения в памяти; запись в буфер пользователя не доходит), `shell.openExternal`, `shell.openPath`, `shell.showInFolder`, `shell.trash` (оболочка, которая ничего не делает и отвечает так же, ошибки за те же промахи прежние).

**Запуск (`alef`).** После разбора командной строки приложения лаунчер сверяет права манифеста с сохранёнными решениями. Всё решено — приложение стартует без вопроса. Есть новое право — спрашивает: `--grant allow|substitute|deny` отвечает за все нерешённые права и запоминает; окно согласия (по умолчанию); без окна (`--no-prompt` или нет дисплея) приложение не стартует, код выхода 3, права названы. Право, которого больше нет в манифесте, забывается. Изменённый список прав спрашивается заново, неизменённый — нет. В процессе запущенного приложения следит за хранилищем (`watch`, раз в 500 мс) и применяет только сужение.

**Окно согласия.** Отдельный процесс `alef consent <запрос> <ответ>` (служебный): в одном процессе нельзя создать цикл событий окна дважды, а приложение ещё не стартовало. Страница встроена в `alef`, в процессе нет кода приложения, команды `runtime.consent.request|answer|cancel` существуют только там: в реестре приложения их нет (для приложения это `NOT_FOUND`). Ответ проверяется на стороне Rust (`ask::validate`): каждое право ровно один раз, ничего лишнего, рискованное право с «разрешить» — только с подтверждением. Страница не вставляет тексты манифеста как разметку. Закрытие окна без ответа — отказ запускать.

**Командная строка.** `alef permissions list [<каталог>]`, `set <каталог> <право> <решение>`, `reset <каталог>`. `set` принимает только право, которое манифест запрашивает.

**Окружение.** `ALEF_HOME` переносит каталог данных runtime (там же `consent/`). Для e2e (только с `ALEF_E2E=1`): `ALEF_E2E_CONSENT` — готовые ответы `право=решение;...` и `*=решение` для остальных; `ALEF_E2E_CONSENT_UI` — клики пользователя в окне (JSON), которые страница проигрывает по собственным кнопкам.

## Приёмка

| Проверка | Как | Результат |
|---|---|---|
| `check` возвращает три исхода для каждого права; манифест без права — отказ, без вопроса к пользователю | Rust unit-тесты `alef-core` (`tests/consent.rs`) | зелёные |
| Хранилище: решение привязано к идентичности; чужая идентичность с тем же `id` спрашивается заново; изменённый список прав спрашивается заново | unit-тесты `consent.rs` (core и launcher), e2e `decisions` | зелёные |
| Окно согласия показывает все права манифеста, помечает рискованное, не даёт стартовать без решений и без подтверждения, возвращает решения; приложение не может вызвать `runtime.consent.*` | e2e `ask`, `cancel`, `consent` | зелёные |
| Подмена `app.env`, `clipboard.read`, `shell.*` неотличима: код и форма ответа те же, что у настоящего; двойник ничего не трогает | unit-тесты `alef-modules`, e2e `consent` (журнал оболочки) | зелёные |
| Команда без двойника отказывает на «подменить» | unit-тест `alef-core`, e2e `consent` (`window.create`) | зелёные |
| `alef permissions` меняет решение; сужение действует сразу, расширение — нет | e2e `decisions`, `narrowing`, unit-тест `watch` | зелёные |
| Решение пережило перезапуск; приложение с теми же правами не спрашивает | e2e `decisions` | зелёные |
| Каталог данных runtime недоступен ни одному праву и гранту | unit-тест `alef-core`, e2e `consent` | зелёные |

## Риски

- **Неотличимость неполная** (тайминги, сравнение каналов): этап обещает «приложение не получает кода ошибки и не видит разницы в данных», а не стойкость к целенаправленному поиску подмены. Это записано в окне согласия и в документации.
- **Приложение, не переносящее подмену** (зависает на таймауте сети, падает без файлов) — ответственность разработчика; в шаблоне `create-alef-tron` пример обработки таймаутов и пустой ФС.
- **Хранилище решений — цель для атак** (подмена файла решений). Файл в каталоге данных runtime, вне scopes `fs` любого приложения; запись только из процесса runtime.
- **Усталость от вопросов**: правила «разрешить всё/подменить всё», доверенные ключи, запоминание решения.
