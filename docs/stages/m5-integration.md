# M5 — Системная интеграция

Обзор: `../FRAMEWORK-PLAN.md`. Зависит от M2 (окна, `app`) и результатов M0.3.

## Цель

`menu`, `tray`, `shortcut`, автозапуск, deep links; доводка single-instance (передача аргументов deep link во второй экземпляр).

## Модули

### `menu` (desktop, UI)

```ts
menu.setApplicationMenu(items: MenuItem[]): Promise<void>     // macOS — строка меню; Windows/Linux — меню окна
menu.setWindowMenu(window, items): Promise<void>
menu.popup(items, { x?, y? }): Promise<string | null>         // контекстное меню, id выбранного пункта
menu.on('click', ({ id }) => ...)
MenuItem: { id, label, accelerator?, enabled?, checked?, kind?: 'normal'|'check'|'separator'|'submenu', items? }
// предопределённые роли: copy, paste, cut, undo, redo, selectAll, quit, about, minimize, …
```

`muda`; на macOS обязательны роли стандартного меню приложения.

### `tray` (desktop, UI)

```ts
tray.create({ icon: Uint8Array /* PNG */, tooltip?, menu?: MenuItem[] }, { signal? }): Promise<Tray>
  Tray: setIcon, setTooltip, setMenu, destroy, on('click'|'double-click'|'right-click'|'menu-click', ...)
  instance.on('click', ({ tray, button }) => ...) // button: left | right | middle
  instance.on('menu-click', ({ tray, id }) => ...)
```

`tray-icon` **0.24.2** — target-зависимость только Windows/macOS; на Linux нативные команды → `NOT_AVAILABLE` (AppIndicator/GTK здесь не подключены). Право `permissions.tray: true`; PNG — 1..256 КиБ, стороны 1..256 пикселей, tooltip — до 128 UTF-8 байт без управляющих символов, до 8 треев на документ. Меню использует ограничения `menu`; акселераторы запрещены, в том числе вложенные. Роли редактирования и `minimize` — предопределённые пункты `muda`, без пользовательского id события; `quit`/`about` → `NOT_AVAILABLE`. Все методы асинхронны, принимают `signal`, `Symbol.asyncDispose` вызывает `destroy`. События — только на экземпляре `Tray`, модульного `tray.on` нет.

### `shortcut` (desktop, UI)

```ts
shortcut.register('CommandOrControl+Shift+K'): Promise<Shortcut>   // on('pressed'), unregister()
```

`global-hotkey`; право `permissions.shortcut.global: true`; Wayland — глобальные хоткеи ограничены (portal), → `NOT_AVAILABLE` где невозможно.

### Автозапуск (`app`)

```ts
app.autostart.isEnabled(): Promise<boolean>; enable(); disable()
```

Windows — `HKCU\...\Run`; macOS — Login Item (`SMAppService`); Linux — `~/.config/autostart/<id>.desktop`. Реализация — `auto-launch` или собственная по платформам.

### Deep links (`app`)

```ts
app.on('open-url', ({ url }) => ...)       // myapp://path?x=1
```

- Схемы в манифесте: `deepLinks: [ myapp ]`.
- Регистрация схемы: при упаковке (M7: Info.plist, `.desktop`, реестр в инсталляторе); в dev — `app.registerDeepLinks()` для текущего пользователя (Windows/Linux).
- Если приложение запущено — ссылка доставляется через single-instance в первый экземпляр.

### Режим запуска из JS (`modes`, `app.launch`)

Сегодня режим задаёт манифест: `windows` не пуст — окно, `windows: []` и `console: true` — консольная утилита, `windows: []` без консоли — служба (`../APP-RUNTIME.md`, §2). Приложение, которое одним бинарём работает окном, утилитой и службой (`myapp` — окно, `myapp --cli …` — утилита, `myapp --serve` — служба), выбирает режим само, при старте, по параметрам запуска. Названия режимов: **`cli`** — консольная утилита (то, что сейчас `console: true`), **`foreground`** — явно заданный пользователем долгоживущий процесс без окон на переднем плане терминала, живёт до сигнала или `app.quit()` (не окно на переднем плане и не трей), **`window`** — окна из `windows`.

```ts
app.mode(): Promise<'undecided' | 'cli' | 'foreground' | 'window'>
app.launch(mode: 'cli' | 'foreground' | 'window'): Promise<void>   // один раз за запуск
```

Манифест: `modes: [cli, foreground, window]` — необязательный список режимов, из которых код может выбирать. Правила разбора: непустой `modes` не совместим с `console: true` (консоль включает выбор `cli`); `window` в `modes` — тогда и только тогда, когда `windows` не пуст (это окна режима `window`); `entry` (по умолчанию `/`) — документ-решатель, он исполняется до выбора; без `modes` или с `modes: []` сохраняется прежний запуск; повторы и неизвестные режимы отвергаются, `entry` сохраняет прежние ограничения корневого относительного пути.

Исполнение. Приложение с `modes` всегда стартует безоконно: скрытый `WebView` документа `entry`, без winit и без дисплея, так что на сервере `cli` и `foreground` работают как раньше. Документ читает `app.args()` (аргументы по схеме манифеста) и вызывает `app.launch(...)`.
- `cli`: открываются `app.stdin`, `app.stdout`, `app.stderr`; код выхода — `app.exit(code)`; до выбора запись в stdout — `NOT_AVAILABLE`.
- `foreground`: те же модули, что у безоконной службы; процесс живёт до сигнала или `app.quit()`.
- `window`: движок в одном процессе нельзя запустить заново (SpiderMonkey инициализируется один раз за процесс), поэтому сначала полностью завершается безоконная фаза (мост и слив консольных потоков), затем тот же `alef` запускается дочерним процессом. Исходные аргументы ОС сохраняются без shell и преобразования в UTF-8; скрытый `--launch-mode window` добавляется перед ними, до URL и `--`. Парсер принимает только `window`, отвергает повтор и отсутствие значения; после `--` это обычный аргумент приложения. Родитель ждёт ребёнка и передаёт его код выхода, окружение и stdio наследуются. Ребёнок читает сохранённые решения о правах из того же хранилища; single-instance и deep links работают уже в дочернем процессе. Защита жизненного цикла описана в M5.4 ниже. Цена — второй старт Servo: приложению, для которого это важно, `modes` не нужен.
- `app.launch` повторно в том же режиме — без действия, в другом — `ALREADY_EXISTS`; режим вне `modes` или в неподходящем сочетании — `INVALID_ARGUMENT`; если за 30 секунд после загрузки документа режим не выбран, процесс завершается с кодом 2 и сообщением в stderr. `app.mode()` до выбора — `undecided`.

Не входит: смена режима после выбора; выбор режима без JS (таблица «параметр → режим» в манифесте) — можно добавить отдельно, не меняя `app.launch`; запуск из Finder на macOS (процесс-родитель остаётся фоновым).

Приёмка: один манифест, три запуска e2e — `cli` (вывод в stdout и код выхода), `foreground` (HTTP-сервер отвечает, завершение по сигналу), `window` (дочерний процесс открывает окно, код выхода передаётся родителю); ошибки (`ALREADY_EXISTS`, вне `modes`, истёк срок) — модульные тесты; мутации разбора манифеста и выбора.

## Идентичность приложения

Бинарник runtime общий, поэтому автозапуск, deep links, ассоциации файлов и уведомления приложения опираются на идентичность, которую создаёт установка (`alef install`, `m7-distribution.md` M7b): ярлык с AppUserModelID (Windows), тонкая обёртка `.app` (macOS), `.desktop` (Linux). Все регистрации указывают на `alef run <пакет> ...`. Запуск на месте (без установки) даёт деградацию с понятной ошибкой `NOT_AVAILABLE` там, где нужна идентичность.

## Структура кода

```
alef-modules/src/desktop/   menu.rs, tray.rs, shortcut.rs (+ app/ autostart.rs, deeplink.rs, single_instance.rs при росте app)
packages/api/src/desktop/   menu.ts, tray.ts, shortcut.ts
```

По правилу 7 элементов `desktop/` в Rust к этому этапу превышает лимит — разделение: `desktop/app/` (app, autostart, deeplink, single_instance), `desktop/shell/` (dialog, shell), `desktop/ui/` (window, menu, tray, shortcut).

## Приёмка

| Проверка | Как |
|---|---|
| Меню приложения/окна, контекстное меню, accelerator; клики доходят | e2e + ручная (macOS строка меню) |
| Трей: иконка, меню, клики; удаление при выходе | ручная на трёх ОС |
| Глобальный хоткей при окне не в фокусе; без права — отказ | e2e (Windows/macOS/X11) |
| Автозапуск включается/выключается и переживает перезагрузку ОС | ручная |
| Режим из JS: один манифест с `modes` запускается как `cli`, `foreground` и `window` по параметрам | e2e `launch-modes` |
| Deep link запускает приложение / доставляется в запущенное | ручная после M7-упаковки; dev-регистрация — Windows/Linux |

## Реализация и статус

**Как сделано (M5.2, `menu`)** — `alef-core/src/registry/window/menu.rs`, `alef-modules/src/desktop/ui/menu.rs`, `alef-runtime/src/ui/integration/menu/{mod,model,native,unavailable}.rs`, `packages/api/src/desktop/menu.ts`:

- Валидация до передачи UI: до 256 узлов, глубина до 8, уникальные id до 128 байт, метки до 256 байт, акселераторы до 128 байт, модуль координат popup до 1e6; роль несовместима с собственным id. `x` и `y` popup задаются только вместе. Акселератор разбирает парсер `muda` (Windows/macOS) или `global-hotkey` (Linux, где `muda` нет), поэтому запись, принятая на одной ОС, на другой не отвергается по синтаксису.
- Меню — ресурс одного документа-владельца; нативные объекты и таблица живут на UI-потоке. Единственный forwarder получает события `muda`, подавляет устаревшие и отдаёт только живому владельцу; закрытие окна и перезагрузка документа освобождают его меню.
- Windows: меню приложения/окна (подкласс окна `muda`), замена и очистка; popup (`menu.popup`) показывает контекстное меню модально на UI-потоке, возвращает id выбранного пункта или `null`, `x`/`y` — логические пиксели клиентской области окна, без них — позиция курсора; выбор ждётся не дольше 500 мс после закрытия меню. Роли `copy`, `cut`, `paste`, `selectAll`, `undo`, `redo`, `minimize` — предопределённые пункты `muda` (они не отключаются и не получают id события); `quit` и `about` → `NOT_AVAILABLE`: `quit` завершил бы процесс мимо `before-quit`, а `about` не знает, как называется приложение, — пункт страницы с `app.quit()` делает то же.
- macOS: меню приложения (корни — только подменю), меню окна и popup → `NOT_AVAILABLE`; локально не проверено, ветка собирается только в CI.
- Linux: `muda` требует GTK и `libxdo`, которых нет ни у winit-цикла, ни в CI, поэтому зависимость `muda` объявлена только для Windows/macOS, а на Linux любая нативная операция → `NOT_AVAILABLE` (`menu/unavailable.rs`), валидация работает.
- e2e `menu` честно проверяет: отказы на неверные деревья, дубли id, акселераторы, роли с id, координаты и состав popup, принятие вложенного дерева с акселератором, замену и очистку меню, роли редактирования, `NOT_AVAILABLE` для `quit`/`about`, пустой popup → `null`, отсутствующее окно → `NOT_FOUND`, очистку при выходе. **Клик по пункту, акселератор, действие роли и непустой popup автоматически не проверяются** (нет синтетического ввода; сценарий пишет `MANUAL menu-click-accelerator-role-and-popup-not-tested`) — только вручную. Для пункта с акселератором в манифесте нужно право `shortcut` (`global: false`).
- Мутации: 33 в Rust (`alef-core`, `alef-modules`, таблица и модель `alef-runtime`) и 14 в JS-обёртке пойманы; выжившие первого прогона закрыты тестами или удалением лишнего кода (флаг `closed`, проверка роли в `actionable`, `Array.isArray` в обёртке).
- Зависимость `muda` закреплена на **0.19.3** (уже была в lockfile), версий не поднималось.
- Проверки (Windows): полный gate — tsc, oxlint, 224 теста JS, fmt, структура, `gen:types --check`, clippy по рабочему пространству и с `spike-integration`, тесты Rust, сборка, весь e2e и загрузка приложения-примера alef-file-manager — зелёный (тогда эта проверка была в этом репозитории; приложение теперь отдельный репозиторий, в alef-runtime её больше нет); сам `menu` прошёл 340 запусков подряд.
- Не объяснено: в первых ~70 запусках `menu` дважды случился сбой — один раз `alef.exe` вышел с кодом 0xC0000409 (аварийное завершение процесса), один раз после снятия процесса не освободились процесс и каналы; текст паники тогда не сохранили, на том же бинарнике 340 последующих запусков (в том числе три параллельных цикла с `RUST_BACKTRACE=full`) прошли чисто, и в коде `muda` 0.19.3 подозрительного заимствования не найдено. Харнесс e2e теперь запускает приложение с `RUST_BACKTRACE=1` и при неожиданном выходе или неосвобождённых каналах печатает последние строки его вывода, чтобы следующий сбой оставил улики.

**Как сделано (M5.2, `shortcut`)** — `alef-core/src/registry/window/shortcut.rs`, `alef-modules/src/desktop/ui/shortcut.rs`, `alef-runtime/src/ui/integration/{shortcut,shortcut_source,shortcut_tests}.rs`, `packages/api/src/desktop/shortcut.ts`:

- Команды `shortcut.register` и `shortcut.unregister`, право `shortcut.global` (с подменой). Регистрация — ресурс документа: ответ `{ id, owner, token }`, где `id` — `s<сессия>:r<ресурс>`, а `token` — числовая идентичность события в диапазоне 1..2^53−1, отдельная от нативного id; при подмене тоже число, но ОС не трогается. Снять регистрацию может только документ-владелец, и только по handle ровно в этом виде; перезагрузка документа и закрытие окна снимают его регистрации.
- Нативный `GlobalHotKeyManager` и таблица регистраций принадлежат UI-потоку; callback источника помечает событие уникальным токеном до помещения в ограниченную очередь и будит winit. Событие уходит только живому документу-владельцу, только на нажатие, не на отпускание. Пределы: 128 регистраций, акселератор 1..256 байт без управляющих символов; Windows использует нативные id 1..0xBFFF с безопасным переиспользованием (R-021 ниже), токены выделяются независимо от них и не повторяются. Занятая комбинация — `ALREADY_EXISTS` (на macOS так отображается и отказ Carbon).
- `Shortcut.on('pressed')` фильтрует `owner` и `token`; событие неверной формы пропускается, а не роняет обработчик.
- e2e `shortcut`, `shortcut-denied`, `shortcut-substitute`: настоящая регистрация **Ctrl+Alt+Shift+F20** (на Linux и macOS — **Ctrl+Alt+Shift+F12**: F20 нет в их раскладках, CI Linux это показал), повтор → `ALREADY_EXISTS`, неверный акселератор, снятие и повторная регистрация, чужой handle из дочернего документа → `NOT_FOUND`, закрытие дочернего окна освобождает комбинацию; отказ и подмена — отдельными запусками с собственным каталогом согласий. Сценарий не создаёт реестровых записей и файлов вне временного каталога.
- Исторические проверки M5.2 (Windows, до R-020/R-021/R-022): 810 тестов Rust по всему рабочему пространству, 207 JS, весь e2e (49 сценариев) и загрузка приложения-примера alef-file-manager (тогда в этом репозитории) прошли; `clippy --workspace --all-targets -D warnings`, tsc, oxlint, структура, fmt и `gen:types --check` чистые. Мутации: 28 в Rust (`alef-modules` и таблица `alef-runtime`) и 14 в JS-обёртке, пойманы все. Первый прогон отпустил настоящих: различие модификаторов, предел токенов Win32, повторное освобождение при sweep, закрытие окна, отображение «комбинация занята», жизнь владельца, длину акселератора, тело `unregister`, форму handle и событие с пустым payload — под них добавлены тесты, `live_owner` и `Table::release_window` вынесены, чтобы их можно было проверить без цикла событий; проверка handle сведена к одному сравнению с каноническим видом (две другие были её следствием).
- На момент M5.2 tray ещё не был сделан; трей описан ниже в M5.3. Настоящее нажатие ОС остаётся ручным (сценарий пишет `MANUAL shortcut-os-pressed-not-tested`; синтетических событий нет). Linux — только X11 с `DISPLAY` (Wayland → `NOT_AVAILABLE`), Linux и macOS локально не запускались: их ветки проверяет только CI. Подмена не проверена внешним конкурентом за комбинацию. Активный spike M0.3 владеет источником событий hotkey и исключает одновременную работу.

**Как сделано (R-020)**

- Подмена `shortcut.register` отвечает числом, как и настоящая регистрация; внутри модуля у подменённой регистрации по-прежнему нет нативного токена (`None`): host не вызывается ни при регистрации, ни при снятии. Снятие по handle, ошибки чужого и уже снятого handle и освобождение ресурса идут общим путём. Модуль принимает от host токены 1..2^53−1, в том числе выше 0xBFFF.
- Токены подмены и настоящих регистраций выдаёт один процессный `ShortcutToken::allocate()` в `alef-core` (проверяемый монотонный `AtomicU64`, без оборачивания): общего диапазона, чётности и шага нет, поэтому токен подмены нельзя отличить от настоящего, он не совпадёт с живым токеном даже после ужесточения согласия, и событие для него никогда не приходит. Исчерпание — ошибка `INTERNAL`.
- JS: `Shortcut` остаётся публичным классом, но `owner` и `token` — приватные поля, конструктор приватный, экземпляр создаёт только `shortcut.register()`; на экземпляре видно только `id`. Подмена идёт тем же путём подписки, отмены и снятия, ветки `null` нет. Тест типов компилирует потребителя через `typescript/unstable/sync` и проверяет, что `owner`, `token` и конструктор недоступны.
- Проверки: Rust (форма ответа подмены, границы токена, уникальность токенов при конкурентном выделении, снятие подмены как настоящей, подмена после ужесточения согласия не совпадает с живым токеном), JS и e2e `shortcut-substitute`. Мутации: пять в этой части (аллокатор оборачивается, выдаёт ноль, подмена показывает `null`, у всех подмен один токен, токен выше диапазона Win32 отвергается) пойманы все.

**Как сделано (R-021)**

- Токен события (его видит страница) и нативный id — разные числа. Нативный id берётся из пула: на Windows это 1..0xBFFF с переиспользованием, на остальных ОС монотонный процессный счётчик до `u32::MAX` без переиспользования (доказанного барьера очереди для macOS и X11 нет).
- Источник событий: `set_event_handler` крейта `global-hotkey` 0.8.0 ставится до создания менеджера; обработчик под mutex берёт `нативный id → токен` и кладёт уже помеченное событие нажатия в ограниченную очередь (256, переполнение сбрасывает новое). Маршрутизация сравнивает токены, поэтому событие старой регистрации не достанется новой, получившей тот же нативный id. Запись источника удаляется до снятия регистрации: нажатие снятого id в очередь не попадает.
- Переиспользование (Windows): после успешного `unregister` UI-поток выбирает свои `WM_HOTKEY` через `PeekMessageW(NULL, WM_HOTKEY, WM_HOTKEY, PM_REMOVE)` и `DispatchMessageW` (сообщения других владельцев обрабатываются как обычно, не больше 256 за проход) и только когда нативная очередь пуста, возвращает id в свободный пул; пока барьер не завершён, id остаются в карантине. Ошибка нативного `unregister` оставляет запись в `retiring`, id не возвращается. Номер, который система не дала занять, возвращается в пул сразу: ОС его не держала.
- Проверки: churn больше 0xBFFF регистраций без исчерпания, неудачное снятие, незавершённый барьер, событие старой регистрации не доходит до новой, отпускание игнорируется, нажатие снятого id не ставится в очередь, id не переиспользуются там, где барьера нет, не повторяются между менеджерами, отказанный id берётся снова. Мутации: двенадцать в этой части пойманы все (одна, удаление записи источника при снятии, сначала не была поймана и получила тест очереди). Не проверено: настоящий слив `WM_HOTKEY` на Windows (нужно реальное нажатие) и поведение на Linux и macOS (проверяет только CI). Обработчик крейта держится на `OnceCell` и молча не ставится повторно; иного потребителя, кроме исключённого spike, в runtime нет, но это ограничение, а не проверенная гарантия.

**Как сделано (R-022)**

- В `window/app.rs` результат оконной операции разбирает `handle_result`: отказ drag-resize, нормализации прокрутки, синхронизации viewport, redraw/reveal и публикации snapshot идёт в лог и не заканчивает приложение; ошибка запуска (иконка, открытие окна, создание контекста) остаётся фатальной. Тик разбирает reveal, quiet redraw и snapshot независимо, поэтому ошибка viewport не блокирует публикацию состояния.
- Повторяющийся отказ одной операции пишется один раз за эпизод (до её следующего успеха), иначе тик повторял бы строку каждые несколько миллисекунд.
- Проверенные `synchronize_viewport`, `redraw`, `try_reveal` возвращают только несовпадение размера поверхности, а это не потеря GL-контекста; отдельного результата «контекст потерян» эти методы не дают, поэтому правило «завершать только при потере контекста» сводится к «завершать только при ошибке запуска». Если такой результат появится, он должен быть фатальным.
- Проверки: оконная ошибка не фатальна ни для одной операции и ни для одного вида ошибки, ошибка запуска фатальна; первая ошибка операции пишется, повторные нет, успех возобновляет запись. Мутации: четыре в этой части пойманы все. Вручную: на каких оконных менеджерах Linux `drag_resize_window` возвращает ошибку и что видит пользователь при постоянном несовпадении поверхности (окно без картинки, ошибка в логе один раз).

- Право: `permissions.tray` — необязательный bool (по умолчанию `false`, поле не ломает старые манифесты), отдельное право `tray` без scope с тремя исходами. Подмена: вызовы «успешны», ОС не трогается, события не приходят, форма ответа та же; отказ и необъявленное право — `PERMISSION_DENIED`.

Трей — ресурс документа-владельца: `destroy`, закрытие окна, перезагрузка документа и выход снимают иконку; неудачная замена оставляет прежнее состояние, неудачный `destroy` — ресурс для повторной попытки; изменение трея, который в этот момент уничтожается, — `NOT_FOUND`.

Меню — то же дерево, что у `menu` (та же проверка); акселераторы в меню трея запрещены (на Windows у иконки нет окна, которому их передать); на Linux любые роли в меню трея не поддерживаются и отклоняются с `InvalidInput`, акселераторы запрещены как и раньше; роли copy/cut/paste/selectAll/undo/redo/minimize — предопределённые пункты `muda`, `quit`/`about` → `NOT_AVAILABLE`.

GTK не нужен. **Как сделано (M5.4, режим запуска из JS)** — **автоматический gate Windows завершён**; терминальные и платформенные ограничения — ниже. **M5 целиком ещё не принят**: остаются ручные проверки других частей этапа.

- Манифест проверяет `modes` и `entry` по правилам выше; пустой/отсутствующий список сохраняет прежний запуск. `app.mode()` и `app.launch()` используют общее процессное состояние под одной блокировкой: до выбора — `undecided`, повтор того же режима — без действия, другого — `ALREADY_EXISTS`, неразрешённого — `INVALID_ARGUMENT`. Неудачное принятие оконного запуска не фиксирует режим. `app.stdin`, `app.stdout`, `app.stderr` доступны только после выбора `cli`; в `undecided`, `foreground` и `window` — `NOT_AVAILABLE`.
- Срок выбора — 30 секунд **после полной загрузки документа `entry`**, не от старта процесса; повторные уведомления загрузки срок не перезапускают. Истечение сообщается один раз в stderr и завершает процесс с кодом 2; запоздалый `app.launch` получает `TIMEOUT`.
- Оконный ребёнок стартует только после полного завершения headless-фазы, остановки моста и слива консольных потоков. `relaunch` сохраняет исходные `OsString`-аргументы, добавляет скрытый `--launch-mode window` **перед** ними; строгий парсер не допускает другой режим, повтор или отсутствующее значение. Окружение (включая `ALEF_HOME`), cwd и stdio наследуются, сохранённые решения о правах ребёнок читает из того же хранилища без повторного запроса. Родитель ждёт ребёнка и передаёт код выхода (на Unix сигнал — `128 + signal`, непредставимый код — 1).
- Windows: Job Object с `KILL_ON_JOB_CLOSE` назначается через `PROC_THREAD_ATTRIBUTE_JOB_LIST` при создании процесса, **до исполнения кода ребёнка**; нет промежутка между spawn и последующим присоединением к job. Закрытие последнего handle job, в том числе при гибели родителя, завершает принадлежащие job процессы.
- Перезапуск (`app.relaunch`) не часть защиты: оконный ребёнок, запустивший замену, при выходе не уносит её. Windows: job лаунчера с `BREAKAWAY_OK`, замена стартует с `CREATE_BREAKAWAY_FROM_JOB` (если job процесса флаг не разрешает, замена стартует внутри него). Unix: замена в своей группе процессов, поэтому ни `kill(-группа)` лаунчера, ни watchdog macOS до неё не дотянутся. Без этого замену убивало бы вместе с остатками ребёнка (находка проверки: сценарий `app.relaunch()` из ребёнка не покрыт e2e, закрыт тестами `a_program_started_again_from_a_job_outlives_the_job`, `a_program_the_child_started_again_outlives_the_parent_and_the_child_does_not` и, для Unix, `a_program_started_again_leads_a_group_of_its_own`; последний здесь не запускался, его проверит CI).
- Linux: отдельная группа процессов, пересылка `SIGINT`/`SIGTERM`/`SIGHUP` группе; `PR_SET_PDEATHSIG(SIGKILL)` защищает непосредственно ребёнка при гибели создающего родительского потока. Это не гарантия уничтожения произвольных потомков, ушедших из группы.
- macOS: отдельная группа и fork-watchdog с нативными `kqueue`/`kevent`, наблюдающий завершение родителя и ребёнка и убивающий группу. Нативное выполнение **не проверено**; watchdog должен получить процессорное время, его внешняя остановка/уничтожение обходит эту защиту. Это не безусловная гарантия ОС, как Windows job.
- Зависимости лаунчера дополнительно закреплены на уже существующих `windows-sys = 0.59.0` и `libc = 0.2.189`: в lockfile добавлены только два ребра зависимостей, новых пакетов нет. Окно согласия перенесено из `consent_window.rs` в `consent/window.rs`, чтобы сохранить лимит 7 элементов каталога; изменения механизма согласия не требовались.
- Проверки (Windows): `alef-core` — 302 теста, полный suite `alef-modules` прошёл (3 ранее существовавших ignored; точный total не заявлен), `alef-runtime` — 110, `alef` — 45, JS — 239. Сборка и `clippy --workspace --all-targets -D warnings`, fmt, tsc, oxlint, структура и `gen:types --check` (51 экспорт) прошли. Кросс-clippy только `alef-core` и `alef-modules` для Linux/macOS прошёл; Unix-лаунчер и runtime этим не проверены и не объявляются собранными.
- Ручные мутации: по сохранённым результатам 12 мутаций пойманы целевыми тестами, исходники восстановлены (3 — манифест, 4 — состояние выбора, 3 — парсер/runtime, 2 — spawn/код выхода); большинство строк выбора покрыто 10 из них. Это подтверждение целевых проверок, не полный mutation gate и не независимый повтор каждой мутации.
- Свежая Windows-сборка из исходников этого worktree дала `compiler-artifact` с `fresh: false`; SHA-256 начинается с `bb72fd3c`, копия для e2e совпала с артефактом. Прежнее исчезновение общего бинарника осталось необъяснённым; это история, не текущий блокер.
- Итоговый наблюдавшийся e2e: **9 групп PASS** — `app`, `relaunch`, `console`, `service`, `service-signal` (доставка сигнала на Windows явно skipped), `arguments` (8 случаев), `launch-modes`, `core`, `manifest` (18 случаев). `launch-modes` — пять запусков: `cli` → 7, оконный ребёнок → 9, `foreground` по запросу → 5 дважды, `undecided` → 2. Проверены `/ping`, `/quit`, `before-quit` и освобождение процессов/pipe; Windows fallback по запросу не считается проверкой сигнала.
- Ограничения сигнала: отдельный Node v24.12.0 child на Windows после `process.kill(ownedPid, 'SIGTERM')` завершился с code 1 / signal null, обработчик SIGTERM не исполнился. Runtime слушает консольные Ctrl+C/Ctrl+Break/close/shutdown; portable harness не доставляет эти события и явно пропускает доставку сигнала на Windows. **Ctrl+C/Ctrl+Break остаются ручными**, Unix SIGTERM (ожидаются exit 143 и `before-quit`) — для CI, здесь не запускался. Нативное выполнение Linux/macOS и терминальные проверки не закрыты автоматическим gate Windows.
